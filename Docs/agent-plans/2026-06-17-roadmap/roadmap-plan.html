Conventions used in every milestone. Commit messages follow the existing type: lowercase summary convention (feat, fix, refactor, style, test, docs) seen in the git history. Each milestone adds or updates tests in the same style (Swift Testing for units; XCUITest for the smoke suite) and must leave the full FITScope.xctestplan green. API keys are entered at runtime and stored in the Keychain — never committed or logged.

Selective UI-test runs. The full FITScopeUITests suite is very long (~13 min). For changes that don't touch UI behaviour — e.g. an additive presentational element, or logic fully covered by unit tests — run only the directly relevant UI test(s) (-only-testing:FITScopeUITests/FITScopeUITests/<testName>) rather than the whole suite, and the unit suite (which is fast). Note: interrupting an in-flight xcodebuild can leave an unsigned .xctest in the built app and break the next incremental build with a CodeSign error — run xcodebuild clean if that happens.

Implementation notes — done & verified.
  • Design change (sandbox). The planned env-var hook (FITSCOPE_UITEST_FIXTURE → open by path) is incompatible with the app sandbox (files.user-selected.read-write only): a sandboxed app cannot read an arbitrary path, and the maintainer requires the sandbox to stay intact with no test data shipped in the app. Instead the suite drives the standard Open panel (powerbox), which grants sandbox access exactly as a user selection would. Key facts confirmed at runtime: the app-under-test has no XCTest injected, so its existing isRunningTests guard is false under XCUITest and it already presents its launch Open panel — no app launch-logic change needed; and on macOS 26 that panel appears inside the app's own accessibility tree (a dialog with identifier open-panel), so it is driven through the main app element via ⌘⇧G + path + Return, not through the out-of-process panel-service bundle.
  • Fixtures. The suite uses two in-repo fixtures under FITScopeUITests/Fixtures/, so it no longer depends on the SwiftFITS submodule corpus (which may change). MonoImage.fits is a real NAXIS=2 image that renders. InvalidImage.fits is a hand-crafted dummy whose header omits the mandatory SIMPLE keyword — chosen over a real unsupported-geometry file (e.g. NAXIS=6) precisely because such a file could become supported later and silently break the error-path test, whereas a missing SIMPLE is rejected unconditionally by SwiftFITS (mandatory-keyword order is never relaxed, even in lenient mode) and can never be valid. Verified against the real parser: the dummy throws “Missing property SIMPLE expected at index 0”; the image parses cleanly. Both are resolved by filesystem path (relative to #filePath) and are deliberately not bundled into any target.
  • Identifiers. A single shared AccessibilityIdentifier enum, grouped into one nested sub-enum per view (e.g. AccessibilityIdentifier.ImageToolbarView.zoomIn). Each string value mirrors its qualified path (e.g. "ImageToolbarView.zoomIn"), so an identifier seen in the accessibility inspector or a test failure names its component and role directly. The file has no app dependencies and is a member of both the app and UI-test targets, so the tests reference the same constants — no hardcoded strings. Annotated: image canvas, loading/error views, status pill, files list + rows, add-files button, inspector container + sections + reset, gamma toggle, floating-toolbar buttons, inspector toggle, headers table/picker/search. Inspector-section identifiers are explicit stable constants (InspectorView.Section.gamma, …) passed into the generic InspectorSectionView — not derived from the section's display title, so renaming or localizing a heading can't silently break the tests.

Added testAccessibilityIdentifiersAreWired: after opening a file it asserts every always-present identifier resolves (canvas, files list, file row, inspector + toggle, gamma section, gamma toggle) — one cheap guard against a mis-wired identifier, rather than a brittle test per identifier; the per-flow tests then drive these for real. The headers-window controls and the loading/error placeholders appear only in states this test doesn't enter and are covered by their flows.

Commit
fix: keep fitted images fitted on resize and clamp zoom-out
Implementation notes — done & verified.
  • Pure geometry first (TDD). Four new helpers on CanvasGeometry, each covered by unit tests written and watched to fail before implementing: boundedFitFactor (the fit magnification, clamped to the scroll view's minimum…maximum range so an extreme content-to-viewport ratio can't exceed those bounds — re-evaluated on resize to keep an image fitted), minimumMagnification (the smallest useful zoom = the fit factor, but never above 1.0 so actual size stays reachable for a small image scaled up to fit, nor below the 0.05 floor), canZoomOut (whether the current magnification sits meaningfully above the minimum bound), and isFitted (whether the magnification is at the fit magnification, used to decide whether a resize should re-fit). 10 new tests added to CanvasGeometryTests; suite 14/14 green.
  • Two distinct concepts. The "is the image currently fitted?" decision (drives re-fit on resize) compares against the fit magnification, while the "may the user zoom out?" decision compares against the minimum magnification. These differ for a small image, which fits while scaled up above 100% yet must still allow zooming out down to actual size — so they are deliberately separate functions rather than one shared bound.
  • Canvas re-fit on resize. ZoomableImageView.Coordinator now recomputes its fit geometry on every viewport (clip-view frame) change. If the image was fitted before the resize it re-fits; otherwise it just refreshes the zoom-out bound for the new size. The scroll view's minMagnification is set to the computed minimum (no longer a fixed 0.05), so pinch/scroll/toolbar zoom-out all clamp at the fit bound. The vestigial contentSize field (only ever assigned) was removed.
  • Zoom-out enablement. The coordinator reports canZoomOut whenever the magnification or viewport changes; ImageCanvasView holds it as state and passes it to ImageToolbarView, which disables the zoom-out button when the whole image is visible. The pure decision lives in CanvasGeometry.canZoomOut, so the view stays thin and the logic is unit-tested.
  • Output callbacks instead of bindings (review). Per the maintainer's preference against the property-wrapper _ prefixes, the canvas reports magnification and zoom-out availability through plain onZoomChange / onCanZoomOutChange closures (matching the existing onHover) rather than @Bindings — both values only ever flow out of the canvas, so this is also the more honest data flow.
  • Resize border fix (review). Reported: zooming in and then enlarging the window left the image smaller than the viewport with black borders on all sides — the zoomed-in (not-fitted) branch had left the magnification untouched while the viewport outgrew it. Fixed with a new pure CanvasGeometry.magnificationAfterResize (a fitted image follows the new fit magnification; a zoomed-in image keeps its magnification but never drops below fit, so it snaps up to fill the viewport). Recentering happens only when the magnification actually changes (or while fitted), so a zoomed-in pan position is preserved across a resize. Covered by four new unit tests.
  • Pan-past-edges fix (review). Reported: a click-drag pan could drag the image past its edges, showing the black background. The manual pan in HoverImageNSView.mouseDragged called clip.scroll(to:) with an unconstrained origin, which bypasses the clip view's bounds constraint. Now the proposed origin is routed through CenteringClipView.constrainBoundsRect (which clamps the larger dimension and centres the smaller one) before scrolling, so a pan stays within the image. This is an AppKit interaction left to manual verification, consistent with the suite's documented pan/drag exclusions.
  • Verified. FITScopeTests unit suite green (69 tests, 21 suites). The toolbar-zoom UI test (testToolbarZoomControlsChangeReadout) still passes — it clicks zoom-out only after zooming in, so the new disabled-at-fit state doesn't affect it. Resize-keeps-fitted behaviour is an AppKit interaction left to manual verification (per the suite's documented UI-test exclusions); its geometry is unit-tested.

fix: stabilize the split-view layout while a window is still loading
Implementation notes — done & verified.
  • Root cause (measured, not guessed). A first attempt — relaxing LoadingView's rigid minWidth: 400, minHeight: 300 — was insufficient: the maintainer reported the sidebars still clipped with an invalid image (which uses ErrorView, untouched) and while a normal image loaded. fix: complete off-screen renders and re-renders of an already-open file
Implementation notes — done (model layer verified; warning fix needs maintainer's console confirmation).
  • Original hypothesis was wrong. The plan blamed a "colliding identity," but OpenFile.id has always been a unique UUID and the canvas keyed its render task on it, so two opens of the same URL were already independent. The real, surfaced problems were: (a) non-displayed files never rendered at all (rendering was driven solely by the displayed canvas's .task), and the keystone issue — driving load/render from the view's .task made every model @Published write happen "within view updates," which SwiftUI rejects (the "Publishing changes from within view updates" console warning, proven via an in-container stack capture to originate from load()/render() running inside ImageCanvasView's .task).
  • Architectural fix (maintainer chose the full redesign, option b). Load → render → thumbnail now runs in a model-owned task on OpenFile (prepare(throttle:)), not the view. WindowModel.open() prepares every opened file, so non-displayed rows render and update on their own (fixes (a)); close() cancels a file's preparation. Because the work is no longer in the view's .task, the model's @Published writes land outside SwiftUI's update pass — fixing the warning at the architectural level rather than per-write. ImageCanvasView now only observes the result and resets its own per-file view state.
  • Concurrency cap (option b). A RenderThrottle (a main-actor FIFO counting semaphore, limit = max(2, cores − 2)) owned by WindowModel bounds how many files render at once, so opening many files can't saturate the CPU. (Total memory still grows with the number of rendered results — releasing off-screen results is a possible later refinement; not in scope.)
  • The actual "publishing within view updates" culprit (found by instrumentation, after several wrong guesses). Moving load/render off the view did not stop the warning when switching to an already-rendered file. Logging every ObservableObject's objectWillChange (with a stack, to a file in the sandbox container) during a switch showed it was WindowModel: List(selection: $model.selectedFileID) writes the @Published selection from within SwiftUI's update pass (ViewGraphRootValueUpdater.render) on every row click, and MainWindowView.onAppear calls open() (setting @Published files/selection) during the update on launch. Not the render pipeline, not @State, not ImageAdjustments (all ruled out by the capture). Fixed by writing those through deferred bindings/calls (DispatchQueue.main.async) so they land on a fresh run-loop turn; re-running the capture confirmed no WindowModel publish now occurs during an update. The interim FITSImageLoader run-loop hop was reverted (the model task supersedes it); the canvas zoom-report and .task deferrals are kept as the same "don't write observed/view state during the update pass" hygiene.
  • Scope. Per the maintainer, M1.4 (status pill, disabled controls, canvas overlay, attention icon) was not pulled in; this milestone covers the lifecycle + off-screen completion only. The per-row spinner now reflects RenderPhase (added earlier).
  • Verified. New unit tests: RenderThrottle caps concurrency; OpenFile.prepare loads+renders+thumbnails and is idempotent; WindowModel.open prepares every file to ready; close cancels preparation. Full unit suite 87/23 green. UI: render, error, identifier-wiring, toolbar zoom, multi-file selection switch, floating bars, and close all pass. The console warning's absence can't be asserted in the harness (app-process only), so it needs the maintainer's confirmation in Xcode.
