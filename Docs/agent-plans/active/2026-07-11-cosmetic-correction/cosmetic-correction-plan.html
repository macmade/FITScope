Generated: 2026-07-12

Overview

The backlog item asks that unstretched images no longer have their min/max normalization range distorted by hot pixels. Rather than bolt outlier logic onto the normalization stage, we add a dedicated Cosmetic Correction stage that repairs defective pixels (hot and cold) before any other processing, with a matching, user-togglable control in the inspector. Because the repair happens on the raw samples, every downstream stage benefits — normalization and the auto-stretch derivation — and the fix generalizes from "don't let outliers skew the range" to "remove sensor defects from the displayed image."

The stage lives in the SwiftPixel submodule as a new PixelProcessor, inserted before the channel-forming/debayer stage so a hot pixel is repaired on the raw mosaic before demosaicing can smear it across its neighbours. Detection is a conservative, neighbour-based robust test (median + MAD of same-kind neighbours); correction replaces a detected defect with the median of those neighbours. Both hot- and cold-pixel correction are independently configurable, and the whole stage is on by default with intentionally conservative thresholds so it only touches unambiguous, isolated spikes and cannot erase faint stars out of the box.

Questions & answers

Should hot-pixel handling be part of normalization, or a separate processor before normalization, togglable in the inspector?
A standalone processor, placed before debayer, with a matching inspector control.
Range-estimation fix only, or full pixel repair?
Full hot-pixel correction — the stage repairs the pixels, not just the range used for normalization.
What should be configurable?
Hot-pixel correction, cold-pixel correction, and any other meaningful options (exposed here as an independent enable + strength for each of hot and cold, under a master enable).
On by default?
Yes — on by default. Agreed, with one recorded reservation: FITScope is also an inspection tool, so a default-on stage that edits pixels can hide sensor defects a user may want to see and, if detection ever misfires, could erase faint stars. Mitigation baked into the plan: detection is deliberately conservative (isolated single-pixel spikes only, safe threshold), so the out-of-box risk is negligible; users who want it stronger can raise the strength.
Does the pre-debayer placement require knowing the Bayer pattern?
No. Same-colour CFA neighbours are always at even offsets (±2, 0), (0, ±2), (±2, ±2) for any Bayer pattern (a shift of 2 lands on the same cell of the 2×2 tile), so the stage only needs to know the source layout (mono / CFA / RGB), which comes straight from PixelPipeline.Config.inputFormat. The concrete pattern is not needed.

Implementation notes

Implemented test-first (Swift Testing). Added Processors/CosmeticCorrection.swift conforming to PixelProcessor and Equatable, with:

  • A nested Layout enum (mono / cfa / rgb) that exposes a step (1, or 2 for CFA so step-2 offsets always land on the same Bayer colour for any pattern) and a required channels count (1 for mono/cfa, 3 for rgb). A single interleaved index formula (ny·width+nx)·channels + channel with the layout's step covers all three layouts, so no per-pattern knowledge is needed.
  • A nested Parameters value type (isEnabled, correctHot + hotThreshold, correctCold + coldThreshold): Sendable, Equatable, CustomStringConvertible, with a conservative enabled .default (both corrections on, k = 8.0).
  • Detection per sample: gather in-bounds same-kind neighbours (≤8), compute the neighbour median m and σ = max(1.4826·MAD, sigmaFloor); flag hot when correctHot, the sample is a strict local maximum (v > neighbourMax), and v − m > hotThreshold·σ; cold is the symmetric condition. The strict-local-extreme requirement is the primary star-safety guard (a multi-pixel blob's peak is not strictly greater than its equally bright neighbours), and it also blocks flat-region false positives together with the sigmaFloor.
  • Correction reads from the original samples and writes into a copy (var output = pixels, made unique by withUnsafeMutableBufferPointer), so a repair never feeds back into an adjacent pixel's detection. Parallelized with PixelUtilities.parallelOrSerial using the same nonisolated(unsafe) pointer idiom as readRawPixels; each iteration writes only its own output slot. Borders use whatever in-bounds neighbours exist. Rebuilds the buffer preserving isNormalized.

Decisions. The stage is value-range-agnostic (neither requires nor changes normalization); it is a no-op when disabled or when both corrections are off, and throws unsupportedChannelCount when the buffer's channel count does not match the layout. sigmaFloor (1e-6) and the default k = 8.0 are deliberately provisional — the plan settles the final flat-region guard form and thresholds empirically in Milestone 6. The Xcode project uses explicit file references (no synchronized groups), so both new files were registered by hand in all four project.pbxproj sections (build file, file reference, group, Sources phase) following the existing hand-assigned ID scheme; SwiftPixel's Package.swift globs the target directory, so it needed no change.

Added SwiftPixelTests/Processors-CosmeticCorrection.swift (18 tests): name/description, Equatable, conservative default, single hot/cold repair to neighbour median, hot/cold toggles, multi-pixel star left intact, flat-region-with-noise no false positives, corner (partial neighbourhood) repair, CFA step-2 same-colour sampling, RGB per-channel, disabled/constant/empty no-ops, normalization-flag preservation, and wrong-channel-count throwing.

Round 1

  • Per-pixel vDSP.sort + allocations in the hot path — Medium (Performance). repairedValue called PixelUtilities.median/medianAbsoluteDeviation, each triggering a vDSP.sort whose setup cost dominates on an ≤8-element array and would run tens of millions of times on a 24 MP frame, plus a redundant second median and separate max()/min() passes. Not a defect (matches the plan's guard), but the absolute 1e-6 floor means very different things for 16-bit vs [0,1] data. Deferred: the plan settles the flat-region guard/threshold form empirically in Milestone 6; consider making the floor relative to the local level or a noise estimate there.
  • = alignment not maintained in corrected — Low (Style). Fixed: re-aligned the three assignments.

Review comments
  • No use of Accelerate here? — asked why the processor uses no Accelerate/vDSP, unlike the other SwiftPixel processors. Appendix — Detection & correction algorithm

Neighbour lattice (by layout). For each pixel, the "same-kind" neighbours are:

  • mono: the 8 pixels at offsets (±1, 0), (0, ±1), (±1, ±1), single channel.
  • cfa: the 8 pixels at offsets (±2, 0), (0, ±2), (±2, ±2), single channel — always the same Bayer colour regardless of pattern, because a shift of 2 lands on the same cell of the 2×2 tile.
  • rgb: the same 8 step-1 offsets, but per channel — read the matching channel of each neighbouring pixel (interleaved, channels-strided).

Detection. Let m = median of the neighbours and σ = 1.4826 · MAD(neighbours around m) (a robust standard-deviation estimate). A pixel value v is:

  • hot when correctHot and v > m + hotThreshold · σ;
  • cold when correctCold and v < m − coldThreshold · σ.

Flat-region guard. When the neighbourhood is (near-)uniform, σ ≈ 0 and the test above would flag any tiny deviation. Guard by additionally requiring the pixel to be a strict local extreme (exceed the neighbour max for hot / fall below the neighbour min for cold) by a margin, and/or floor σ with a small absolute epsilon. Final form to be settled in Milestone 6.

Star-safety. A real star spans several pixels, so the neighbours of its peak are also bright, raising m; the peak therefore does not exceed m + k·σ at a conservative k. Only genuinely isolated single-pixel spikes are flagged. This is the property Milestone 6 verifies.

Correction. Replace each flagged pixel with the neighbour median m. Read from the original buffer and write into a copy so a correction never influences the detection of an adjacent pixel in the same pass. Border pixels (incomplete neighbourhoods) are clamped/mirrored or left untouched.
