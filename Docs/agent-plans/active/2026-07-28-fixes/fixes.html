A short backlog of defects observed while using FITScope: an unexpected system permission prompt at launch, an overlay that is not always correctly registered to the image right after loading, and poor responsiveness when several images are loaded at once.

Backlog

  1. Unexpected "access data from other apps" prompt at launch

    Launching the app now triggers the system prompt asking for permission to access data from other applications. FITScope should not require this, and the prompt should not appear at all.

    This is recent behavior. The app group has been in place for a long time and the prompt was not appearing back then, so unless something environmental has changed, this looks like a regression.

  2. Stars overlay is sometimes misaligned right after loading an image

    After loading an image and toggling the stars overlay on, the star markers are sometimes drawn slightly off from the stars they mark. Zooming in or out corrects the alignment, and it stays correct afterwards. Whether the other canvas overlays are affected in the same way has not been checked.

  3. Poor responsiveness while loading multiple images at once

    When several images are loaded in one go, the app does not stay responsive enough while they are being processed. Selecting a file in the sidebar during that time does not immediately switch to it: the view keeps showing a previously selected image instead. How it resolves has not been pinned down — it is unclear whether the correct image eventually appears on its own or whether the selection has to be made again.

  4. Star detection blocks the file preparation pipeline

    Opening several images at once paints their previews far more slowly than rendering them requires: the pipeline advances at the speed of star detection rather than of rendering.

    OpenFile.prepare() acquires a RenderThrottle slot and holds it across load → render → star detection → thumbnail. With the limit at max(2, cores−2), one file's detection therefore gates when the next file may start loading and rendering at all, and detection is by far the longest of those stages. prepareSelectedFrame() has the same shape for carousel frames, holding a high-priority slot across detection. A file's own thumbnail does not wait on its own detection — the render commit starts it concurrently — so this is a throughput problem across files rather than a per-file one. Likely related to item 3.

    What needs to be done. Detection should run as its own task so a preparation slot covers load → render → thumbnail only. Four constraints shape that:

    • The analysis must stay CPU-bounded — detaching it outright lets a session folder spawn a detection per file and saturate the machine, which is what the throttle exists to prevent.
    • It must inherit the priority of the work that spawned it. The selected file prepares at high; queuing its analysis at normal leaves the stars for the frame on screen waiting behind every background file's preparation.
    • It must be enqueued immediately after the render, not after the thumbnail wait: makeThumbnail resizes on the global utility queue, which a folder of opening files saturates, so anything sequenced after it inherits that delay.
    • LoadedImage.isDetectingStars drives the toolbar's star-detection indicator and is set only once detection actually starts. It has to mean "queued or running" — set when the work is enqueued, cleared if it is abandoned in the queue — or the indicator reads as idle for the whole wait.
