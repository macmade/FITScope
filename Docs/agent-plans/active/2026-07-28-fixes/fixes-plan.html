Overview

The source backlog records four defects observed while using FITScope: an unexpected “access data from other apps” system prompt at launch, a stars overlay that is not always registered to the image right after loading, poor responsiveness while several images load at once, and star detection gating the file-preparation pipeline. Only the fourth arrives with a worked-out design; the other three describe symptoms whose cause has not been established.

The plan therefore alternates diagnosis and fix milestones rather than assuming a cause. It runs in the order the permission prompt forces: item 1 first, because the prompt blocks test runs and nothing else can be verified until it is gone; then item 2; then item 4; and finally item 3, re-measured after item 4 lands, since the backlog itself notes the two are likely the same problem. Each milestone is scoped to be reviewable and committable on its own, and carries its own status, implementation notes and review fields, which the implement command updates in place as work progresses.

Questions & answers

Items 1–3 need diagnosis before a fix can be specified, while item 4 comes with a concrete design. How should the plan be ordered?

Item 1 needs to be fixed first, as it affects testing — the prompt prevents tests from running. Then item 2. Then item 4. Then evaluate / re-measure item 3 and fix if necessary.

Item 1’s likely suspects include SwiftUtilities (the embedded, unsandboxed Updater.xpc service and the launch-time update check). May the plan propose changes inside the submodules?

Propose, but ask before changing. The plan may identify a submodule as the root cause and describe the change; every submodule edit is put to the user for approval before it is made.

Item 2 notes that whether the other canvas overlays are affected “has not been checked”. What should the fix cover?

The shared displayed-rect plumbing. All overlays draw through the same displayedImageRect published by ZoomableImageView, so fix it once at the source and verify every overlay (stars, objects, grid, reticle, scale bar, north) registers correctly.

What verification should each milestone require?

Unit tests plus a manual check: XCTest coverage for the testable logic (queue behaviour, geometry, indicator state) and hand-verification of the visible symptoms in the running app.

Conventions to follow

  • The Xcode project is authoritative: build and test through xcodebuild with FITScope.xcodeproj, not swift build. Keep project.pbxproj in sync with any file added or moved.
  • Match the surrounding style: let over var, no force-unwraps, aligned =, early returns, one type per file, doc comments on private members too.
  • Comments describe the code as it is — never what changed. Rationale for changes belongs in the commit message and in this plan’s implementation notes.
  • Submodule edits (SwiftUtilities, SwiftAstro, xcconfig) are proposed here but must be approved before they are made.
  • Never commit, push, or run git pull / git submodule update; leave that to the user. Never skip or delete a test to make a milestone pass.

Risks

  • Item 1 may be environmental. The backlog allows for that (“unless something environmental has changed”). Milestone 1 must be able to conclude “not a code defect” and say so, rather than forcing a code change.
  • Sandboxing the updater service may break in-app updates, since replacing the application bundle is exactly what a sandbox forbids. Milestone 2 carries an explicit fallback for that outcome.
  • Two concurrent pools can oversubscribe the CPU. Splitting detection out of the render throttle means preparation and analysis run side by side; if their limits are not chosen together, item 4’s fix could make item 3 worse rather than better.
  • Detaching detection changes observable ordering. Weights, the sidebar pill and the Analysis tab all key off metrics that arrive from detection; they will now settle later than the render. Existing tests that await preparation to observe a star field will need a new await point rather than a relaxed assertion.

Open questions

  • Whether the analysis queue should be a second RenderThrottle instance or a new type. The existing throttle already provides bounded concurrency, FIFO ordering and promotion; the only gap is that a caller cancelled while suspended still consumes a slot hand-off. Milestone 5 decides, preferring reuse.
  • Whether LoadedImage.detectStars() should keep owning the isDetectingStars / hasDetectedStars transitions, or expose them so the enqueuing caller can drive the “queued” state. Milestone 6 decides.

Goal

Establish, from the system’s own record rather than from inference, which process asks for “access data from other apps”, which application TCC holds responsible, and what it was trying to read. Nothing else in the plan can be verified until the prompt is gone, so this is the first milestone — and it deliberately changes no code.

Tasks
  • Reproduce deliberately: reset the decision with tccutil reset SystemPolicyAppData com.xs-labs.FITScope, then record whether the prompt appears on a plain launch, on a xcodebuild test run, or on both.
  • Capture the TCC decision while launching: log stream --predicate 'subsystem == "com.apple.TCC"' --info --debug. Record the service name (expected kTCCServiceSystemPolicyAppData), the requesting process, the responsible process, and the path that triggered it.
  • Determine whether Updater.xpc is spawned at launch — watch for the Updater process in the log or in Activity Monitor. It is unsandboxed, so any read it makes under ~/Library/Containers or ~/Library/Group Containers is TCC-gated, and prompts would be attributed to FITScope as the responsible app.
  • Use the test run as a discriminator: applicationDidFinishLaunching returns early under isRunningTests, so the 5-second background update check never runs during tests. If the prompt still appears there, the update check is ruled out.
  • Check the app-group read: AppDelegate.preferences opens UserDefaults(suiteName: "group.com.xs-labs.FITScope") during AppDelegate init on every launch. Confirm from the log whether the requester is the app itself or the nested service.
  • Rule out a provisioning problem: confirm that the com.apple.application-identifier prefix M2S7CSUC5Z against team 326Y53CJMD is a legacy App ID prefix, by checking the profile the app is signed with.
  • Note whether Debug and Release differ — the Debug build additionally carries the test-injected com.apple.security.temporary-exception.files.absolute-path.read-only for / (see Appendix A), which widens the sandbox and may change what TCC gates.
  • Write the conclusion into Implementation notes below, including the possibility that this is environmental and no code change is warranted.

Implementation notes

No code was changed. The cause was established from the system log, which had already recorded every prompt: the persisted store still held the events, so nothing had to be reproduced and no TCC decision had to be reset. All evidence below is from log show --last 3d read on 2026-07-29, covering 2026-07-26 → 2026-07-29.

The tccd evidence is perishable — read this before trying to re-run the queries. com.apple.TCC:access debug records are pruned far more aggressively than containermanagerd's. Quotes captured here between 10:19 and 11:13 on 2026-07-29 were already unreproducible by 11:45 the same morning: the retained tccd window had rolled forward to begin at 2026-07-28 18:54, dropping the 18:27 and 18:38 launches quoted below. They were verified against the raw dumps taken at capture time, and the conclusions they support are each independently corroborated by containermanagerd or launchd records, which survive. Anything below timestamped before 18:54 on 2026-07-28 should be treated as a capture-time quote, not a live query.

Root cause — the App Group identifier is not team-ID-prefixed. containermanagerd treats every app-group container as protected and grants access silently only when the requestor's signature passes “strict scrutiny”. FITScope passes none of the tests it is put through, so the request is escalated to TCC and becomes the “access data from other apps” prompt.

Apple documents the behaviour exactly, in the macOS Sequoia 15 release notes (this machine runs macOS 26.5.1):

“To protect users' privacy, app group containers (in ~/Library/Group Containers) are now protected by System Integrity Protection. […] the app must use containerURL to get the app group container path and meet one of the following requirements: the app is deployed through Mac App Store; the app group identifier is prefixed with the app's Team ID; or the app group identifier is authorised by a provisioning profile embedded within the app. If the app doesn't meet these requirements, the system might present the user a prompt to authorize the app's use of the app group container. If granted, that consent applies only for the duration of that app instance. This restriction also applies to app extensions, although in that case the system won't prompt the user for consent but will instead just deny the access. (114586798)”

(The two emphasised passages are this document's emphasis, not Apple's.) Those three requirements are precisely the three containermanagerd tests that matter, and FITScope meets none of them. Hypotheses ruled out

  • The embedded Updater.xpc is exonerated. A 3-day query on processImagePath CONTAINS "Updater.xpc" returns no entries, and the service's bundle identifier never appears in the TCC log — but that alone is only absence of evidence, since a process emitting no os_log output would look the same. The positive evidence is launchd's own record, which states the service was registered and not created: [pid/11512 [FITScope]:] will attach to com.xs-labs.SwiftUtilities.Updater next time it's created — one of 16 such messages, every one of them “next time it's created”, never a creation. That it is genuinely on-demand is confirmed from the bundle (CFBundlePackageType XPC!, ServiceType Application) and the source (NSXPCListener.service()), and UpdaterServiceLocator.isAvailable is a pure FileManager.fileExists check that opens no connection — so even a background update check could not have spawned it. It remains unsandboxed nested code, a separate concern noted below, but it does not cause this prompt.
  • The launch-time update check is ruled out, on three independent grounds. Timing: the app's sandbox is initialised at 18:27:27.885 and the prompt fires at 18:27:28.106 — about 0.2 s after launch, whereas backgroundUpdateCheckDelay schedules the check at +5 s. That launch has since been pruned, but the same 0.2 s gap is reproducible on a launch inside the retained window: launchd registers the service at 20:23:54.493, containermanagerd rejects at 20:23:54.513 and 20:23:54.681, sandboxd raises the request at 20:23:54.692 and tccd prompts at 20:23:54.702 — 0.21 s, an order of magnitude inside the 5 s delay. Test runs: the prompt fires there too, where the isRunningTests guard returns from applicationDidFinishLaunching before the check is ever scheduled. And reach: the check is gated on automaticallyCheckForUpdates, which Preferences reads from defaults, not sharedDefaults — so it never touches the App Group even when it does run.
  • Provisioning is not itself a defect. The M2S7CSUC5Z / 326Y53CJMD mismatch flagged while planning is benign: the app is signed with the wildcard “Mac Team Provisioning Profile: *”, whose com.apple.application-identifier is M2S7CSUC5Z.* — a legacy App ID prefix — while com.apple.developer.team-identifier is 326Y53CJMD. It is relevant only indirectly: that wildcard profile carries no com.apple.security.application-groups entitlement — confirmed by dumping the embedded profile — which is almost certainly why containermanagerd's profile validated entitlements test fails. The log reports only that the test failed, not why, so that last step is a well-founded inference rather than something the log states.
  • This is not environmental, and the backlog's premise is mistaken. The backlog reasons that “the app group has been in place for a long time and the prompt was not appearing back then, so unless something environmental has changed, this looks like a regression”. The App Group has not been in place for a long time: git log -S on the entitlements file returns exactly one commit, 083c28f feat(preferences): add per-format auto-stretch preferences, dated 2026-07-11 — seventeen days before the report, and nine days before the updater was embedded. The defect arrived with the feature that introduced the App Group; nothing environmental changed. The outcome is also deterministic rather than incidental: the check is decided by the code signature, so it cannot vary between runs of the same binary.
  • Why the prompt returns on every launch. Not a stale or corrupted TCC record: Apple's release note states that consent, once granted, “applies only for the duration of that app instance”. This rests on the documentation, not on the rejection counts below — containermanagerd rejects on every container lookup regardless of TCC state, and there are several lookups per launch, so those counts are not prompt counts and cannot carry the point. The consequence for milestone 2 is that its acceptance criterion cannot be “I clicked Allow and it stopped” — consent never persists anyway. Only a launch with no prompt at all counts.

Why it reaches the user before any guard can help

AppDelegate.preferences is a stored property, so Preferences() → AutoStretchPreference.sharedDefaults → UserDefaults(suiteName: "group.com.xs-labs.FITScope") runs while AppDelegate is being initialised — before applicationDidFinishLaunching, and therefore before the isRunningTests guard. That is why the prompt blocks unit-test runs: testmanagerd begins a FITScopeTests run at 20:30:37.942 and the prompt fires at 20:30:39.252 against the Debug binary. The same pairing repeats at 20:33:50 → 20:33:51 and 20:37:34 → 20:37:35.

UI tests are unaffected, and it is worth being precise about why rather than claiming the whole test plan is blocked. UITestSupport always launches the app with -uiTestingIsolatedDefaults, under which AppDelegate.makePreferences() backs the store with private suites and never opens the App Group at all. So the blocker is the FITScopeTests host specifically — which is what the log shows.

Debug versus Release

No difference in outcome. Both are rejected identically; the Debug build's test-injected temporary exceptions widen the sandbox but do not affect the app-group check, which is decided by the signature, not by file-path exceptions. Prompts were recorded against both binaries.

What Apple documents

The App Groups entitlement reference states that macOS accepts two forms: group.<name>, which requires registration on the Apple Developer website, and <team identifier>.<name>, which does not. FITScope uses the first form without the registration and profile validation that form depends on, which is what the strict-scrutiny failure reports.

Additional defect found — the extensions are hit too, in two different ways

The same root cause reaches both app extensions, but not identically, and the difference matters for how milestone 2 is verified. Apple's release note says the restriction “applies to app extensions, although in that case the system won't prompt the user for consent but will instead just deny the access”. That is true of the thumbnail extension and false of the preview one — the behaviour is a property of the extension point, not of extensions in general, and the log settles it:

ExtensionAUTHREQ_PROMPTING eventsOutcome
FITScopePreviewExtension9Prompts the user separately, on its own
FITScopeThumbnailExtension0Refused outright, silently

So there are two user-visible prompts, not one: the app's and the preview extension's. Milestone 2's “no prompt at all” criterion therefore has to include a Finder/QuickLook pass, not just an app launch.

The thumbnail extension, meanwhile, is refused without ever being offered the choice: 

tccd  Refusing TCCAccessRequest for service kTCCServiceSystemPolicyAppData
      from extension …FITScopeThumbnailExtension…, extension point disallows prompting

The consequence is visible in the extension's own fault-level output — the most direct proof of the functional bug, since it is the extension itself reporting that it could not read the preference: 

F FITScopeThumbnailExtension[68229] [com.apple.defaults:User Defaults]
  Couldn't read values in CFPrefsPlistSource<0x846c59280>
    (Domain: group.com.xs-labs.FITScope, User: kCFPreferencesCurrentUser, …):
    accessing preferences outside an application's container requires
    user-preference-read or file-read-data sandbox access

FITScopeThumbnailExtension therefore never reads the shared per-format auto-stretch preference and silently falls back to its default, whatever the user set. This is a real functional bug, not only a nuisance prompt, and it is fixed by the same change. All three targets — app, preview extension, thumbnail extension — declare the same unprefixed group.

Recommendation carried into milestone 2

Rename the group to the team-ID-prefixed form, 326Y53CJMD.com.xs-labs.FITScope, in all three entitlements files and in AutoStretchPreference.appGroupID. It needs no portal registration and no change of provisioning profile, and it is the form already proven for this team ID on this machine — though on a differently-signed binary: Xcode Format is Developer ID signed with no embedded profile, whereas FITScope is Apple Development signed with a wildcard profile. The inference still holds, because the test keys off the signature's TeamIdentifier, which codesign confirms is 326Y53CJMD for FITScope too.

It is not a submodule change: the identifier occurs in exactly four places, all in this repository — the three entitlements files and AutoStretchPreference.swift:41. It does not appear in project.pbxproj, so no Xcode-project sync is required. One remark for milestone 2 rather than a blocker: DEVELOPMENT_TEAM = 326Y53CJMD is defined in the xcconfig submodule (Common/Signing.xcconfig:26), so writing the literal team ID into the entitlements duplicates a submodule-owned value. $(TeamIdentifierPrefix) is an option for the entitlements files, though the Swift constant needs a literal either way.

Scope confirmed while reviewing: only two values can live in the shared suite, written under the keys autoStretchPreviews.fits and autoStretchPreviews.xisf (built by AutoStretchPreference.previewsKey(_:); autoStretchPreviewsFITS and autoStretchPreviewsXISF are the Preferences property names, not the stored keys). Both default to true, and the container currently holds just one of them. No test hardcodes the group ID — the tests inject their own suites. The user has since decided against migration on the grounds that the app is not yet in production (see Review comments), which this scope makes an easy call.

One caveat milestone 2 should not be surprised by: the release note's requirement is that the app “use containerURL to get the app group container path” and meet one of the three conditions. FITScope uses UserDefaults(suiteName:), not containerURL. The rename is expected to be sufficient regardless — the log shows UserDefaults driving the same container lookup that strict scrutiny gates, and Xcode Format is approved on exactly that path — but that is an inference, not something the log or the documentation states outright. If the rename alone does not silence the prompt, this is the first thing to look at.

The unsandboxed Updater.xpc remains a genuine hardening concern — an empty <dict/> entitlements file nesting unsandboxed code inside a sandboxed app — but it is unrelated to this prompt and out of scope for this plan's phase 1 goal. Recorded here so it is not lost.

B — What a preparation slot covers today

The span held by one slot of the render throttle, which is sized max( 2, ProcessInfo.processInfo.activeProcessorCount - 2 ) in WindowModel.init(). Star detection sits inside the span, which is why one file’s detection gates the next file’s load. 

OpenFile.prepare( throttle:priority: )
    await throttle.acquire( key: id, priority: priority )   ← slot taken
    defer { throttle.release() }                            ← slot held to the end of the task
        await self.load()                                   load
        await self.image?.renderer.render()                 render
        await self.image?.detectStars()                     ← detection: the longest stage
        await self.thumbnailTask?.value                     thumbnail
        self.prepareFramePreviews()                         carousel previews (own acquisitions)

OpenFile.prepareSelectedFrame()
    await throttle?.acquire( key: id, priority: .high )     ← high-priority slot taken
    defer { throttle?.release() }
        await image.renderer.render()                       render
        await image.detectStars()                           ← detection, still inside the slot

Target shape after milestone 7: the slot covers load → render → thumbnail, and the analysis is enqueued on its own bounded queue right after the render returns — before the thumbnail wait, because makeThumbnail resizes on DispatchQueue.global( qos: .utility ), which a folder of opening files saturates.
