Decode Once, Render Many — Implementation Plan

Generated 2026-07-13
Source: Docs/agent-plans/active/2026-07-13-decode-once/decode-once.html

This plan removes the redundant per-render pixel decoding on the interactive render path and unifies it with the thumbnail decode-once special-case, without raising steady-state memory. A small cross-format DecodedRenderSource abstraction lets a source decode its pixels once and render them repeatedly; ImageRenderer.render() then decodes a frame a single time and renders both the displayed result and the original / before-image from the same samples, and the preview renderers share the very same seam.

The milestones are ordered by dependency: first the abstraction and the per-format conformers (FITS + XISF, which already expose the decode-once core; then RAW + ImageIO, which need a small public decode-free render entry added), then the render-path dedup that lands the win, then the thumbnail fold-in, and finally a verification pass. Each milestone is independently reviewable and committable, and carries its own status, completion date, implementation notes, automated-review findings, and human review comments so it can be updated in place as work proceeds.

Questions & answers

What is driving this investigation — measured memory pressure, or the redundant decoding?
Mainly the double-decode (CPU / latency). Releasing detectionImage is secondary; the focus is the render / thumbnail decode paths.
Which decoding redundancy should be eliminated?
The within-pass double decode — result + original being decoded twice in one render pass — done in a memory-neutral way. Not a persistent decoded-pixel cache (which would reintroduce held memory).
How deep should the change go?
Full: the render-path dedup and the thumbnail fold-in (the preview renderers share the seam, dropping their bespoke decode-once previewSettings twins).
Which formats are in scope?
All four — FITS, XISF, RAW, and ImageIO. RAW and ImageIO get a small new public decode-free render entry so no format is left re-decoding.

Notes

Guiding constraint

  • Steady-state memory must not increase. A DecodedRenderSource is created inside a single render() call (or one preview render) and dropped when it returns. It must never be retained across renders — that would reintroduce the held-pixel memory the current design deliberately avoids.
  • Behaviour is unchanged. Decoding is deterministic, so the shared samples are byte-identical to today's independent decodes; rendered output is identical. This is a pure dedup / refactor, and each milestone's tests should assert that equivalence.

Build & test

  • An .xcodeproj exists (FITScope.xcodeproj) — build and test through Xcode (xcodebuild, scheme FITScope, macOS), not swift build/swift test. Test plan: FITScope.xctestplan.
  • New source / test files must be wired into their targets through project.pbxproj (build file, file reference, group, Sources phase), mirroring the existing entries; validate with plutil -lint.
  • The decode-free render cores already live in the submodules (SwiftPixel / SwiftAstro); the new seams are app-side. No submodule change is expected — raise one before making it if it proves necessary.

Key files

  • Render orchestration: FITScope/Model/ImageRenderer.swift (render() at :321, makeResult(source:settings:) at :406).
  • Source protocol: FITScope/Model/ImageRenderSource.swift (makeResult(settings:), detectionImage, autoStretchColorSource default).
  • Format sources: FITScope/Model/{FITS/FITSRenderSource, XISF/XISFRenderSource, RAW/RAWRenderSource, ImageIO/ImageIORenderSource}.swift.
  • Processor entries: FITScope/Image/ImageProcessor+{FITS,XISF,RAW,ImageIO}.swift — decode-free cores (render(rawSamples:…), render(planes:…)), decode helpers (decodedImageHDU, xisfPlaneSamples, rawImageSamples, imageIOPlaneSamples), and autoStretchColorSource(fromSamples:/fromPlanes:).
  • Preview path: FITScope/Image/{FITSPreviewRenderer, XISFPreviewRenderer}.swift (the inline decode-once + previewSettings(decoded:) / (planes:) twins to fold in).

Context: what is not changing

  • detectionImage stays held for the source's lifetime. Beyond the one-shot star detection and background analysis (LoadedImage.detectStars()), it is also a live consumer of the interactive auto Screen Transfer — ImageRenderer.canAutoScreenTransfer (:229, called every render) and autoScreenTransferSettings(.uniform) (:306-310), plus the mono autoStretchColorSource default. So it cannot simply be released after detection; releasing it is explicitly out of scope here.
  • FITS RGB colour-plane frames and data cubes keep the byte path (their decoded() returns nil), matching today's preview behaviour.

Introduce the DecodedRenderSource abstraction

Goal

Add the cross-format seam and retarget the renderer's per-result helper onto it, with no behavioural change (every source still decodes per render via the default decoded() returning nil). Everything compiles and existing tests pass.

Tasks
  • Define a Sendable protocol exposing makeResult(settings:) throws -> ImageProcessor.RenderResult and autoStretchColorSource(maxDimension:) -> ImageProcessor.AutoStretchColorSource? (new file under FITScope/Model/, one type per file).
  • Give makeResult(settings:) a shared home so both a decoded frame and an ImageRenderSource satisfy it — either a common supertype protocol both refine, or have ImageRenderSource conform to the render-producing protocol. Keep ImageRenderSource's existing method signature intact for all callers.
  • Add func decoded() throws -> (any DecodedRenderSource)? to ImageRenderSource with a default implementation returning nil.
  • Retarget ImageRenderer.makeResult(source:settings:) (:406) to accept the shared render-producing type rather than any ImageRenderSource; call sites unchanged for now (still pass the source).
  • Build via xcodebuild; wire the new file(s) into the app target; confirm the existing render/preview tests still pass (no behaviour change).

FITS & XISF conformers

Goal

Provide DecodedRenderSource conformers for the two formats that already expose a decode-once core, and implement decoded() on their sources — reusing the existing decode helpers and decode-free render entries.

Tasks
  • FITS: a value type wrapping (samples, width, height, bitsPerPixel, properties) whose makeResult calls ImageProcessor.render(rawSamples:…) and whose autoStretchColorSource(maxDimension:) calls ImageProcessor.autoStretchColorSource(fromSamples:…) (subsampled). FITSRenderSource.decoded() builds it via decodedImageHDU(data:properties:), returning nil for RGB-plane / cube frames (byte fallback preserved).
  • XISF: a value type wrapping (planes, properties) whose makeResult calls ImageProcessor.render(planes:xisf:…) and whose autoStretchColorSource(maxDimension:) calls ImageProcessor.xisfAutoStretchColorSource(fromPlanes:…). XISFRenderSource.decoded() builds it via xisfPlaneSamples(data:properties:) (always non-nil).
  • Add equivalence unit tests: for representative fixtures, source.decoded()?.makeResult(settings:) produces byte-identical output (image bytes + pixel formats) to source.makeResult(settings:), and the derived autoStretchColorSource matches the data-based one.
  • Wire new files into the app + test targets; build and run tests.

Tasks

Add the conformer wrapping (plane, properties) and RAWRenderSource.decoded(). Reuse rawAutoStretchColorSource for the colour source (from the decoded mosaic).

Add the conformer wrapping (planes, properties) and ImageIORenderSource.decoded(). Provide the matching autoStretchColorSource (ImageIO has no per-channel auto source today — resolve to the appropriate mono/none, consistent with the source's current autoStretchColorSource).
  • Confirm the refactor of each byte path to route through its new decode-free entry produces identical output (delegation, not reimplementation).
  • Add the same equivalence tests as milestone 2 for RAW and ImageIO fixtures. Wire files into targets; build and test.

Render-path dedup in ImageRenderer.render()

Goal

Land the actual win: decode a frame once per render pass and render both result and original from the same samples, falling back to the source (per-render decode) when decoded() returns nil.

Tasks
  • In ImageRenderer.render() (around :352-366), inside the background work, obtain let decoded = (try? source.decoded()) ?? source once, then call the retargeted makeResult(decoded, settings) for result and makeResult(decoded, originalSettings) for original.
  • Confirm the shared decode is valid for both: samples are orientation-independent (orientation is a pipeline step) and both renders use the same maxDimension, so full-resolution samples serve both; binning happens post-decode.
  • Keep the fallback path intact for FITS RGB / cube frames (decoded() → nil → render from the source, decoding per call, exactly as today).
  • Preserve the render-generation / commit semantics unchanged (this only affects how many times bytes are decoded within one pass).
  • Add a regression test asserting the committed result and original images are unchanged versus the pre-refactor output for a first render and after an orientation change.
  • Build & run the app; verify open, adjust, and rotate/flip all render correctly.

Goal

Refactor the preview renderers onto the shared DecodedRenderSource so the decode-once logic lives in one place, dropping the bespoke previewSettings(decoded:) / previewSettings(planes:) twins.

  • Keep the existing preview unit tests green (they exercise the priority logic); add coverage if a twin removal leaves a gap.
  • Build & verify a thumbnail renders identically (QuickLook / the thumbnail extension) for FITS and XISF fixtures.

Appendix

Milestone dependency order

  • 1 → 2, 3: the abstraction must exist before any conformer.
  • 2 & 3 → 4: the render-path dedup benefits every format that implements decoded(); wiring it after both conformer milestones lets it land complete (a format without decoded() would simply fall back, so ordering is for cleanliness, not correctness).
  • 2 → 5: the thumbnail fold-in reuses the FITS/XISF conformers from milestone 2; it does not depend on RAW/ImageIO (the preview path is FITS + XISF only).
  • 6: verification after all code changes.

Equivalence-test shape (shared by milestones 2 & 3)

For each format fixture and a few representative settings (linear default, an auto-stretch, an orientation): assert source.decoded()?.makeResult(settings:) equals source.makeResult(settings:) on image bytes, inputPixelFormat, and outputPixelFormat; and that the decoded-frame autoStretchColorSource matches the source's data-derived one. This nails down the "byte-identical, pure dedup" guarantee at the unit level.
