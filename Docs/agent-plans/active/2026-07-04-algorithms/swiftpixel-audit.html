Overview

This report audits every SwiftPixel processor and core primitive for numerical correctness, edge-case handling, and test coverage. The headline is reassuring: the mathematically heavy routines are correct. The 2D convolution pad/convolve/crop pipeline, the Gaussian kernel, the Levenberg–Marquardt Gaussian fit (all seven analytic Jacobian partials hand-verified), the tone/levels/stretch vector paths, the four standard Bayer demosaics (bilinear and VNG), and the colour, geometry and cosmetic-correction stages all produce correct output and are, for the most part, well tested.

The defects that exist cluster into a small number of themes: one true output-corruption bug (non-finite input to Normalize), a recurring NaN-handling gap across several statistics routines, a systemic guard-order mistake that hides the accurate error and leaves a guard effectively dead, a non-standard Bayer pattern that demosaics incorrectly, a Screen-Transfer constant that deviates from the algorithm it cites, and a set of unenforced public-API preconditions (one a hard crash). The remainder are test-coverage gaps and cosmetic notes.

Method & verification

The 33 files were audited by eight independent, fresh-context reviewers, one per coherent file-group, each with a findings-only mandate and instructed to verify formulas and Accelerate/vDSP semantics against authoritative sources (Apple SDK headers & docs, and algorithm references) rather than from memory, to consult git history for rationale, and to cross-check every finding against the existing tests.

Every finding below was then reviewed by the lead, and the load-bearing items were independently re-verified against the source. In particular: the Normalize NaN/Inf corruption (BUG-1) was reproduced with a throwaway Accelerate program; the .rgbg tile geometry, the STF raw-MAD usage, the GaussianKernel non-finite-σ trap, the guard-order pattern, the mis-wired MonoToRGB test, and the small-total histogram statistics were each confirmed by reading the cited code; the vDSP_mmovD, vDSP_vdiv operand-swap, and vvpow semantics were confirmed against the Xcode SDK headers by the auditors. Confidence levels are carried on each finding.

Cross-cutting themes

  • Non-finite (NaN/Inf) samples are not sanitized. FITS float32/float64 frames legitimately carry NaN blank pixels, and readRawPixels decodes them at face value. Several routines then misbehave: Normalize corrupts the whole buffer (BUG-1), PixelUtilities.median/percentileBounds have undefined sort order (CR-8), and CosmeticCorrection can leave a real hot pixel next to a NaN uncorrected (CR-9). A single decode-time or stage-level sanitization policy would close all three.
  • Guard order hides the accurate error. MonoToRGB (CR-4) and Debayer (CR-5) both run a sample-count guard computed for channels: 1 before the channels == 1 guard, so a multi-channel buffer reports dataSizeMismatch and the accurate unsupportedChannelCount is effectively unreachable. The same shape of mistake, in two files.
  • Public-API preconditions are unenforced. Unlike PixelBuffer.init/checkedSampleCount (which throw), several public entry points trust their inputs: Convolution.convolve (CR-11), zeroSumResponse (CR-12), Curves.value(at:) (CR-13), and GaussianKernel(sigma:) (CR-3, a hard crash). The main pipeline always feeds them valid data, so these are external-surface risks.
  • Negative-path tests that pass for the wrong reason. invalidNormalize exercises the wrong processor entirely (CR-6), and several invalidChannels tests assert only throws PixelBufferError.self, so they pass on the guard-order error path (CR-4/CR-5) rather than the guard they name. Broadly, many value tests assert only range/finiteness, not the defining formula.

Bug

BUG-1 Normalize corrupts NaN/Inf input and flags it normalized Bug

Processors/Normalize.swift:110–186 (.minMax; the same root reaches .percentile and .identity) · Confidence: high (lead-reproduced empirically)

What & why

Normalize runs on raw (non-normalized) buffers, so NaN/Inf FITS blanks reach it. The constant-image guard guard minValue != maxValue (:118) does not catch NaN because NaN != NaN is true, so a NaN sample falls through to the divide path: vDSP_minvD/maxvD return NaN → range/scale/offset are NaN → the entire buffer becomes NaN and is marked isNormalized = true. Reproduced: [NaN,10,20,30] → all-NaN; [+Inf,10,20,30] → [NaN,0,0,0]. Downstream, convertTo8Bits maps NaN → 0 silently, so one blank pixel can blacken or NaN-poison the whole frame.

Recommendation

Sanitize non-finite samples (treat as missing when computing min/max/percentile; replace with 0 or the low bound), or reject non-finite input explicitly. Note the min != max guard cannot double as a NaN guard.

Test status

Missing — no NaN/Inf test in Processors-Normalize.swift; random tests use finite 0…5000 values only. (If non-finite input is deemed out-of-contract, this is a documented correctness-risk rather than a bug — but there is currently neither a guard nor a doc note, and the trigger is realistic for this library's domain.)

Correctness-risk

CR-1 .rgbg is not a valid Bayer CFA and demosaics to wrong colours Correctness-risk

Processors/Debayer.swift:46, 242–250 (and both interpolators) · Confidence: high (lead-verified)

What & why

.rgbg is implemented as the tile R,G / B,G, which tiles to greens on every odd column of every row (vertical stripes), not the diagonal quincunx that the four valid patterns (rggb, bggr, grbg, gbrg) and every demosaic algorithm assume. Both bilinear and vng therefore fabricate the missing colours from wrong-colour neighbours (e.g. blue at a green site averaged from greens). deinterleave (partition-only, no interpolation) is unaffected. This is the non-standard “RGBG” entry advertised in the README.

Recommendation

Remove .rgbg from the public Pattern enum, or, if a striped RGBG sensor must be supported, document it as non-Bayer and give it its own path. Do not present it as a peer of the four valid CFAs.

Test status

Not caught — the RGBG tests assert only the present colour / positivity; there is no VNG RGBG test.

CR-2 STF shadow clip uses raw MAD, not the normalized MAD its cited constant assumes Correctness-risk

Processors/STFParameters.swift:228 · Confidence: high (lead-verified)

What & why

shadows = median − shadowClipFactor · mad uses the raw MAD from PixelUtilities.medianAbsoluteDeviation (no 1.4826 factor). The type documents “the PixInsight / XISF display function model” with a default shadowClipFactor = 2.8 — but PixInsight's −2.8 multiplies the normalized MAD (MADN = 1.4826 · MAD), so the shadow clip lands ≈1.48× too shallow versus the referenced algorithm. Tellingly, CosmeticCorrection.swift:162 already defines and applies robustScaleFactor = 1.4826 — the STF path is the outlier. The stretch still lands the median on the target background (that depends only on m0 and the MTF), so results look plausible — only the black-point depth deviates.

Recommendation

If PixInsight parity is intended, normalize the MAD (median − shadowClipFactor · (1.4826 · mad), reusing the existing constant). Otherwise correct the docstring to state the raw-MAD convention and that 2.8 is not PixInsight's −2.8 semantics.

Test status

Wrong-expectation — computedFromStatsClipsShadowsBelowTheMedian asserts shadows == median − 2.8·mad (raw), codifying the deviation; the median→target tests hold regardless of clip depth and cannot catch it.

CR-3 GaussianKernel(sigma:) hard-crashes on NaN/Inf σ Correctness-risk

GaussianKernel.swift:71–72 · Confidence: high (lead-verified; auditor-reproduced)

What & why

Swift.max(sigma, 1e-6) does not sanitize a non-finite first argument — Swift.max(.nan, 1e-6) == .nan (all NaN comparisons are false, so max returns its first arg). Then Int((safeSigma * radiusInSigmas).rounded(.up)) traps: “Double value cannot be converted to Int because it is either infinite or NaN.” The clamp defends only against small/negative σ. A public initializer that hard-crashes on a Double input is out of step with the library's throw-not-trap style.

Recommendation

let safeSigma = sigma.isFinite ? Swift.max(sigma, 1e-6) : 1e-6, or fail via a thrown error.

Test status

Missing — no NaN/Inf test; the negative/zero-σ clamp path is also untested.

CR-4 & CR-5 Guard order makes the channel guard dead and reports a misleading error (MonoToRGB, Debayer) Correctness-risk

Processors/MonoToRGB.swift:55–67, Processors/Debayer.swift:126–138 · Confidence: high (lead-verified)

What & why

Both compute checkedSampleCount(…, channels: 1) and throw dataSizeMismatch before the channels == 1 guard. Because PixelBuffer enforces pixels.count == width·height·channels, the count guard passes only when channels == 1 or the image is empty — so for any non-empty multi-channel buffer the caller gets dataSizeMismatch, and the accurate unsupportedChannelCount is reachable only for a zero-area buffer. Functionally the input is still rejected; the reported reason is wrong and the documented channel error is effectively dead.

Recommendation

Check channels == 1 first, then the sample-count/geometry guard.

Test status

Wrong-expectation — both invalidChannels tests pass but exercise the dataSizeMismatch path, not the channel guard they are named for (they assert only throws PixelBufferError.self).

CR-6 MonoToRGB's invalidNormalize test exercises Debayer, not MonoToRGB Correctness-risk

SwiftPixelTests/Processors-MonoToRGB.swift:102 · Confidence: high (lead-verified)

What & why

The test is named invalidNormalize and builds a normalized mono buffer, then instantiates and runs Processors.Debayer(mode:.bilinear, pattern:.bggr) instead of Processors.MonoToRGB(). It validates Debayer; MonoToRGB's mustNotBeNormalized guard has no coverage (a copy-paste defect).

Recommendation

Replace the Debayer call with Processors.MonoToRGB() and assert the specific error case.

Test status

Missing/wrong-expectation — as written.

CR-7 Histogram percentiles/median collapse to bin 0 for small sample totals Correctness-risk

HistogramStatistics.swift:170, 180, 113 · Confidence: high (lead-verified)

What & why

t1 = Int(Double(total) * 0.01) truncates to 0 for every total < 100; the scan then matches at the first bin because cumulative >= 0 is always true, so percentile1 is reported as bin 0 regardless of where the data lie. For total == 1, percentile99 and the total / 2 median crossing collapse to 0 too, while min == max are computed correctly — an internally inconsistent result. Correct for total ≥ 100, which is why the real (million-sample) image histogram never triggers it — but init(data:) and percentiles(…) are public.

Recommendation

Clamp the thresholds to ≥ 1 (or use ceil and require cumulative > 0); apply the same to the total / 2 median crossing for total == 1.

Test status

Missing — singlePeak/linearSpread use total == 100 (the exact boundary that hides it); nothing exercises total < 100.

CR-8 Sort-based median/percentiles are undefined for NaN, and the two median overloads can diverge Correctness-risk

PixelUtilities.swift:269, 306, 327 · Confidence: medium

What & why

median(_: [Double]) sorts via vDSP.sort while the generic median<T>(_:) uses Array.sorted(). For finite input the two paths are provably identical (verified for all counts), so the documented equivalence holds. But neither vDSP.sort nor sorted() defines NaN ordering, so with NaN input the percentile/median value is undefined and the two overloads can disagree. FITS float frames can contain NaN.

Recommendation

Document that inputs must be NaN-free, or drop/guard NaN before sorting in median/percentileBounds. Part of the NaN theme (see BUG-1, CR-9).

Test status

Missing — no NaN test for either overload.

CR-9 CosmeticCorrection mishandles NaN neighbours Correctness-risk

Processors/CosmeticCorrection.swift:425–443, 402–410 · Confidence: medium

What & why

The insertion sort orders via buffer[j] > key; a NaN compares false against everything, acting as a “wall” that leaves the neighbour buffer partially unsorted, so the neighbour median/min/max become unreliable when any neighbour is NaN. Consequences are bounded — no crash, and a flagged replacement can't emit NaN — but a genuine hot/cold pixel adjacent to a NaN may be silently left uncorrected, and a NaN sample passes through unrepaired. ±Inf is handled acceptably.

Recommendation

Treat non-finite neighbours as absent during the gather, or document that the stage assumes finite samples.

Test status

Missing — no NaN/Inf test.

CR-10 STF computed collapses to a hard threshold when median ≤ shadows Correctness-risk

Processors/STFParameters.swift:237–238 · Confidence: medium

What & why

If the normalized median is 0 with mad > 0 (a frame whose background dominates ≥50% of pixels), then shadows = 0, m0 = 0, midtones = mtf(0.25, 0) = 0. A channel with midtones = 0 validates but takes the scalar fallback where mtf(0, x) is a binary step (x>0 → 1) rather than a smooth stretch. This is an inherent limit of the MTF auto-stretch (PixInsight degenerates similarly), but it is silent here.

Recommendation

Optionally clamp m0 away from the exact endpoints, or document the degenerate-midtones behaviour. Low priority unless median-0 frames are expected.

Test status

Missing.

CR-11 Public Convolution.convolve validates no preconditions Correctness-risk

Convolution.swift:69, 83–93 · Confidence: high

What & why

convolve(_:width:height:kernel:radius:) is public but never checks values.count == width·height, kernel.count == (2·radius+1)², or radius ≥ 0. A short values traps out-of-bounds; a short kernel makes vDSP.convolve over-read. Inconsistent with the library's defensive style. The sole in-repo caller (zeroSumResponse) always passes consistent arguments, so this is an external-surface risk.

Recommendation

Guard the three preconditions (return [] / throw), or document them as hard preconditions.

Test status

Missing — no direct test of the public convolve.

CR-12 zeroSumResponse ignores image.channels → silent garbage on multi-channel input Correctness-risk

Convolution.swift:49–52 · Confidence: high

What & why

It forwards pixels/width/height but not channels, and convolve treats the data as single-channel. For a multi-channel buffer it reads the first width·height interleaved samples — a geometrically incoherent channel mix — and returns in-bounds garbage. The doc says “single-channel” but nothing enforces it.

Recommendation

Guard image.channels == 1 (throw/precondition), or document loudly.

Test status

Missing.

CR-13 Public Curves.value(at:) trusts its precondition → Inf/NaN on a malformed curve Correctness-risk

Processors/Curves.swift:157, 232 · Confidence: medium

What & why

Curve.init is public and does not sort/dedup/validate; validate() is only called inside process(buffer:). value(at:) (also public) calls tangents(), which divides by Δx. A consumer that builds a curve with duplicate or non-increasing x and calls value(at:) directly gets a ±Inf/NaN secant that can propagate (the final min/max clamp does not reliably sanitize NaN). The main pipeline is safe because process validates first.

Recommendation

Guard Δx ≤ 0 in value(at:)/lookupTable(), or have them validate / document the precondition prominently.

Test status

Missing — nonIncreasingXThrows only covers the process path.

CR-14 4-channel createCGImage assumes premultiplied alpha, unenforced and untested Correctness-risk

PixelBuffer.swift:240–243 · Confidence: medium

What & why

For 4 channels the bitmap info is premultipliedLast, so CoreGraphics reads the RGB samples as already multiplied by alpha. A consumer supplying straight RGBA gets wrong colours wherever alpha < 1. Documented, and the pipeline only ever emits 3-channel RGB, so it is reachable only via direct 4-channel construction — but nothing enforces or converts it.

Recommendation

Keep if the premultiplied contract is intended; add a test exercising alpha < 1 to pin the semantics, and optionally note the straight-alpha alternative (noneSkipLast).

Test status

Missing — createCGImageWith4Channels uses alpha 1.0, where premultiplied ≡ straight.

CR-15 GaussianFit singularity threshold is absolute, not scaled Correctness-risk

GaussianFit.swift:391 · Confidence: low

What & why

The pivot floor abs(matrix[c][pivot]) > 1e-12 is absolute, but JᵀJ entries scale with amplitude²·N and can be very large, so an ill-conditioned system may be treated as solvable, yielding a poor step. In practice masked by Marquardt diagonal damping and the strict candidateCost < currentCost acceptance gate, so an actually-accepted wrong step is unlikely.

Recommendation

Consider a relative threshold (scaled by the max diagonal), or rely on the damped system explicitly. Low priority given the mitigations.

Test status

Missing — no singular/degenerate-geometry input test.

CR-16 The new rotated/elliptical Gaussian-fit Jacobian is effectively untested Correctness-risk

SwiftPixelTests/GaussianFit.swift:55–69, 104–109 · Confidence: high on the gap (math verified correct)

What & why

The analytic Jacobian was newly hand-derived (commit 131d928) and is correct (all seven partials hand-verified), but no test recovers parameters from a rotated (θ≠0) or truly elliptical (σx≠σy) truth: the only recovery test uses a round Gaussian (θ=0, σx=σy), so the θ column sees no signal, and modelPeaksAtTheCenter evaluates at the centre where exp(0)=1 regardless of θ/σ. The paths most likely to harbour a hand-derivation error have no regression guard.

Recommendation

Add a recovery test with θ≈0.5–0.7 and σx≠σy, asserting θ (modulo the π degeneracy) and both widths; and a fixed-seed noisy-recovery test (the doc sells noise robustness, but every test is noiseless).

Test status

Missing (rotation/ellipticity recovery, and noisy data).

CR-17 By-design correctness-risks worth a conscious decision Correctness-risk

various · Confidence: high (behaviour), design judgment

What & why
  • Debayer edge-replicate contamination (Debayer+Bilinear.swift:88–144, Debayer+VNG.swift:319–356): border pixels average in edge-clamped wrong-colour samples, mixing e.g. red into the green plane on the 1-pixel border (dominates tiny images). Locked by golden tests; inherent to edge-clamp demosaicing.
  • Invert/BrightnessContrast/CorrectGamma transform the alpha channel (Invert.swift:73 et al.): 1−x etc. run over the whole interleaved buffer, inverting alpha on a 4-channel buffer. Documented as “uniform to every channel”; RGBA rarely reaches these stages.
  • Bin hardcodes a 2×2 CFA cell (Bin.swift:30–48, 213–234): single-channel input is always averaged as a Bayer mosaic (same-parity sites two apart), not a plain 2×2 box; misuse on a plain luminance image aliases silently. Documented, wired pre-demosaic.
  • HistogramStatistics.median is the lower-median bin (:109–118): first bin reaching total/2, biased low vs an interpolated median. Documented and Int-typed.
Recommendation

No code change required; each is documented. Flagged so the trade-offs are conscious, and (for the Debayer border) as an option if border fidelity ever matters.

Improvement

Correct today, but a better algorithm, a tighter contract, or (mostly) a missing test would strengthen them.

  • IMP-1 — VNG gradients mix unlike-coloured samples (Debayer+VNG.swift:287–299): the 1-step gradient term compares the centre against a different-coloured mosaic sample, so gradients are not the like-coloured differences true Chang/Cok VNG uses, weakening edge selectivity in high-chroma content. The threshold constants k1=1.5, k2=0.5 are correct; the “VNG” label overstates fidelity. Either compute like-coloured gradients or soften the doc to “gradient-directed (VNG-style)”.
  • IMP-2 — Normalize is global across channels (Normalize.swift:115–116, 144): min/max & percentile span all channels (preserving colour ratios), a legitimate default but undocumented and untested on multi-channel buffers.
  • IMP-3 — Levels does not validate outputBlack > outputWhite (Levels.swift:123): an inverted output range is silently accepted despite the “darkest/brightest” docs (contrast with the enforced inputWhite > inputBlack).
  • IMP-4 — No-op correctGamma: 1.0 still forces auto-normalization (PixelPipeline.swift:477 vs the no-op filters at :404–475): unlike brightnessContrast/levels/curves/… (rebound to nil when neutral), a no-op gamma inserts a Normalize(.minMax) and flips a raw result to a min-max-normalized one. Filter correctGamma == 1.0, or document the asymmetry (stretch, whiteBalance, invert are likewise unfiltered but harder to detect).
  • IMP-5 — binFactor silently ignored for .rgb input (PixelPipeline.swift:369): an invalid binFactor (0/negative) throws for mono/CFA but is dropped for .rgb — inconsistent validation. Consider validating binFactor ≥ 1 in Config.init.
  • IMP-6 — Bin/Resample pipeline wiring is untested (PixelPipeline.swift:369–372, 397–400): no pipeline test sets binFactor or maxDimension; the insertion, the channels == 1 Bin guard, and the Resample-after-channel-forming ordering are unverified (the processors are tested only in isolation).
  • IMP-7 — BitsPerPixel.size traps on overflow (BitsPerPixel.swift:89–99): numberOfPixels * 8 traps on Int overflow, unlike the throwing geometry path (checkedSampleCount). Theoretical (∼10¹⁸ samples) but contradicts the throw-not-trap philosophy.
  • IMP-8 — Convolution depends on undocumented vDSP border width (Convolution.swift:93–105): correctness hinges on vDSP.convolve zeroing exactly a radius-wide ring; add a pinning comment and an output-edge regression test.
  • IMP-9 — MonoToRGB requires non-normalized input for a structural op (MonoToRGB.swift:69–73): channel replication is range-independent; the guard likely enforces pipeline ordering — keep if intentional, else relax.
  • IMP-10 — Scale clears the normalized flag for range-preserving transforms (Scale.swift:69–70): a conservative, always-safe false-negative; documented. No action needed.
  • IMP-11 — Test-coverage gaps across otherwise-correct code: PixelBuffer Equatable (dimensions/flag) & the throwing-body flag-preservation contract; all four error enums' errorDescription strings; ColorBalance non-pivot smoothstep, WhiteBalance gray-world gains & guards, Hue arbitrary-angle round-trip, Saturation; bilinear interior (only 2×2 goldens = all border) and per-pixel non-RGGB colour; Bin odd/non-divisible dims & factor ≥ 3; Resample non-square/partial-cell; Orient composition from a mirrored+rotated state; GaussianKernel absolute-weight & clamp path.
  • IMP-12 — Histogram allocates unused bin arrays (Histogram.swift:76–80): all five accumulators are allocated regardless of mode (per-iteration compute is already mode-specific); ∼5 KB, negligible.

Cosmetic

  • COS-1 — vDSP_mmovD comment transposes M and N (PixelUtilities.swift:234–238): the code is correct (verified against Apple's SDK header), but the comment labels N=1 as “column” and M=count as “row”, backwards versus both the header's parameter names and the same line's argument order. Reword to “M=1 column, N=count rows”.
  • COS-2 — mtf's m == 0.5 branch is redundant (PixelUtilities.swift:405–408): the general formula already returns exactly x there (exact power-of-two arithmetic); the branch is a harmless explicit identity. The no-divide-by-zero claim was verified.
  • COS-3 — “luminance” vs “luma” naming (Saturation.swift, ColorBalance.swift): the Rec. 709 coefficients are applied to gamma-encoded samples, which BT.709 terms luma (Y′), not luminance (Y). Coefficients are correct; naming only.
  • COS-4 — zero-sample readRawPixels throws instead of returning [] (PixelUtilities.swift:126–130): empty Data yields a nil baseAddress → bufferAccessFailed. Likely unreachable if callers reject zero-area geometry; optional guard count > 0 else { return [] }.
  • COS-5 — Bin.outputSize returns (0,0) for a factor process rejects (Bin.swift:108–120): a consumer pre-sizing gets (0,0) then a throw; process's throw is the safety net.
  • COS-6 — Debayer+Deinterleave doc says dimensions “must be positive” but 0 is accepted and returns empty sets; no behavioural impact.
  • COS-7 — GaussianFit tests are model-self-consistent: samples are generated and fit by the same model, so an off-centre/rotated value is never checked against an external ground truth (only the centre value is). Add one hand-computed off-centre assertion.
  • COS-8 — GaussianFit docstrings describe a stale “finite-difference Jacobian” (GaussianFit.swift:36–40, 229–230): the type doc says the fit “uses a numerical (finite-difference) Jacobian rather than analytic derivatives … hand-coded derivatives error-prone,” and modelResiduals refers to “every finite-difference Jacobian column” — but since commit 131d928 the fit uses the (verified-correct) analytic Jacobian at :341–349, with modelResiduals now used only for cost evaluation. Update both docstrings to say “analytic Jacobian.” (Notable: the stale text warns against the very hand-coded derivatives the code now correctly uses.)
