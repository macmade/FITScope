Overview

This report audits every SwiftAstro algorithm — the matched-filter star detector, the signal-to-noise / sky-background estimators, the FITS preprocessing, and the positional-astronomy ephemeris — for correctness, on the same basis as the SwiftPixel audit (M2). SwiftAstro builds on SwiftPixel; where an issue actually lives in SwiftPixel it is noted as an overlap rather than re-filed.

The headline is again reassuring: the heavy math is correct. The ephemeris is a faithful, numerically-verified implementation of Paul Schlyter's low-precision model (every Sun/Moon/planet element, the lunar perturbation series, the Kepler solver, sidereal time, the equatorial↔horizontal transform, twilight, and moon phase reproduce Schlyter's worked example). The star-detection statistic (zero-sum Gaussian matched filter, robust MAD·1.4826 noise on the response, strict-neighbour peak finding, moment centroids, and the Gaussian-fit seed), and the SNR “SNRWeight” formula, all check out against references.

The defects that exist cluster into recurring themes: one functional bug (a valid Bayer pattern rejected while a broken one is accepted), a non-finite (NaN/Inf) handling gap that mirrors SwiftPixel's, a set of single-number metric conventions that don't match their names or disagree across measurement paths, and several test-coverage holes that leave correct code unguarded.

Method & verification

The 23 files were audited by five independent, fresh-context reviewers, one per domain (matched-filter detector; star moments/fit/types; SNR + preprocessing + core; ephemeris position models; ephemeris facade / coordinates / events), each with a findings-only mandate and instructed to verify formulas against authoritative sources rather than memory. The ephemeris reviewers correctly identified the reference as Paul Schlyter's “Computing planetary positions” (not Meeus) and verified against it, one of them re-deriving Schlyter's worked example in a standalone Swift program.

Every finding was then reviewed by the lead and the load-bearing items re-verified against the source. Notably, one reported latent crash was refuted on verification: a claimed +Inf → Int(NaN) trap in the bright-star pass (+BrightStars.swift:121) is not reachable — the edge-margin guard at :105 (base.x >= margin …) is false for a non-finite centroid, so the candidate returns nil before the Int() conversion. It is excluded from the findings below. The FITS GBRG bug, the FWHM RMS-vs-geomean split, the roundness gate/report mismatch, the saturationLevel override, and the NAXIS-cube truncation were each confirmed by reading the cited code. Confidence levels are carried on each finding.

Cross-cutting themes

  • Non-finite (NaN/Inf) samples are inconsistently handled (the same theme as SwiftPixel M2). Float FITS frames carry NaN blanks, and the decoder passes them through. The detector guards finiteness on some derived metrics (.isFinite at MatchedFilterStarDetector.swift:332, 401, 502 and +BrightStars:171), so a blank generally causes graceful under-detection rather than a crash — but nothing sanitizes the input, and SignalToNoise/SkyBackground emit NaN statistics or silently discard a good frame (CR-2). One decode-time policy (mask or reject blanks) would close it across the board.
  • The Bayer .rgbg / GBRG tangle ties back to SwiftPixel M2 (CR-1). The FITS decoder omits the valid, common GBRG pattern and instead maps the non-standard RGBG — which routes into SwiftPixel's incorrect .rgbg demosaic. Fixing it well spans both submodules: add GBRG here (BUG-1) and resolve .rgbg in SwiftPixel.
  • Single-number metric conventions don't match their names or each other. hfr is the half-light (encircled-50%) radius, not the acquisition-software HFR its name implies (CR-3); the one-number fwhm is the RMS of the two axis widths on the moment path but the geometric mean on the fit path, mixed within one StarField (CR-4); and the bright-star roundness cut gates one eccentricity but reports another (CR-5). A consumer comparing SwiftAstro metrics to other tools, or across stars, gets subtle mismatches.
  • The ephemeris is a faithful low-precision Schlyter implementation. Its findings are test-coverage gaps and one horizon-convention consistency note (CR-7) — not math errors. The stated “fraction of a degree” outer-planet accuracy and the mean-phase moon model are honestly documented.
  • SwiftPixel overlaps (noted, not re-filed): the PixelUtilities.median/percentileBounds NaN sort order, PixelBuffer.init performing no finiteness validation, and the .rgbg pattern itself — all already captured in the M2 SwiftPixel report.

Bug

BUG-1 FITS decoder rejects the valid GBRG Bayer pattern and maps the non-standard RGBG Bug

Preprocessing/FITSImageDecoder.swift:132–139 · Confidence: high (lead-verified)

What & why

The BAYERPAT switch handles BGGR, RGBG, GRBG, RGGB and throws on everything else — so a frame carrying the common, valid BAYERPAT = 'GBRG' (many Sony/ZWO one-shot-colour sensors, partly because FITS stores rows bottom-up) is rejected outright with “Unsupported BAYERPAT value GBRG,” even though SwiftPixel supports .gbrg as a first-class, tested pattern and the whole demosaic path downstream handles it. In its place the switch maps RGBG, which is not a pattern capture software emits and which resolves to SwiftPixel's non-checkerboard .rgbg (the broken demosaic flagged in M2 CR-1). This reads as a GBRG→RGBG transposition. The committed fixtures are GRBG (Seestar) and RGGB (ZWO), so the gap was never exercised.

Recommendation

Add case "GBRG": return .gbrg. Drop or re-route RGBG in step with the SwiftPixel M2 CR-1 resolution (it should not silently select a broken demosaic).

Test status

Missing — the decoder Bayer test asserts only .rggb and nil (mono); no GBRG/BGGR/RGBG or error-path case exists.

Correctness-risk

CR-1 NAXIS ≥ 3 data cubes are silently truncated to their first plane Correctness-risk

Preprocessing/FITSImageDecoder.swift:63–90 · Confidence: high (lead-verified)

What & why

The decoder validates only that NAXIS1 > 0 and NAXIS2 > 0; it never reads the NAXIS count nor rejects NAXIS3 > 1. For a 3-plane RGB FITS or any data cube, expectedBytes is computed for a single plane, prefix(expectedBytes) grabs exactly plane 1's bytes, the size check passes, and the decoder returns only the first plane as a single-channel image — silent data loss, no error. The doc claims a “2D image HDU” but nothing enforces NAXIS == 2.

Recommendation

Read hdu.header.naxis and reject (or explicitly handle) NAXIS != 2; at minimum throw for NAXIS ≥ 3.

Test status

Missing — no cube fixture or NAXIS assertion.

CR-2 Non-finite (NaN/Inf) samples are not sanitized — SNR/background emit NaN, detection silently under-counts Correctness-risk

SignalToNoise.swift:84–88, SkyBackground.swift:120–132; detector median/MAD/convolution paths · Confidence: high (lead-verified)

What & why

Float FITS frames legitimately carry NaN blanks, decoded at face value. SkyBackground.estimate uses pixels.min()/.max() and PixelUtilities.median, all unreliable with NaN, and returns a struct whose absolute level/noise/minimum/maximum are then NaN. SignalToNoise.estimate gets noise = NaN, and guard noise > 0 (NaN > 0 == false) makes it return nil — a good frame with one blank pixel is discarded. In the detector, non-finite input mostly causes graceful under-detection (finiteness guards on derived metrics turn a poisoned measurement into a dropped candidate), but nothing sanitizes the input, so counts silently fall. This is internally inconsistent — the detector guards .isFinite in several spots while the statistics helpers do not. (A reported +Inf crash in the bright pass was refuted — see Method.)

Recommendation

Adopt one non-finite policy: mask/replace blanks at decode (or reject non-finite input with a thrown error), and filter to finite samples before median/MAD/min/max in SignalToNoise/SkyBackground.

Test status

Missing — all fixtures are 16-bit integer (always finite); no NaN/Inf path is exercised.

CR-3 hfr is the half-light (encircled-50%) radius, not the acquisition-software HFR its name implies Correctness-risk

StarDetection/StarMoments.swift:162–190 · Confidence: high (lead-verified)

What & why

halfFluxRadius accumulates flux in order of increasing radius and returns the radius enclosing 50% of the flux — the half-light / effective radius (SExtractor FLUX_RADIUS at 0.5), = σ√(2 ln2) ≈ 1.177σ for a Gaussian. That is not what acquisition software (NINA/SGP/Ekos) reports as “HFR”, which is HFD/2, a flux-weighted mean radius = σ√(π/2) ≈ 1.253σ — a +6.4% definitional offset for an ideal Gaussian, more on real stars. The code is internally consistent (its FWHM = 2·HFR relation holds under this definition), so the choice looks deliberate — but the name and the RealFrameValidationTests rationale (which attributes the difference to the Gaussian fit) are misleading; the offset is definitional and would persist with identical centres and no fit.

Recommendation

Decide the intended convention: keep the half-light radius but rename/clarify it and correct the test rationale, or switch to the flux-weighted mean radius Σ(w·r)/Σw for interop with acquisition-software HFR.

Test status

Loose — measuresARoundGaussian (10% tol) and RealFrameValidationTests (20% tol) both absorb the ~6% offset and cannot discriminate the two definitions.

CR-4 One-number fwhm is the RMS of σx,σy on the moment path but the geometric mean on the fit path — mixed within one StarField Correctness-risk

StarMoments.swift:113 (RMS) vs MatchedFilterStarDetector.swift:394, 684 (geomean) · Confidence: high (lead-verified)

What & why

StarMoments.fwhm = fwhmPerSigma·√((Mxx+Myy)/2) — the quadratic mean (RMS) of the two widths. When the Gaussian fit succeeds, the detector instead reports fwhmPerSigma·√(σ_major·σ_minor) — the geometric mean (verified at :394 and :684). For a round star these coincide; for σ=(2,4) they differ by +11.8%. The detector mixes bases in one result set: fit-measured stars carry the geometric-mean FWHM, while moment-fallback stars and all bright-pass stars (+BrightStars reports refined.fwhm) carry the RMS FWHM. StarField.medianFWHM/fwhmRange then aggregate across the two bases, and the size-band purity cut is applied on different bases per star — bright/saturated/trailed stars, the most elongated, are exactly the ones on the RMS basis. (Eccentricity, by contrast, is consistent: both paths use √(1 − σ_minor²/σ_major²).)

Recommendation

Pick one single-value FWHM convention (geometric mean is the standard “equivalent circular”/seeing FWHM) and use it in both paths.

Test status

Missing — only round-star tests exist, where RMS and geomean coincide.

CR-5 Bright-star roundness cut gates on base.eccentricity but the star reports refined.eccentricity Correctness-risk

StarDetection/MatchedFilterStarDetector+BrightStars.swift:107 (gate) vs :177 (reported) · Confidence: high (lead-verified)

What & why

The purity gate is applied to the eccentricity of the detection footprint (base, global background), but the emitted Star carries the eccentricity of the refined core aperture (refined, local background) — measured on different sample sets. So a bright star can pass the gate on base yet be emitted with refined.eccentricity > roundnessLimit, violating the stated purity contract. Round stars (the common case) have both ≈ 0, so only borderline-elongated bright blobs are affected.

Recommendation

Apply the roundness cut to refined.eccentricity after refinement (or gate on whichever value is reported).

Test status

Missing.

CR-6 saturationLevel is silently defeated by the default-on bright-star pass Correctness-risk

MatchedFilterStarDetector.swift:137–138, 633–636 vs +BrightStars.swift (no saturation gate) · Confidence: high (lead-verified)

What & why

saturationLevel is documented as dropping candidates whose peak sample is at/above the level (bloomed). The matched-filter path honours it (:633), but the bright-star pass — whose explicit purpose is to recover a bright star's saturated, flat-topped core — has no saturation gate and is on by default. So with saturationLevel set and default detectsBrightStars: true, saturated stars are dropped by one path and re-added by the other. Nothing documents that a user must also set detectsBrightStars: false for saturationLevel to take effect.

Recommendation

Honour saturationLevel in the bright pass, or document that it applies only to the matched-filter pass and is overridden by the bright pass.

Test status

Missing — saturationLevel is never set to a non-default value (see IMP-6).

CR-7 Two horizon conventions coexist — isAboveHorizon at 0° vs sunrise at −0.833° Correctness-risk

Ephemeris/HorizontalCoordinate.swift:39–42 vs Ephemeris/TwilightEvents.swift:67 · Confidence: medium (both individually correct)

What & why

isAboveHorizon is altitude > 0 (geometric), while TwilightEvents uses sunriseAltitude = −0.833° (refraction + semidiameter). A caller comparing SolarPosition.horizontal(…).isAboveHorizon against sunrise/sunset finds the Sun reports isAboveHorizon == false for the minutes its centre sits between −0.833° and 0° — i.e. after the reported sunrise. Both thresholds are defensible and documented, but the library never reconciles them (internally, twilight uses −0.833° directly and never routes through isAboveHorizon).

Recommendation

Call out the distinction in both docs, and/or offer a refraction-aware isAboveHorizon(refraction:) so “Sun is up” agrees with the sunrise time.

Test status

The −0.833°…0° band is not probed by any test.

CR-8 Bilinear demosaic smooths the frame, biasing the CFA absolute-noise estimate low Correctness-risk

Preprocessing/BayerGrayscaleConverter.swift:84–91 (feeding SkyBackground/SignalToNoise) · Confidence: medium

What & why

The converter removes the CFA checkerboard (which would inflate the noise estimate) via bilinear demosaicing — but bilinear reconstruction is a low-pass filter: R/B at each site average 4 neighbours (G, 2), so (R+G+B)/3 has materially suppressed per-pixel noise. Absolute ADU noise from SkyBackground/SignalToNoise on a demosaiced CFA frame is therefore biased low relative to a true mono frame or a 2×2 superpixel. For CFA-vs-CFA relative weighting this is consistent; CFA-vs-mono comparisons are not on equal footing. An inherent trade-off of the (deliberately resolution-preserving) approach, worth recording.

Recommendation

Document that CFA-frame noise is smoothing-suppressed and not directly comparable to mono; if absolute noise matters, estimate it on the raw mosaic per CFA phase.

Test status

Not asserted (tests check means/geometry, not noise characteristics).

CR-9 Jupiter and Saturn positions are never numerically validated Correctness-risk

SwiftAstroTests/Ephemeris/PlanetPositionTests.swift · Confidence: high (lead-verified)

What & why

Among planets, only Mercury/Venus/Mars get a numeric Schlyter check, and Uranus/Neptune get only a heliocentric distance-range check (which exercises a/e but not N,i,w,M). Jupiter and Saturn have no accuracy test at all (they are never even referenced in the position tests) — a future typo in a Jupiter/Saturn element polynomial would very likely pass CI silently. The elements are correct today (all verified against Schlyter); this is purely regression exposure.

Recommendation

Add a heliocentric long/lat/dist assertion for Jupiter and Saturn against Schlyter's worked example, matching the Mercury/Venus/Mars pattern.

Test status

Missing.

Improvement

  • IMP-1 — StarMoments eccentricity is not upper-clamped (StarMoments.swift:134): max(0, 1−minor/major) guards only the lower bound; a non-PSD moment matrix (negative weights, reachable via the public init? or the bright pass's aperture pixels below local sky) yields ecc > 1, violating the documented 0…1 invariant. Clamp to [0,1].
  • IMP-2 — detectionImage materializes the data segment twice (FITSImageDecoder.swift:106–107): it calls imageHDU (which renders the whole data segment) only to read the header, then linearImage renders it again — a real, avoidable cost on large frames. Read the header once and reuse it.
  • IMP-3 — integer BLANK undefined pixels are not masked (FITSImageDecoder.swift): the FITS BLANK sentinel for integer BITPIX is not read, so undefined pixels pass through as ordinary values and skew statistics. Rare in camera FITS, low impact. (BZERO/BSCALE application itself is correct.)
  • IMP-4 — SNR noise is whole-image MAD, not a background-isolating estimator (SignalToNoise.swift:84–86): PixInsight's SNRWeight uses a multiscale (MRS) noise estimate that excludes stars/nebulosity/gradients; whole-image MAD is inflated by real structure on high-signal frames. A documented trade-off; note the divergence or estimate on a high-pass residual.
  • IMP-5 — sampleWidth fits a full Gaussian over a window that grows with the estimate (MatchedFilterStarDetector.swift:368, 389): as FWHM grows toward the clamp of 40, the fit window reaches ~161×161 ≈ 26 000 samples × up to 360 fits, on every default-config detection. Fit over the connected footprint or a capped sub-window.
  • IMP-6 — matched-filter purity/gate knobs are entirely untested (Configuration: saturationLevel, minSeparation, edgeMargin, sharpnessLow, roundnessLimit, minFWHMFactor, maxFWHMFactor, thresholdSigma): none is ever set to a non-default value, so the size band, roundness, sharpness, separation, edge margin, saturation gate and threshold are validated only at their defaults. Add toggle tests as the bright-star tests already do.
  • IMP-7 — SignalToNoise.init(noise:) accepts non-positive noise (SignalToNoise.swift:47–62): weight = 1/noise², and the public initializer does not validate, so init(noise: 0).weight is +∞ (the estimate path guards, the initializer does not). Precondition/failable-init or document positivity.
  • IMP-8 — outer-planet mutual perturbations omitted (Planet.swift:119–158): Saturn can be ~0.8° and Jupiter ~0.3° off. Honestly documented (“a fraction of a degree for the outer ones … ample for deciding whether a planet is above the horizon”) and consistent with the visibility purpose — not a bug; add Schlyter's perturbation terms only if sub-0.1° is ever wanted.
  • IMP-9 — the Ephemeris facade has no dedicated test: normalizedDegrees/normalizedHours wraparound (esp. negative/NaN), obliquity, radians/degrees, and the horizontal transform at edge cases (poles, zenith, HA wrap) are untested directly (only anchored indirectly via SolarPositionTests). Add a small EphemerisTests.
  • IMP-10 — isAboveHorizon consistency tests are tautological (PlanetPositionTests.swift:166, LunarPositionTests.swift:152): isAboveHorizon == (altitude > 0) restates the implementation and can never fail. Replace with fixed-value cases (incl. the altitude == 0 → false boundary).
  • IMP-11 — the moment→Gaussian-fit seeding has no direct unit test (GaussianFit+StarMoments.swift): the seed (σx=√λ₁, σy=√λ₂, θ=½·atan2(2Mxy, Mxx−Myy)) is correct but only exercised end-to-end (which sorts the σ and checks orientation indirectly). Add a direct seed-value assertion on a known ellipse.
  • IMP-12 — bootstrap footprintWidth did not receive the annulus-sky robustness of commit 5532c9a (MatchedFilterStarDetector.swift:476–477): it reads a whole-window median as “background.” Not an incomplete fix in practice (fixed radius; only the bootstrap seed, corrected by the now-robust sampleWidth) — recorded so a future change doesn't assume it is annulus-robust.

Cosmetic

  • COS-1 — 1.4826 (MAD→σ) duplicated across SignalToNoise, SkyBackground, and the star detector as separate private constants. Correct, but a shared constant would prevent drift.
  • COS-2 — BayerGrayscaleConverter mixes a channels stride with a hardcoded /3 (:88–90): base = index*channels then reads base, base+1, base+2 and divides by 3. Correct (the CFA pipeline always yields 3 channels) but the mixed convention is misleading.
  • COS-3 — StarMoments.halfFluxRadius has a dead else branch (:176–180): the cumulative's last element equals flux, so ≥ flux/2 always holds and the fallback is unreachable. Plus informational notes: no Sheppard/pixelization correction (~+4% on FWHM at σ≈1) and a small noise-driven eccentricity floor — inherent to moment measurement.
  • COS-4 — OrbitalElements Kepler solver yields NaN for e ≥ 1 (:92, √(1−e²)): unreachable (every element set is a fixed low-eccentricity body, max e≈0.206); a note that the internal struct is not general-purpose.
  • COS-5 — Ephemeris altitude asin(horizontalZ) is not domain-guarded (:163), unlike EquatorialCoordinate.angularSeparation's min(√h,1) (:62): mathematically bounded, but FP rounding at the exact zenith could push the argument a hair over 1 and return NaN. Clamp for parity.
  • COS-6 — bright-pass doc overstates metric comparability (+BrightStars.swift:82–85): it measures shape from a circular aperture (including background pixels), the matched-filter path from the connected footprint (above bg+3σ), so flux/fwhm/hfr are on a different basis — “comparable” is only loosely true. Soften the comment.
  • COS-7 — misaligned = at MatchedFilterStarDetector.swift:477 (let localBackground is not =-aligned with its block), against the repo's alignment convention.
  • COS-8 — the SyntheticStarGrid ground-truth fixture is unused by any detector test (it is referenced only by its own generator self-test): its saturated/eccentric/haloed ground truth never validates detector recall or metric trends. Add a small recall/metric test over it, or remove the unused fixture.
  • COS-9 — honorsBrightPassThreshold doesn't isolate the knob (BrightStarDetectionTests.swift:187–196): it sets two bright-star parameters and asserts only recall, so it can pass without the threshold parameter doing anything. Assert a change versus default.
