Overview

M6 re-ran the M1 benchmark harness fresh, in Release, on the current post-M5 tree, and classified every SwiftPixel processor and core primitive (and the SwiftAstro algorithms) by workload shape to judge Metal suitability. This is an analysis-only milestone — like the M2/M3 audits, no production code was changed. It produces two lists for the phases ahead: the Metal target list (for M7/M8+) and the “stays on CPU” list (for Phase 4 / M9).

Why re-run. The committed M1 baselines (2026-07-15) predate several Phase-2 changes and are stale — most notably Debayer VNG (20.85 → 55.76 ms after M5.8's canonical port) and Normalize (3.01 → 4.08 ms after M5.1; both figures are min, as throughout) — and the SwiftAstro decode rows were renamed when M5.15 retired FITSImageDecoder. The numbers below are the current truth.

Method & how to read the numbers

Two cost views. The harness runs each algorithm on a different representative frame (mono/raw stages on 2048² = 4.19 Mpx, colour stages on 1024² = 1.05 Mpx), so raw milliseconds are not comparable across rows. Every table therefore also gives throughput (Mpx/s) — pixels processed per second, the size-independent measure — and a projected cost at 8.3 Mpx (a real 3840×2160 frame, the app's full-resolution render size). min is used as the least-noisy estimate of intrinsic cost, per the harness convention.

Workload taxonomy (what determines GPU fit):

  • Per-pixel (map) — each output sample is a pure function of the co-located input sample(s). Embarrassingly parallel; the ideal GPU shape.
  • Neighbourhood / stencil — each output reads a small fixed window (convolution, demosaic, local median). Parallel, GPU-friendly, higher arithmetic intensity.
  • Reduction — the whole image collapses to a few numbers (min/max, sum, median & MAD via a full sort). Poor GPU fit — sorting on the GPU is a bitonic network that rarely beats Accelerate.
  • Geometric / permutation — samples are moved, not transformed (rotate, mirror, resample, channel replicate). Bandwidth- or scatter-bound; often has a dedicated Accelerate/vImage primitive.

Metal-suitability rubric. A row is a strong GPU candidate when it is per-pixel or stencil (independent outputs), has real arithmetic intensity, has no cheap Accelerate equivalent, and runs on the large full-resolution frames the app renders. A row is “optimize on CPU first” when it is slow only because of implementation overhead (per-index closures, allocations) or a sort, where a CPU fix is lower-risk and may erase the need for a GPU port. A row is “already optimal” when it is Accelerate-backed and fast.

Load-bearing constraint — the pipeline is Double, Metal has no double. Every SwiftPixel sample is a 64-bit Double, but the Metal Shading Language Specification states Metal does not support the double type (only half and float). So any GPU kernel must operate in Float32 (or Float16), a deliberate precision reduction from today's Double math — which the whole correctness audit (M2–M5) was verified in. This is not a detail: it gates all of Phase 3 and needs a maintainer decision (see Open decisions D-A). Confirmed against the Metal Shading Language Specification (Apple).

Headline findings

F1. The CPU story is two-tier: vDSP-vectorized vs. scalar-closure

Every fast processor runs on Accelerate (vDSP / vForce); every slow one runs a scalar Swift closure per pixel via PixelUtilities.parallelOrSerial. The gap is stark: per-pixel vDSP processor stages hit 290–3200 Mpx/s, while the scalar-closure stages (Hue, Saturation, ColorBalance, MonoToRGB, Orient, CosmeticCorrection) sit at ~20 Mpx/s — a 15–100× spread. The sort-based reductions (median / MAD / percentileBounds) also land at ~17 Mpx/s, but for a different reason (the O(n log n) sort). This split — not intuition — defines the two work-lists below.

F2. Some “hot” processors are overhead-bound, not compute-bound — a CPU fix, not Metal

MonoToRGB is a channel copy, yet it takes 187 ms. It writes ~96 MB, which at that time is ~0.5 GB/s effective — two orders of magnitude below this machine's memory bandwidth. It is bound by the per-index closure and bounds-checking, not by the work or the bandwidth. Orient (a pure permutation, 188 ms) is the same story. These do not need a GPU — they need a chunked/strided CPU rewrite (or a vImage/vDSP primitive), which should recover ~10× on the CPU alone. Rushing them to Metal would hide the real defect and pay the Float32/transfer cost for nothing.

F3. The single biggest cost in the system is detectStars — and it is not a clean Metal target

Star detection is 1.69 s on a 1 Mpx crop (~0.6 Mpx/s) — it would be several seconds on the app's full frames, dwarfing everything else. But it is a composite pipeline: a matched-filter convolution (already vDSP), robust-noise median/MAD (sort-bound), and a Levenberg–Marquardt Gaussian fit per star (small, iterative, serial). The convolution could move to MPSImageConvolution; the per-star fits do not parallelize cleanly across the image. Its two hot sub-parts — convolution and median/MAD — are shared SwiftPixel primitives, so the CPU wins in F5 benefit detection directly, at no extra risk.

F4. The strongest Metal case is fusing the display chain, not porting any one processor

The pipeline defines a long fixed chain of per-pixel stages that run back-to-back — Normalize → WhiteBalance → Stretch → BrightnessContrast → Gamma → Levels → Curves → ColorBalance → Hue → Saturation → Invert (the app wires all of these to controls except Gamma, which the pipeline supports but the app does not currently expose) — and the app re-runs the enabled ones at full resolution whenever an adjustment changes. On unified memory a fused GPU pass uploads once (or shares the buffer with no copy), chains all these kernels on one command buffer with the intermediate staying resident, and reads back once. That amortizes the (small) submission latency over the whole chain and keeps the interactive re-render responsive — a far better payoff than accelerating a single stage while the rest stays on the CPU.

F5. The highest-leverage CPU win is median / MAD

These sort the full 4.19 M-sample array (~248 ms, and MAD allocates a second full array for the deviations). The median is the 50th percentile — a quickselect (O(n) partial selection) computes it without a full sort, and the MAD's absolute-deviation pass can go through vDSP. They are consumed by SNR, SkyBackground, Normalize(.percentile), the stretch statistics and the star detector's robust noise, so one fix ripples across the whole system.

Metal target list (for M7 / M8+)

Ordered by expected payoff. Speedups are provisional order-of-magnitude estimates from the workload shape, not measurements — each must be confirmed with a spike against the M1 harness (per the plan's per-processor template). All assume the Float32 decision (D-A) is settled.

1. Debayer VNG  GPU strong

Why: a 5×5 stencil with per-pixel gradient selection and conditional colour-difference averaging — every output pixel independent, genuine arithmetic intensity, and (unlike bilinear) no fixed-kernel Accelerate form. The M5.8 review already flagged Metal as its natural home. ~110 ms at full resolution today.

Estimate: high (a data-parallel stencil is the GPU's best case); the data-dependent branch per direction is the only friction. Transfer: one mono upload, one RGB download; small vs. the compute.

2. The fused display chain — Stretch, BrightnessContrast, Levels, Curves, ColorBalance, Hue, Saturation, Invert  GPU strong (as a group)

Why: see F4. Individually most of these are already fast on vDSP; the win is fusing the whole interactive re-render into one resident GPU buffer so a slider drag doesn't round-trip each stage through the CPU. This is the case that justifies the M7 infrastructure investment.

Estimate: the payoff is latency and CPU offload on interactive edits, not raw throughput on any one stage. Transfer: the crux — the design must keep the buffer GPU-resident across stages (no per-stage copy); on unified memory this is cheap if done right and ruinous if not.

3. CosmeticCorrection  GPU strong

Why: a per-pixel 8-neighbour local-median/MAD stencil, already written to read source-only and write its own slot (embarrassingly parallel). ~417 ms at full resolution. The tiny per-pixel sort maps to a fixed unrolled network on the GPU.

Estimate: high. Transfer: one upload, one download; it runs pre-demosaic on the raw mono/CFA buffer.

Evaluate: Hue / Saturation / ColorBalance individually  GPU / vDSP

Members of the fused chain above. Standalone, Hue favours the GPU (branchy RGB↔HSV resists vDSP); Saturation and ColorBalance are also CPU-vectorizable (the luma is a fixed linear combination, the per-channel adjustment affine) — so if the fused pass slips, they have a cheaper CPU path. Convolution and the detector's matched filter could use MPSImageConvolution, but they are already on vDSP, so measure before porting.

Stays on CPU — optimize here (Phase 4 / M9)

These should be improved on the CPU, not ported. Several are higher-leverage and lower-risk than the Metal work.

  • median / MAD / percentileBounds — replace the full sort with a quickselect (the median/percentile need only a selection, not a total order) and route the MAD's absolute-deviation pass through vDSP to drop the second full allocation. Benefits SNR, SkyBackground, Normalize(.percentile), the stretch stats, and the star detector. Highest leverage.
  • MonoToRGB, Orient — overhead-bound (F2). Rewrite the per-index closure as chunked/strided work; Orient maps onto vImage's rotate/reflect primitives, and MonoToRGB onto a strided vDSP copy. Expect ~10× on the CPU with no precision change.
  • readRawPixels — per-sample decode + byte-swap; a vDSP integer→float conversion (with a vImage byte-order pass) beats the scalar closure. Directly speeds the FITS decode rows.
  • detectStars — profile its sub-stages on a real frame first; it inherits the median and (optionally) convolution wins. A dedicated milestone, not a blind port.

Data-transfer & fusion analysis

  • Unified memory helps, but is not free. Apple-silicon GPUs share DRAM with the CPU, so a MTLBuffer can wrap the sample storage without a copy. The real cost is per-command-buffer submission latency (tens of µs) and any implicit format conversion — both negligible when amortized over millions of pixels, but able to dominate a single cheap stage on a small preview.
  • Fuse, don't ping-pong. A per-stage “upload → one kernel → download” design would lose to the CPU. The chain must stay GPU-resident across stages (F4); this is what M7's dispatch seam has to make natural.
  • Float32 conversion is a real, recurring cost (D-A). If the buffer stays Double on the CPU, every GPU excursion pays a Double→Float down-convert and a Float→Double up-convert. The fused chain pays this once (in/out); a per-processor port pays it every stage — another argument for fusion over piecemeal ports.
  • Small previews may never want the GPU. The preview path already downsamples (maxDimension); at a few hundred kpx the submission + conversion overhead can exceed the compute. The seam should fall back to CPU below a size threshold (and in headless/no-GPU environments).

Decision  Open decisions for the maintainer

M6's task 4 is to review this before M7 builds any infrastructure. These shape Phase 3:

  • D-A — Float32 for GPU. Metal has no double. Accept Float32 (single precision) for GPU kernels? For display-referred stages on normalized [0, 1] data this is almost certainly fine; for anything feeding measurement/detection it needs thought. This gates all of Phase 3.
  • D-B — Metal scope: fused chain vs. per-processor. The evidence favours building M7 around a fused, GPU-resident display pass (F4) rather than the plan's implied one-processor-per-milestone ports (M8+). Confirm the direction, since it reshapes M7/M8+.
  • D-C — phase ordering. Several top CPU wins (median/quickselect, MonoToRGB/Orient vectorize, readRawPixels) are lower-risk, need no Float32 decision, and also speed up detectStars and decode — the system's biggest costs. Consider doing that CPU work (Phase 4 / M9) before or alongside the Metal build, rather than strictly after. This is a suggested re-ordering, not a change made unilaterally.
  • D-D — refresh the committed baselines? The committed M1 baselines are stale. Options: (a) refresh both submodules' Docs/Benchmarks to these post-M5 numbers so Phase 3/4 measure against current state; (b) keep M1 as the historical reference and treat this report as the M6 snapshot; (c) both. The plan's M9/M10 currently say “measure against the M1 baseline.”
  • D-E — detectStars in scope for Phase 3? It is the biggest single cost but a composite, not a clean port. Confirm whether it gets its own profiling+optimization milestone or is deferred.

Recommended next step

Pending the decisions above, the highest-confidence sequence is: (1) settle D-A/D-B; (2) take the median/quickselect and MonoToRGB/Orient/readRawPixels CPU wins (low risk, broad benefit, no precision change); (3) build M7 around a fused Float32 display pass and prove it end-to-end with a trivial kernel; (4) port VNG and CosmeticCorrection as the first stencils on that infrastructure, each measured against this baseline.
