Overview

This plan audits and improves the image-processing and astronomy algorithms behind FITScope, which live in two nested submodules: SwiftPixel (pixel processors and core imaging primitives) and SwiftAstro (star detection, signal-to-noise, preprocessing, and ephemeris math). SwiftPixel is itself a submodule of SwiftAstro (Submodules/SwiftAstro/Submodules/SwiftPixel).

The approach is audit-first: we build a repeatable benchmark and profiling harness, then produce a written correctness audit of every algorithm before touching code. Confirmed issues are triaged and appended to this plan as concrete fix milestones (Phases 1–2, complete). Only then do we tackle performance.

Performance direction — revised after the M6 profiling (see profiling.html and “Replan” below). The original plan moved the hot processors to Metal first; the profiling showed that the largest costs are better addressed on the CPU (the sort-based robust statistics, the un-vectorized scalar processors), that full-resolution interactivity is primarily a caching problem rather than a compute-speed one, and that Metal is a last-mile, conditional win that would be swamped without caching first. So the order is now CPU optimization → caching → re-measure → Metal only if the numbers justify it. Every performance change is measured against the harness baseline, and every behavioural change is guarded by the existing per-algorithm unit tests.

Questions & answers

  • How should the open-ended correctness audit (backlog item 1) be structured?

    Audit-first, then fix. Dedicated audit milestones produce a written findings report; confirmed issues become their own fix milestones appended to this plan, keeping review separable from changes.

  • How should the plan decide which processors move to Metal (backlog item 2)?

    Profile-driven. An early milestone profiles the processors on representative FITS images and selects the hot ones from measured data, before any Metal kernel is written.

  • Should the plan build a benchmark harness for the optimization work (items 2 and 3)?

    Yes — a dedicated harness. A repeatable benchmark harness with representative FITS images gives every optimization a measured baseline and a regression guard.

  • What is in scope for the audit?

    Everything in both submodules. All of SwiftPixel (processors + core primitives) and all of SwiftAstro, including the Ephemeris positional-astronomy math.

Replan (post-M6): direction & key decisions

The M6 profiling (profiling.html) reshaped the performance half of this plan. The decisions below were worked through with the maintainer and drive Phases 3–7; they are recorded here so the rationale is not lost.

  • CPU and caching before Metal. The dominant cost is star detection (a composite, not a clean GPU target) whose hot sub-parts are shared CPU primitives; the slow display stages are un-vectorized scalar closures; and MonoToRGB / Orient are overhead-bound, not compute-bound. So the CPU wins are higher-ROI and lower-risk than Metal, and several benefit the app and the library alike.
  • Interactivity is a caching problem. ImageRenderer re-runs the whole pipeline on every adjustment (no cross-render cache, deliberately, because hundreds of full-resolution images can be open at once), and editing is full-resolution — so a slider drag re-runs decode + cosmetic + debayer + normalize (~750 ms) that don't depend on the slider. Caching the linear buffer for the active image (released under memory pressure) is the single biggest interactivity lever — and a prerequisite for any display-path acceleration to matter.
  • Metal is last-mile and conditional. It is decided by the re-measure (M12), targets a fused Float32 display pass, and is built only if a vectorized, cached CPU display chain is still short of interactive. The Metal Shading Language has no double type (verified against the MSL spec), so any GPU kernel is Float32; the CPU path is kept regardless (CI / build-VMs have no Metal, and it is the parity reference).
  • Precision boundary (D-A). Everything inside the library is Double. If a Float32 display path is adopted, the safe boundary is the display chain (normalized [0,1] data, output to a ≤16-bit image); ingest and the SwiftAstro analysis path stay Double. The Float32 decision is deferred to M12; the Double-domain work (M7–M11) does not depend on it.
  • Float32, if adopted, is a two-family split by role (D-B), not generics or per-op duplication (M13). A PixelPreprocessor family works in Double (through Normalize); a PixelProcessor family works in Float32 (the display chain), with one Double→Float32 conversion at the Normalize seam. Each stage lives in exactly one family (no op implemented twice); PixelBuffer stays concrete (a hidden generic behind PixelBuffer64 / PixelBuffer32 aliases, or a duplicated struct). The Float32 family requires normalized input (its existing contract), so it only ever runs after Normalize; with no display chain the pipeline stays Double end to end (.identity normalize included).
  • Metal keeps the public API Double (D-B). A Metal-capable stage is one processor with an internal GPU kernel (a CPU-reference + kernel pair bound by a parity test), not a public Float32 family; Float32 lives inside the kernel / a GPU-resident texture, never in the public PixelBuffer.
  • Orient stays last, vectorized. Keeping it after the display chain lets the linear cache survive rotations (a rotate re-runs only the display chain on the cached buffer). Export needs real re-oriented pixels, so it is a genuine (vectorized) permutation, not a view transform; it joins the Float32 display family if M13 is adopted.
  • Baselines (D-D) / detectStars (D-E). The committed M1 baselines stay as the historical reference; M6's fresh numbers live in profiling.html, and M12 re-measures at full resolution. detectStars gets its own profiling+optimization milestone (M9).

Implementation notes

Approach. Per the interactive design decisions, the harness is an env-gated Swift Testing benchmark (both submodules use Swift Testing, not XCTest) living in each submodule's test target under Benchmarks/. It runs only when RUN_BENCHMARKS is set, so normal runs skip it entirely; no new build targets were added, so Package.swift stays in sync automatically and the .xcodeproj was kept in sync by adding the files programmatically with the xcodeproj Ruby gem (idempotent script). Built with TDD: the pure harness logic has fast unit tests that run in the normal suite; only the heavy capture is gated. No production source was changed — everything is additive under Benchmarks/.

Metrics. Min/median/max wall-clock (monotonic DispatchTime) over N iterations, plus a best-effort peak allocation. The allocation meter samples malloc_zone_statistics's size_in_use from a background thread (an NSLock-guarded @unchecked Sendable tracker); an earlier phys_footprint approach was discarded because it read ~0 after allocator warmup. Every measured result flows through a withExtendedLifetime guard so an optimized build can't elide it as dead code.

Frames. SwiftPixel ships no fixtures, so it synthesizes deterministic mono / RGB / raw-mono / RGGB-mosaic frames (gradient + noise, never constant); a tiny() variant drives the fast smoke test. SwiftAstro reuses the committed FITS fixtures via FITSTestImage (an ESA M35 centre crop for detection/SNR, the real RGGB light frame for Bayer/decode) and a small synthetic set for its smoke test.

Baseline & layout. Each run writes a machine-diffable JSON plus a deterministic Markdown table to that submodule's own Docs/Benchmarks/ (self-contained; FITSCOPE_BENCH_OUT can redirect it). The generic Core/ timing/reporting code is intentionally duplicated across the two independent submodule repos (test-target code can't be shared without adding a library target). Each submodule's main README.md gains a “Benchmarks” section documenting how to run and interpret the output.

Capture caveat. xcodebuild test does not forward the shell environment to the test host, so the gated capture is driven via SwiftPM: RUN_BENCHMARKS=1 swift test -c release --filter Test_<Module>Benchmarks.

M9.1 Star detection — dense-field scale robustness & nebula false positives Completed

Goal

Dense / crowded fields (the M35 cluster) detect only a handful of stars. Root cause: the two-stage FWHM auto-estimation's growing-window refinement merges neighbouring stars on a crowded field and runs the detection scale several-fold too large (≈3 → 17 px on M35), so the matched-filter kernel and the size-band purity cut reject the real ≈3 px population — collapsing detection to ~55 where ~1745 exist. Fix direction: detect on the crowding-robust bootstrap scale (estimateFWHM) and drop the refinement; M5.14's merge-aware bootstrap made it redundant, and reference tools (NINA, photutils DAOFIND) do no such global-scale auto-refinement. Discovered from M9's profiling. Low-risk.

M42 nebula false positives (the harder, open part). The separate bright-star pass emits spurious “stars” on flat, bright nebulosity (seen on the C6-ASI585 and C6-R7 M42 frames). Root cause: the pass forms connected components above a global threshold (bg + 6σ); a flat patch of bright gas crosses it and noise fragments it into round, PSF-sized blobs that clear every other purity cut (size band, roundness, single-peak). Latent until the scale fix above un-hides them (the old oversized scale dropped them as “too small”). A simple local-contrast cut (blob peak vs local sky) does not clearly generalise — the raw maximum is noise-inflated for large blobs (a large flat blob clears it on noise alone), and a robust-peak variant (median of the brightest samples) over-corrects, washing out a compact star embedded in a large above-threshold gas patch. Needs a fresh, spatially-aware “is there a concentrated core?” discriminator that is robust both to the noise-inflated max and to a compact core inside a large component, and that still keeps saturated flat-topped stars (which have no strict local maximum, so a naive “require a peak” rule would wrongly drop them).

Tasks
  • Add a local (spatially-varying) background & noise estimator to SwiftAstro — a mesh of per-tile robust medians and MAD-sigmas, interpolated to full resolution.
  • Use it for detection decisions only (scale estimation, the matched-filter and bright-pass thresholds, footprint levels); keep every reported measurement on the raw pixels so flux / hfr semantics and the H3.69 calibration are unchanged.
  • Drop the growing-window FWHM refinement and detect at the (now locally-grounded) bootstrap scale.
  • Confirm on the real fixtures: the M35 dense-field collapse is fixed, the M42-stack / C6-ASI585 / C6-R7 scale errors are fixed, and the bright-pass nebula false positives are gone.

Implementation notes

Approach. A root-cause milestone, built with TDD. Measurement showed the goal's stated fix direction was unsafe (see Review comments), so with the maintainer's approval the work targets the shared cause of both halves instead: every whole-frame “is this above the background?” decision was taken against a single global median + 1.4826×MAD, which is meaningless on a frame carrying large-area nebulosity. Everything stays in Double (D-A). All work is in SwiftAstro only — SwiftPixel is untouched and the app needed no change.

What was built. A new public LocalBackground (SwiftAstro/SignalToNoise/, beside SkyBackground): a mesh of per-tile robust median and 1.4826×MAD, median-filtered against its 3×3 neighbourhood (the SExtractor treatment for tiles a source has contaminated), bilinearly interpolated back to pixel resolution, with blank-safe statistics inherited from the shared PixelUtilities helpers. The detector consults it for the two decisions taken over the whole frame at once — the scale estimate and the bright pass's blob threshold. The two decisions that are already local keep their own basis: the matched filter thresholds the zero-sum convolved response (which has removed the smooth background before the threshold applies), and a candidate's footprint level comes from its own measurement window. Reported measurement stays on the raw samples, so flux / hfr semantics are unchanged; the one place a mapped value is reported is the bright pass's photometric zero for a blob whose sky annulus yields no positive flux.

The refinement is gone. refinedFWHM, sampleWidth, refinementSampleSize and sampleWidthMinRadius are deleted; detection runs at the bootstrap scale, as the milestone intended. The bootstrap gained a bounded second pass over a window scaled to its first estimate, because the fixed radius-10 window puts the sky annulus inside a broad star, which reads the star as its own background and sizes it far short. That second pass is accepted only while it still rests on about as many unmerged stars as the first — on a crowded field the wider window reaches into the neighbours instead, and without that guard it reproduces exactly the runaway the deleted refinement suffered from. Because the mesh only describes sky while sources are a minority of a tile, scale(of:configuration:) resolves the map and the scale together, widening the tile (64 → 512) until it is at least 3× the FWHM it measured; every real fixture settles on the first tile, so an ordinary frame still pays for exactly one map.
