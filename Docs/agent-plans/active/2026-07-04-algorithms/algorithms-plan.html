Overview

This plan audits and improves the image-processing and astronomy algorithms behind FITScope, which live in two nested submodules: SwiftPixel (pixel processors and core imaging primitives) and SwiftAstro (star detection, signal-to-noise, preprocessing, and ephemeris math). SwiftPixel is itself a submodule of SwiftAstro (Submodules/SwiftAstro/Submodules/SwiftPixel).

The approach is audit-first: we build a repeatable benchmark and profiling harness, then produce a written correctness audit of every algorithm before touching code. Confirmed issues are triaged and appended to this plan as concrete fix milestones. Only then do we tackle performance — profiling to identify the hot processors, moving those to Metal kernels (SwiftPixel has none today), and optimizing the remaining CPU processors with Accelerate and fewer allocations. Every performance change is measured against the harness baseline, and every behavioural change is guarded by the existing per-algorithm unit tests.

Questions & answers

  • How should the open-ended correctness audit (backlog item 1) be structured?

    Audit-first, then fix. Dedicated audit milestones produce a written findings report; confirmed issues become their own fix milestones appended to this plan, keeping review separable from changes.

  • How should the plan decide which processors move to Metal (backlog item 2)?

    Profile-driven. An early milestone profiles the processors on representative FITS images and selects the hot ones from measured data, before any Metal kernel is written.

  • Should the plan build a benchmark harness for the optimization work (items 2 and 3)?

    Yes — a dedicated harness. A repeatable benchmark harness with representative FITS images gives every optimization a measured baseline and a regression guard.

  • What is in scope for the audit?

    Everything in both submodules. All of SwiftPixel (processors + core primitives) and all of SwiftAstro, including the Ephemeris positional-astronomy math.

Notes

Algorithm surface (as of 2026-07-15).

  • SwiftPixel — Processors (~22): Bin, BrightnessContrast, ColorBalance, CorrectGamma, CosmeticCorrection, Curves, Debayer (+ Bilinear / Deinterleave / VNG), Hue, Invert, Levels, MonoToRGB, Normalize, Orient, Resample, Saturation, Scale, STFParameters, Stretch, WhiteBalance.
  • SwiftPixel — Core primitives: Convolution, GaussianFit, GaussianKernel, Histogram, HistogramStatistics, PixelBuffer, PixelPipeline, PixelProcessor, PixelUtilities, BitsPerPixel.
  • SwiftAstro: StarDetection (MatchedFilterStarDetector, GaussianFit+StarMoments, StarMoments, StarField, Star, StarDetecting), SignalToNoise (SignalToNoise, SkyBackground), Preprocessing (BayerGrayscaleConverter, FITSImageDecoder), Ephemeris (11 files: planet/lunar/solar positions, twilight, moon phase, coordinate systems).

Current state.

  • SwiftPixel uses no Metal today — all processors are pure CPU, ~15 files already lean on Accelerate (vDSP / vImage). Adding a GPU path is a new architectural capability, not a refactor.
  • Both submodules have strong unit-test coverage: roughly one test file per processor and per algorithm. These tests are the correctness safety-net for every change; a few already use XCTest measure() blocks.
  • There is no dedicated, reusable benchmark harness yet — Milestone 1 creates one.

Working conventions.

  • All work happens inside the submodule repositories (SwiftAstro and the nested SwiftPixel), not in the FITScope app target. Per the working agreement, each submodule change is approved case by case, and commits/pushes/submodule-pointer bumps are left to the maintainer — this plan never performs them on its own.
  • Each submodule has both an .xcodeproj and a Package.swift; keep them in sync and prefer building/testing through xcodebuild.
  • Never weaken, skip, or delete a unit test to make a change pass. When a fix legitimately changes expected output, update the test deliberately and record why in the milestone's implementation notes.

Phase 1 · Groundwork & audit

M1. Benchmark & profiling harness Completed

Goal

Create a repeatable, reusable harness that measures per-processor and per-algorithm runtime on representative FITS images, so every later optimization has a measured baseline and a regression guard, and so processor "hotness" can be ranked from data rather than intuition.

Tasks
  • Assemble a small, representative set of input frames (mono + Bayer, a few bit depths and sizes) drawn from the existing test fixtures; document each frame's characteristics.
  • Build a benchmark entry point (XCTest performance target and/or a small executable) that runs each processor / core primitive over the frame set and reports wall-clock time and, where relevant, peak allocations.
  • Capture a baseline result set and store it in the repo (or under Docs) so before/after comparisons are reproducible.
  • Document how to run the harness and interpret its output.
  • Confirm the harness builds and runs green via xcodebuild in both submodules.
Status

Completed   Completed: 2026-07-15

Implementation notes

Approach. Per the interactive design decisions, the harness is an env-gated Swift Testing benchmark (both submodules use Swift Testing, not XCTest) living in each submodule's test target under Benchmarks/. It runs only when RUN_BENCHMARKS is set, so normal runs skip it entirely; no new build targets were added, so Package.swift stays in sync automatically and the .xcodeproj was kept in sync by adding the files programmatically with the xcodeproj Ruby gem (idempotent script). Built with TDD: the pure harness logic has fast unit tests that run in the normal suite; only the heavy capture is gated. No production source was changed — everything is additive under Benchmarks/.

Metrics. Min/median/max wall-clock (monotonic DispatchTime) over N iterations, plus a best-effort peak allocation. The allocation meter samples malloc_zone_statistics's size_in_use from a background thread (an NSLock-guarded @unchecked Sendable tracker); an earlier phys_footprint approach was discarded because it read ~0 after allocator warmup. Every measured result flows through a withExtendedLifetime guard so an optimized build can't elide it as dead code.

Frames. SwiftPixel ships no fixtures, so it synthesizes deterministic mono / RGB / raw-mono / RGGB-mosaic frames (gradient + noise, never constant); a tiny() variant drives the fast smoke test. SwiftAstro reuses the committed FITS fixtures via FITSTestImage (an ESA M35 centre crop for detection/SNR, the real RGGB light frame for Bayer/decode) and a small synthetic set for its smoke test.

Baseline & layout. Each run writes a machine-diffable JSON plus a deterministic Markdown table to that submodule's own Docs/Benchmarks/ (self-contained; FITSCOPE_BENCH_OUT can redirect it). The generic Core/ timing/reporting code is intentionally duplicated across the two independent submodule repos (test-target code can't be shared without adding a library target). Each submodule's main README.md gains a “Benchmarks” section documenting how to run and interpret the output.

Capture caveat. xcodebuild test does not forward the shell environment to the test host, so the gated capture is driven via SwiftPM: RUN_BENCHMARKS=1 swift test -c release --filter Test_<Module>Benchmarks.

Verification. Both submodules build and run green via xcodebuild with the benchmark correctly skipped; full normal suites pass (SwiftPixel 419 tests, SwiftAstro 128 tests) with no regressions. Baselines captured in Release: SwiftPixel 29 measurements (star of the show for later phases: PixelUtilities.median/medianAbsoluteDeviation ~245 ms, CosmeticCorrection ~205 ms, MonoToRGB/Orient ~185 ms on 2048²), SwiftAstro 11 measurements (star detection dominates at ~1.7 s on a 1024² crop; ephemeris is nanoseconds).

Automated review loop. 2 iterations with fresh-context reviewers. Round 1 found one Medium (misleading SwiftPixel capture docs) and one Low (normal-suite tests building full-size frames), both fixed; round 2 verified the fixes and found no Critical/High/Medium issues — converged.

Post-review change. On maintainer feedback, the SwiftAstro benchmarks no longer identify as "SwiftPixel": the duplicated Core doc examples and CoreTests fixture strings now use "SwiftAstro", and the SwiftAstro README was made self-contained (no longer deferring to the SwiftPixel README). Only the genuine import SwiftPixel and the SwiftPixel/PixelBuffer type reference remain, since SwiftAstro depends on that module.

Post-review change (2). On further feedback, the separate Benchmarks/README.md in each submodule was removed and its content folded into that submodule's main README.md as a “Benchmarks” section; the gated entry-point doc comments and the generated-report footer now point there instead. Both .xcodeproj files were re-synced accordingly, and both submodules still build and test green via xcodebuild.

M2. Correctness audit — SwiftPixel Completed

Goal

Review every SwiftPixel processor and core primitive for correctness, produce a written findings report, and flag anything that is wrong, questionable, or worth replacing with a better algorithm. No production code changes in this milestone — findings only.

Tasks
  • Audit the core primitives: Convolution, GaussianFit, GaussianKernel, Histogram, HistogramStatistics, PixelUtilities (median, interleave, MTF, percentile bounds, raw-pixel reads), PixelBuffer, PixelPipeline.
  • Audit the processors, grouping related ones: Debayer family (Bilinear / Deinterleave / VNG), tone/levels (Levels, Curves, Stretch, STFParameters, BrightnessContrast, CorrectGamma, Normalize), colour (ColorBalance, WhiteBalance, Hue, Saturation, MonoToRGB), geometry (Bin, Scale, Resample, Orient), and CosmeticCorrection / Invert.
  • For each: verify numerical correctness against the algorithm's definition, check edge cases (bit depth, channel count, boundaries, clipping, NaN/Inf), and note better algorithms or implementations where they exist.
  • Cross-check each finding against existing unit tests — does a test already cover it, is a test missing, or does a test encode the wrong expectation?
  • Record findings with severity (bug / correctness-risk / improvement / cosmetic) in the report captured in M4.

Implementation notes

Deliverable. A findings-only audit — no production code was changed. The findings live in a dedicated report, swiftpixel-audit.html, in this plan folder (styled like the plan, per the maintainer's choice), which M4 will consolidate with the SwiftAstro audit (M3). Scope: all 33 SwiftPixel source files (11 core primitives + 22 processors) and their 36 test files, at HEAD 13fa1ac.

Method. The 33 files were audited by 8 independent, fresh-context sub-agents, one per coherent file-group, each with a findings-only mandate and told to verify formulas and Accelerate/vDSP semantics against authoritative sources (Apple SDK headers & docs, algorithm references) rather than memory, consult git history for rationale, and cross-check every finding against the existing tests. Every finding was then reviewed by the lead, with the load-bearing items independently re-verified against the source: BUG-1 was reproduced with a throwaway Accelerate program; the seven GaussianFit analytic-Jacobian partials were hand-verified; and the .rgbg tile geometry, the STF raw-MAD usage, the GaussianKernel non-finite-σ trap, the guard-order pattern, the mis-wired MonoToRGB test, and the small-total histogram statistics were each confirmed by reading the cited code.

Result. 1 bug, 17 correctness-risks, 12 improvements, 8 cosmetics. The headline is reassuring — the mathematically heavy routines are correct (2D convolution, the Levenberg–Marquardt Gaussian fit, tone/levels/stretch, the four standard Bayer demosaics, and the colour/geometry/cosmetic stages). The defects cluster into a few themes: one true output-corruption bug (BUG-1 — Normalize corrupts NaN/Inf input and flags it normalized, realistic for FITS float frames); a recurring NaN-handling gap (also median/percentileBounds and CosmeticCorrection); a systemic guard-order mistake in MonoToRGB and Debayer that hides the accurate error; the non-standard .rgbg Bayer pattern that demosaics incorrectly; the STF shadow clip using raw MAD where its cited PixInsight constant assumes normalized MAD; and unenforced public-API preconditions (one a hard crash on non-finite σ). Several items are as much test fixes as code fixes (a negative-path test that exercises the wrong processor entirely; the new rotated/elliptical Jacobian left unguarded).

Round 1 (thorough — the reviewer independently re-derived the GaussianFit Jacobian and empirically reproduced BUG-1) found no false positives and confirmed every priority finding; it flagged one Medium (an internal count typo), one Low (a missed finding), and one Info (a test-file miscount), all fixed. Round 2 verified the fixes and the report's internal consistency and reported no Critical/High/Medium issues — converged.

Phase 3 · Metal acceleration of hot processors

M6. Profile & rank the hot processors Not started

Goal

Use the M1 harness to profile the SwiftPixel processors on representative frames and produce a ranked, evidence-backed list of the performance-critical ones — the candidates for Metal — distinguishing GPU-friendly (per-pixel, parallel) work from work that stays on the CPU.

Tasks
  • Run the harness across all processors; rank by runtime on realistic image sizes.
  • For each hot processor, classify its workload (embarrassingly parallel per-pixel, neighbourhood/convolution, reduction, or inherently sequential) to judge Metal suitability.
  • Estimate expected speedup and note data-transfer overhead (CPU↔GPU copies) that could erode gains.
  • Produce the target list for M7 and the "stays on CPU" list feeding Phase 4; review it with the maintainer before building Metal infrastructure.

M7. Metal infrastructure in SwiftPixel Not started

Goal

Introduce the GPU foundation SwiftPixel currently lacks: device/command-queue/library management, a shader-loading path packaged with the module, buffer↔texture bridging with PixelBuffer, and a clean way for a processor to offer a Metal path with a CPU fallback — without changing any processor's observable behaviour yet.

Tasks
  • Add Metal device/queue/library plumbing and decide how .metal shaders are compiled and bundled for both the Xcode project and SwiftPM targets.
  • Define the GPU/CPU dispatch seam in PixelProcessor / PixelPipeline so a processor can run on Metal when available and fall back to CPU otherwise (headless/no-GPU environments included).
  • Add PixelBuffer↔MTLBuffer/MTLTexture conversion helpers that respect bit depth and channel layout.
  • Prove the seam end-to-end with one trivial kernel (e.g. Invert), asserting the GPU and CPU paths produce identical output within tolerance.
  • Keep the Xcode project and Package.swift in sync; ensure CI/tests still pass with and without a usable GPU.
