Overview

This plan audits and improves the image-processing and astronomy algorithms behind FITScope, which live in two nested submodules: SwiftPixel (pixel processors and core imaging primitives) and SwiftAstro (star detection, signal-to-noise, preprocessing, and ephemeris math). SwiftPixel is itself a submodule of SwiftAstro (Submodules/SwiftAstro/Submodules/SwiftPixel).

The approach is audit-first: we build a repeatable benchmark and profiling harness, then produce a written correctness audit of every algorithm before touching code. Confirmed issues are triaged and appended to this plan as concrete fix milestones. Only then do we tackle performance — profiling to identify the hot processors, moving those to Metal kernels (SwiftPixel has none today), and optimizing the remaining CPU processors with Accelerate and fewer allocations. Every performance change is measured against the harness baseline, and every behavioural change is guarded by the existing per-algorithm unit tests.

Questions & answers

  • How should the open-ended correctness audit (backlog item 1) be structured?

    Audit-first, then fix. Dedicated audit milestones produce a written findings report; confirmed issues become their own fix milestones appended to this plan, keeping review separable from changes.

  • How should the plan decide which processors move to Metal (backlog item 2)?

    Profile-driven. An early milestone profiles the processors on representative FITS images and selects the hot ones from measured data, before any Metal kernel is written.

  • Should the plan build a benchmark harness for the optimization work (items 2 and 3)?

    Yes — a dedicated harness. A repeatable benchmark harness with representative FITS images gives every optimization a measured baseline and a regression guard.

  • What is in scope for the audit?

    Everything in both submodules. All of SwiftPixel (processors + core primitives) and all of SwiftAstro, including the Ephemeris positional-astronomy math.

Notes

Algorithm surface (as of 2026-07-15).

  • SwiftPixel — Processors (~22): Bin, BrightnessContrast, ColorBalance, CorrectGamma, CosmeticCorrection, Curves, Debayer (+ Bilinear / Deinterleave / VNG), Hue, Invert, Levels, MonoToRGB, Normalize, Orient, Resample, Saturation, Scale, STFParameters, Stretch, WhiteBalance.
  • SwiftPixel — Core primitives: Convolution, GaussianFit, GaussianKernel, Histogram, HistogramStatistics, PixelBuffer, PixelPipeline, PixelProcessor, PixelUtilities, BitsPerPixel.
  • SwiftAstro: StarDetection (MatchedFilterStarDetector, GaussianFit+StarMoments, StarMoments, StarField, Star, StarDetecting), SignalToNoise (SignalToNoise, SkyBackground), Preprocessing (BayerGrayscaleConverter, FITSImageDecoder), Ephemeris (11 files: planet/lunar/solar positions, twilight, moon phase, coordinate systems).

Current state.

  • SwiftPixel uses no Metal today — all processors are pure CPU, ~15 files already lean on Accelerate (vDSP / vImage). Adding a GPU path is a new architectural capability, not a refactor.
  • Both submodules have strong unit-test coverage: roughly one test file per processor and per algorithm. These tests are the correctness safety-net for every change; a few already use XCTest measure() blocks.
  • There is no dedicated, reusable benchmark harness yet — Milestone 1 creates one.

Working conventions.

  • All work happens inside the submodule repositories (SwiftAstro and the nested SwiftPixel), not in the FITScope app target. Per the working agreement, each submodule change is approved case by case, and commits/pushes/submodule-pointer bumps are left to the maintainer — this plan never performs them on its own.
  • Each submodule has both an .xcodeproj and a Package.swift; keep them in sync and prefer building/testing through xcodebuild.
  • Never weaken, skip, or delete a unit test to make a change pass. When a fix legitimately changes expected output, update the test deliberately and record why in the milestone's implementation notes.

Implementation notes

Approach. Per the interactive design decisions, the harness is an env-gated Swift Testing benchmark (both submodules use Swift Testing, not XCTest) living in each submodule's test target under Benchmarks/. It runs only when RUN_BENCHMARKS is set, so normal runs skip it entirely; no new build targets were added, so Package.swift stays in sync automatically and the .xcodeproj was kept in sync by adding the files programmatically with the xcodeproj Ruby gem (idempotent script). Built with TDD: the pure harness logic has fast unit tests that run in the normal suite; only the heavy capture is gated. No production source was changed — everything is additive under Benchmarks/.

Metrics. Min/median/max wall-clock (monotonic DispatchTime) over N iterations, plus a best-effort peak allocation. The allocation meter samples malloc_zone_statistics's size_in_use from a background thread (an NSLock-guarded @unchecked Sendable tracker); an earlier phys_footprint approach was discarded because it read ~0 after allocator warmup. Every measured result flows through a withExtendedLifetime guard so an optimized build can't elide it as dead code.

Frames. SwiftPixel ships no fixtures, so it synthesizes deterministic mono / RGB / raw-mono / RGGB-mosaic frames (gradient + noise, never constant); a tiny() variant drives the fast smoke test. SwiftAstro reuses the committed FITS fixtures via FITSTestImage (an ESA M35 centre crop for detection/SNR, the real RGGB light frame for Bayer/decode) and a small synthetic set for its smoke test.

Baseline & layout. Each run writes a machine-diffable JSON plus a deterministic Markdown table to that submodule's own Docs/Benchmarks/ (self-contained; FITSCOPE_BENCH_OUT can redirect it). The generic Core/ timing/reporting code is intentionally duplicated across the two independent submodule repos (test-target code can't be shared without adding a library target). Each submodule's main README.md gains a “Benchmarks” section documenting how to run and interpret the output.

Capture caveat. xcodebuild test does not forward the shell environment to the test host, so the gated capture is driven via SwiftPM: RUN_BENCHMARKS=1 swift test -c release --filter Test_<Module>Benchmarks.

M5.1 SwiftPixel — Non-finite (NaN/Inf) sample handling Completed

Fixes

SP BUG-1, CR-3, CR-8, CR-9.  Decision: D1 (sanitization policy).

Goal

Stop non-finite FITS blanks from corrupting output or crashing: the Normalize guard that misses NaN (BUG-1), the GaussianKernel(sigma:) Int(NaN) trap (CR-3), and the undefined NaN order in median/percentileBounds (CR-8) and CosmeticCorrection's neighbour sort (CR-9), applying the D1 policy consistently.

Status

Completed   Completed: 2026-07-16

Implementation notes

Approach. Built with TDD in the SwiftPixel submodule, applying the maintainer's D1 = Filter policy: drop non-finite (NaN / ±Inf) samples in the statistical helpers and guard the value transforms, so a stray FITS blank degrades gracefully instead of corrupting output or crashing. 16 failing tests were written first (5 median, 3 percentile, 1 GaussianKernel, 5 Normalize, 2 CosmeticCorrection) and confirmed red — the Normalize / PixelUtilities / CosmeticCorrection cases as graceful wrong-value failures, the GaussianKernel non-finite-σ case as the actual Int(NaN) hard trap that aborts the test process — then green. 4 source files changed, no new files, so Package.swift and the .xcodeproj stay in sync automatically.

BUG-1 — Normalize. All three modes (.minMax, .percentile, .identity) now take the range over the finite samples only and map non-finite blanks to 0 (black). .minMax uses a single scalar finiteExtent pass (min + max + a non-finite flag) in place of vDSP_minvD/vDSP_maxvD, so a blank no longer defeats the min ≠ max guard (NaN ≠ NaN is true) nor poisons the affine map — robustly, and independent of vDSP's undocumented NaN handling. A private mapNonFinite replaces blanks before the vDSP affine/clip.

CR-3 — GaussianKernel. A non-finite σ now clamps to the 1e-6 minimum (sigma.isFinite ? max(sigma, 1e-6) : 1e-6) instead of trapping in Int(NaN) / Int(+Inf).

CR-8 — median / percentileBounds. Both drop non-finite samples before sorting; the two median overloads now agree (both nil when no sample is finite). The common all-finite path is unchanged — a contains short-circuit avoids the filtering copy.

CR-9 — CosmeticCorrection. Non-finite neighbours are treated as absent during the gather, so a NaN can't wall the insertion sort and leave a genuine hot/cold pixel next to a blank uncorrected.

Verification. Full SwiftPixel suite green via xcodebuild (436 tests, 18 new). M1 harness re-run in Release: the hot primitives are unchanged within noise (median 245→247 ms, medianAbsoluteDeviation 250→254 ms, percentileBounds 245→248 ms, CosmeticCorrection 206→207 ms). Normalize.minMax moved 3.04→4.16 ms (+1.1 ms) — the deliberate cost of the robust scalar finiteExtent over vDSP min/max, on a processor ~60× faster than the hot paths.

Automated review loop. 1 round, converged — no Critical/High/Medium findings. The four lower-severity items were carried to the maintainer pause (see Automated review).

Post-review (decision A). For every finite, realistic input the radius is identical to before (verified against the old max(1, Int(ceil(…)))), so there is no behaviour change; 2 tests added (non-finite radiusInSigmas, pathologically large scale). Decision B: the robust scalar Normalize path is kept as-is.
