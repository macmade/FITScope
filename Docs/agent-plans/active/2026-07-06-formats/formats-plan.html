Overview

FITScope today opens exactly one thing: a single two-dimensional FITS image (NAXIS=2). The whole model pipeline is FITS-typed (OpenFile → FITSImageLoader → FITSImage / FITSImageRenderer), ImageProcessor.render hard-rejects anything but NAXIS == 2, and the keyword Info window is bound to a FITS-specific metadata model. This plan extends the app to open additional FITS geometries (NAXIS=1 and NAXIS=3), the XISF format, and common photographic formats (TIFF, PNG, JPEG, RAW, HEIC).

The chosen approach is a format-agnostic abstraction: rather than bolting each format onto the FITS path, we first extract the shared pieces — a generalized metadata model behind the Info window, a format-neutral image/loader layer, and a multi-image carousel — then add each format as a conformer of that layer. Decoded pixels flow through the existing processing pipeline where it is meaningful (stretch, curves, histogram, and, where a WCS is present, overlays and plate solving), so non-FITS images are first-class rather than display-only. Work is sequenced FITS geometries first (they stay within SwiftFITS), then XISF, then the photographic formats.

Questions & answers

Which architecture should the plan target for adding non-FITS formats to a fully FITS-typed pipeline?
A format-agnostic abstraction — refactor into a shared loader/image/metadata layer that FITS and every new format conform to, giving one display path.
How much of the existing image-processing UI should apply to non-FITS formats (stretch, curves, histogram, overlays, plate solving, star detection)?
The full pipeline where meaningful — feed decoded pixels through the same processing pipeline as FITS. This requires access to pixel data, not just a CGImage. Astronomy-only features (plate solving, star detection, WCS overlays) apply only where a WCS/relevant metadata is present.
The backlog says to use "the SwiftXISF submodule available in SwiftAstro," but SwiftXISF is not currently a dependency of SwiftAstro nor linked into the app. How should the plan wire it in?
The user will make the necessary project/target modifications to include SwiftXISF. The plan therefore assumes SwiftXISF is importable from the app target and does not include a submodule-wiring milestone; the XISF milestone depends on that linkage being in place.
How should the formats be sequenced?
FITS geometries first (NAXIS=1, NAXIS=3 RGB, NAXIS=3 multiple), then XISF, then the photographic formats — with the shared foundations (metadata-model generalization and the carousel) extracted as early milestones regardless.

Assumptions & risks

  • The crux of the refactor is a normalized pixel representation that the processing pipeline (currently FITS Data + BITPIX properties) can consume from any format. SwiftPixel's PixelBuffer is already in the pipeline (as the detection image) and is the likely common currency. Getting this abstraction right without regressing FITS rendering/performance is the main risk (Milestone 2).
  • Regression safety: the FITS path must remain byte-for-byte behaviourally identical after the refactor. Existing tests under FITScopeTests/ are the guard rail; extend them as the abstraction lands.
  • Astronomy features (plate solving, star detection, WCS overlays, north/grid) are gated on the presence of the relevant metadata (WCS keywords). For photographic formats without a WCS these are simply unavailable, not errors — the UI should hide/disable them rather than fail.
  • QuickLook FITScopePreviewExtension/FITScopeThumbnailExtension currently serve FITS. macOS already provides QuickLook for TIFF/PNG/JPEG/HEIC/RAW natively, so extending the extensions is treated as out of scope here (a possible follow-up for XISF); the plan focuses on in-app opening.
  • NAXIS=1 is inherently a graph, not an image; the pixel-processing pipeline (stretch/curves/histogram) does not apply to it. It takes a distinct display branch.
  • SwiftXISF linkage into the app target is handled by the user; Milestone 7 depends on it being present.

Milestone 2 — Format-agnostic image & loader abstraction

Completed

Depends on: Milestone 1.

Goal: Introduce a format-neutral image/loader layer so OpenFile dispatches by type and every format produces a common result: one or more frames, each exposing a normalized pixel representation the processing pipeline can consume, plus generalized metadata. FITS becomes the first (and, at this milestone, only) conformer, with identical behaviour.

Tasks
  • Define the abstraction: a loaded-image protocol/type exposing frames (each with a normalized pixel buffer + per-frame metadata), overall ImageMetadata, and the render input the pipeline needs. Decide the normalized pixel currency (evaluate SwiftPixel PixelBuffer, already used as the detection image) and document the choice.
  • Introduce a loader dispatch keyed on UTType (a registry / factory) so OpenFile and the loader select the right decoder; make FITSImageLoader the FITS conformer behind it.
  • Refactor ImageProcessor.render and FITSImageRenderer so the pipeline consumes the normalized representation rather than assuming FITS Data+BITPIX directly (keep FITS decode intact underneath).
  • Gate astronomy features on metadata availability (WCS present) so non-FITS formats can later reuse the pipeline without those features erroring.
  • Verify no FITS regression: existing FITScopeTests/ pass unchanged; add characterization tests around the new seam if coverage is thin.
  • Keep FITScope.xcodeproj in sync; build & run all tests via xcodebuild.
