Formats — Implementation Plan

Generated: 2026-07-06

Source: Docs/agent-plans/active/2026-07-06-formats/formats.html

Overview

FITScope today opens exactly one thing: a single two-dimensional FITS image (NAXIS=2). The whole model pipeline is FITS-typed (OpenFile → FITSImageLoader → FITSImage / FITSImageRenderer), ImageProcessor.render hard-rejects anything but NAXIS == 2, and the keyword Info window is bound to a FITS-specific metadata model. This plan extends the app to open additional FITS geometries (NAXIS=1 and NAXIS=3), the XISF format, and common photographic formats (TIFF, PNG, JPEG, RAW, HEIC).

The chosen approach is a format-agnostic abstraction: rather than bolting each format onto the FITS path, we first extract the shared pieces — a generalized metadata model behind the Info window, a format-neutral image/loader layer, and a multi-image carousel — then add each format as a conformer of that layer. Decoded pixels flow through the existing processing pipeline where it is meaningful (stretch, curves, histogram, and, where a WCS is present, overlays and plate solving), so non-FITS images are first-class rather than display-only. Work is sequenced FITS geometries first (they stay within SwiftFITS), then XISF, then the photographic formats.

Questions & answers

Which architecture should the plan target for adding non-FITS formats to a fully FITS-typed pipeline?
A format-agnostic abstraction — refactor into a shared loader/image/metadata layer that FITS and every new format conform to, giving one display path.
How much of the existing image-processing UI should apply to non-FITS formats (stretch, curves, histogram, overlays, plate solving, star detection)?
The full pipeline where meaningful — feed decoded pixels through the same processing pipeline as FITS. This requires access to pixel data, not just a CGImage. Astronomy-only features (plate solving, star detection, WCS overlays) apply only where a WCS/relevant metadata is present.
The backlog says to use "the SwiftXISF submodule available in SwiftAstro," but SwiftXISF is not currently a dependency of SwiftAstro nor linked into the app. How should the plan wire it in?
The user will make the necessary project/target modifications to include SwiftXISF. The plan therefore assumes SwiftXISF is importable from the app target and does not include a submodule-wiring milestone; the XISF milestone depends on that linkage being in place.
How should the formats be sequenced?
FITS geometries first (NAXIS=1, NAXIS=3 RGB, NAXIS=3 multiple), then XISF, then the photographic formats — with the shared foundations (metadata-model generalization and the carousel) extracted as early milestones regardless.

Notes

Key files & where format assumptions live (from a codebase survey):

  • FITScope/Image/ImageProcessor.swift — render(data:properties:settings:) hard-requires NAXIS == 2 (~line 216) before reading NAXIS1/NAXIS2; also BITPIX/BSCALE/BZERO decode and Bayer handling. Central blocker for NAXIS=1/3.
  • Submodules/SwiftAstro/SwiftAstro/Preprocessing/FITSImageDecoder.swift — linearImage(from:) / detectionImage(from:) also assume a 2D image (naxis(1)/naxis(2)).
  • FITScope/Image/FITSPreviewRenderer.swift — imageHDU(from:) selects a single first .data section; shared by the app render path and the QuickLook extensions.
  • FITScope/Model/FITS/ — FITSImageLoader, FITSImage, FITSImageRenderer (produces a CGImage plus a PixelBuffer detection image), FITSImageInfo/FITSImageSection/FITSImageProperty (the Codable, Hashable metadata model used as the InfoWindow value type), FITSMetadata typed accessors.
  • FITScope/Model/OpenFile.swift — @MainActor class per opened file, owns a FITSImageLoader; the natural seam for a format-neutral loader.
  • FITScope/Views/Information/InfoView.swift + InfoViewTable.swift — the keyword window; scene declared in FITScopeApp.swift as WindowGroup(id: "InfoWindow", for: FITSImageInfo.self). Its value type must stay Codable, Hashable.
  • FITScope/Views/Canvas/ImageCanvasView.swift + ZoomableImageView.swift — main display; consumes a CGImage. No carousel / multi-frame UI exists today.
  • Openable-type declarations: FITScope/Extensions/UTType.swift (UTType.fits), FITScope/Info.plist (UTImportedTypeDeclarations + CFBundleDocumentTypes, extensions fits/fit), FITSDocument.readableContentTypes = [.fits], AppModel.runOpenPanel() allowedContentTypes = [.fits], and Model/DropAcceptance.swift.
  • Swift Charts is already used (FITScope/Views/SessionMetrics/SessionMetricsChartView.swift) — the reference for the NAXIS=1 graph.
  • SwiftFITS (FITSSection.naxis(_:)) already supports arbitrary axis counts, so the parser is not the limitation — the app-side assumptions are.

Conventions to follow (from CLAUDE.md): one type per file, organized into subfolders; prefer let, no force-unwraps, no raw loops; explicit public/open in framework code; keep the .xcodeproj and any package manifests in sync; build and test via xcodebuild; add SwiftUI previews for every new view; document public and private members.

Assumptions & risks

  • The crux of the refactor is a normalized pixel representation that the processing pipeline (currently FITS Data + BITPIX properties) can consume from any format. SwiftPixel's PixelBuffer is already in the pipeline (as the detection image) and is the likely common currency. Getting this abstraction right without regressing FITS rendering/performance is the main risk (Milestone 2).
  • Regression safety: the FITS path must remain byte-for-byte behaviourally identical after the refactor. Existing tests under FITScopeTests/ are the guard rail; extend them as the abstraction lands.
  • Astronomy features (plate solving, star detection, WCS overlays, north/grid) are gated on the presence of the relevant metadata (WCS keywords). For photographic formats without a WCS these are simply unavailable, not errors — the UI should hide/disable them rather than fail.
  • QuickLook FITScopePreviewExtension/FITScopeThumbnailExtension currently serve FITS. macOS already provides QuickLook for TIFF/PNG/JPEG/HEIC/RAW natively, so extending the extensions is treated as out of scope here (a possible follow-up for XISF); the plan focuses on in-app opening.
  • NAXIS=1 is inherently a graph, not an image; the pixel-processing pipeline (stretch/curves/histogram) does not apply to it. It takes a distinct display branch.
  • SwiftXISF linkage into the app target is handled by the user; Milestone 7 depends on it being present.

Milestones

Phase 1 — Shared foundations

Milestone 1 — Generalize the metadata model & Info window

Completed

Depends on: nothing.

Goal: Decouple the keyword Info window from FITS so any format can supply grouped key/value metadata. Introduce a format-agnostic, Codable, Hashable metadata model (sections of properties) usable as the InfoWindow value type, and adapt the existing FITS metadata into it with no visible change to the FITS experience.

Tasks
  • Design a format-neutral metadata model (e.g. ImageMetadata → [ImageMetadataSection] → [ImageMetadataProperty]), Codable, Hashable, one type per file under Model/Metadata/ (or similar).
  • Make the existing FITS model (FITSImageInfo/FITSImageSection/FITSImageProperty) produce or conform to the generalized model (adapter or refactor), preserving current fields (name/kind/value/comment) and section titles.
  • Retarget InfoView/InfoViewTable/InfoViewTableCell and the WindowGroup(id: "InfoWindow", …) value type to the generalized model; keep search, section picker, keyword count, and CSV/TSV export working.
  • Update the three Info-window open sites (ImageCommands.swift, Sidebar/ImageInfoPanelView.swift, Controls/FileContextMenu.swift).
  • Add/adjust unit tests for the generalized model and the FITS adapter; add a SwiftUI preview for the retargeted InfoView.
  • Keep FITScope.xcodeproj in sync with any new files; build & run tests via xcodebuild.

Milestone 2 — Format-agnostic image & loader abstraction

Not started

Depends on: Milestone 1.

Goal: Introduce a format-neutral image/loader layer so OpenFile dispatches by type and every format produces a common result: one or more frames, each exposing a normalized pixel representation the processing pipeline can consume, plus generalized metadata. FITS becomes the first (and, at this milestone, only) conformer, with identical behaviour.

Tasks
  • Define the abstraction: a loaded-image protocol/type exposing frames (each with a normalized pixel buffer + per-frame metadata), overall ImageMetadata, and the render input the pipeline needs. Decide the normalized pixel currency (evaluate SwiftPixel PixelBuffer, already used as the detection image) and document the choice.
  • Introduce a loader dispatch keyed on UTType (a registry / factory) so OpenFile and the loader select the right decoder; make FITSImageLoader the FITS conformer behind it.
  • Refactor ImageProcessor.render and FITSImageRenderer so the pipeline consumes the normalized representation rather than assuming FITS Data+BITPIX directly (keep FITS decode intact underneath).
  • Gate astronomy features on metadata availability (WCS present) so non-FITS formats can later reuse the pipeline without those features erroring.
  • Verify no FITS regression: existing FITScopeTests/ pass unchanged; add characterization tests around the new seam if coverage is thin.
  • Keep FITScope.xcodeproj in sync; build & run all tests via xcodebuild.

Not started

Goal: Build a generic carousel/filmstrip UI, shown below the main image view, that lists the frames of the currently open image and lets the user select which one to display. Single-frame images (2D FITS, single-image formats) render exactly as today, with the carousel hidden or collapsed.

Goal: Open one-dimensional FITS data (NAXIS=1) and present it as a graph using Swift Charts instead of an image, adapting the chart to CTYPE1 when present and relevant to how the axis should be labelled/scaled.

  • Build a 1D graph view (under Views/…, modelled on SessionMetrics chart usage) with a preview; label/scale the axis from CTYPE1 (and related keywords) when present and relevant, with a sensible default otherwise.
  • Ensure the Info window still shows the header metadata for 1D files; hide image-only controls/overlays for this branch.
  • Add a 1D FITS test fixture and tests; keep FITScope.xcodeproj in sync; build & run tests via xcodebuild.

Milestone 5 — NAXIS=3 support (separate RGB channels)

Not started

Depends on: Milestone 2.

Goal: Open three-dimensional FITS data (NAXIS=3) whose third axis holds separate R, G, B planes, and combine them into a single color image. Require CTYPE1 and CTYPE2 to be present and validated, with no CTYPE3.

Tasks
  • Detect the RGB-planes case (NAXIS=3, third axis = 3, CTYPE1/CTYPE2 present & valid, no CTYPE3) and validate; reject other NAXIS=3 shapes here (handled by Milestone 6).
  • Decode the three planes and combine into a single color image, feeding the normalized representation so the processing pipeline (color-aware stretch/curves/histogram) applies.
  • Ensure color rendering, histogram (per-channel where applicable), and overlays behave correctly for a combined color image.
  • Add an RGB NAXIS=3 fixture and tests; keep FITScope.xcodeproj in sync; build & run tests via xcodebuild.

Phase 3 — XISF

Milestone 7 — XISF file support

Not started

Depends on: Milestones 1, 2, 3, and SwiftXISF being linked into the app target (handled by the user).

Goal: Open XISF files using the SwiftXISF module (ignoring its display function), decoding into the format-neutral image layer. Present XISF metadata (including its FITS keywords and properties) through the generalized Info window, and — since XISF files may contain multiple images — reuse the carousel from Milestone 3.

Tasks
  • Declare the XISF UTI/extension and register it: UTType extension, Info.plist (UTImportedTypeDeclarations + CFBundleDocumentTypes), FITSDocument.readableContentTypes (or its successor), AppModel.runOpenPanel() allowed types, and drop acceptance.

  • Map XISF metadata (XISFMetadata/XISFProperty/XISFFITSKeyword) into the generalized ImageMetadata for the Info window.
  • Expose multiple images as frames feeding the carousel; run the selected frame through the standard pipeline where meaningful.
  • Add an XISF fixture and tests; keep FITScope.xcodeproj in sync (given the user-provided SwiftXISF linkage); build & run tests via xcodebuild.
