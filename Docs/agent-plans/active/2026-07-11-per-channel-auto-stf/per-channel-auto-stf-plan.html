Per-Channel Auto-STF — Implementation Plan

Generated — 2026-07-11
Source — Docs/agent-plans/active/2026-07-11-per-channel-auto-stf/per-channel-auto-stf.html

The auto Screen Transfer is currently uniform (linked): it derives one shadows / midtones pair from the single-channel luminance detectionImage and applies it to every colour channel. On a colour-imbalanced frame the single shadow clip crushes the dimmest channel — measured at 41% of red clipped to pure black on a real Seestar S30 M42 light-pollution sub (6% green, 4% blue; unstretched min/max clips ~0%).

This plan makes the auto-STF per-channel (unlinked) for colour images — each channel derives and applies its own shadows / midtones, so each clips only its own darkest few percent — while keeping uniform (linked) as the default for mono and as a manual option. The per-channel derivation is produced once from the raw colour data the loaders already retain (the CFA mosaic deinterleaved by BAYERPAT, or the RGB planes) and is applied consistently on open, in the inspector's Auto, in the STF editor window's Auto, and in the QuickLook / Finder previews.

The apply path and parameter type already support per-channel — Processors.Stretch.STFParameters.perChannel, Channel.computed(median:mad:…) and the 3-channel computed(from:) were all built in the completed 2026-07-04-stf-stretch initiative — so this is a derivation-input and plumbing change, not new stretch maths.

Questions & answers

Didn't the STF plan already decide against per-channel Auto?

Only pragmatically. Milestone 6 shipped the uniform luminance derivation because the post-debayer RGB buffer exists only transiently at render time and per-channel Auto seemed to need a new SwiftPixel pass to expose it. That is avoidable: per-channel statistics can come from the raw mosaic (which the loaders retain) deinterleaved by CFA position, or from the RGB planes — no render-time buffer required. The plan's original intent was per-channel; the concrete 41% clipping now justifies finishing it.

Should per-channel be the default?

Yes for colour images; mono keeps uniform (it has a single channel). Uniform also stays available as a manual option.

Does the inspector's one-click Auto have to change too?

Yes — required, not optional. The whole point of the on-open / click-Auto reconciliation is that they agree, so if opening applies a per-channel STF the inspector Auto must produce the same.

What about the Auto button in the STF editor window?

It respects the window's per-channel toggle: in per-channel mode it derives and fills the three channels; in uniform mode it derives and fills a single set. "Auto fills whatever I'm currently editing" — and it gives a power user a colour-preserving uniform Auto on demand.

Do we keep uniform (linked) at all?

Yes. Mono has no other choice; linked STF preserves the true colour ratios (PixInsight ships both linked and unlinked); and it already exists as the manual uniform ↔ per-channel toggle in the editor.

Any behavioural consequence to accept?

Per-channel independently lifts each channel's background to the target, which neutralizes background colour casts on open — an automatic background colour balance. This is desirable and matches PixInsight's unlinked default, but it is a real appearance change from today's uniform default. Accepted.

Notes

  • One shared derivation, four consumers. On-open (linear loaders), the inspector Auto (ImageRenderer.autoScreenTransferSettings), the STF window Auto (STFEditorView), and the QuickLook / Finder previews must all produce the same result for a given image, so the per-channel derivation lives in one place and is reached through the ImageRenderSource abstraction. This preserves the "open == click Auto" guarantee the earlier work established.
  • Colour vs. mono is the switch. A colour source (CFA mosaic, RGB planes, or a colour photo) derives .perChannel(red:green:blue:); a single-channel source derives .uniform exactly as today. The decision is per-source, resolved once at derivation.
  • Derivation input (key implementation point). The per-channel statistics come from the colour data the loaders already hold, not from a render-time buffer. The recommended route is deinterleaving the CFA mosaic by BAYERPAT into R/G/B sample sets (unequal counts are fine — only per-channel median / MAD are needed) and calling Channel.computed(median:mad:…) per channel; RGB-plane and photographic sources use their channels directly (or the existing 3-channel computed(from:)). The alternative — building a 3-channel debayered detection buffer at load and reusing computed(from:) wholesale — is the fallback. Confirm the exact shape in Milestone 1.
  • Full-scale domain is unchanged. The STF still applies over Processors.Normalize.Mode.identity in the native full-scale [0, 1] domain; only the parameters become per-channel. The per-channel derivation runs over the same 1 / fullScale-scaled data the render applies the STF to, so parameters and render agree (as the uniform path already does).
  • Independent of the histogram fix. A separate change makes the histogram scale to its interior bins so clipping no longer flattens the plot; that correctly displays clipping. This plan reduces the clipping itself, and does not depend on it.
  • Conventions (repo working agreement). Prefer let; no force-unwrap; no raw loops; one type per file; add SwiftUI previews for new/changed views; document public and private members. Build and test through xcodebuild; keep FITScope.xcodeproj and the SwiftPixel / SwiftAstro projects in sync when files are added. The derivation entry points stay nonisolated / off-main-actor friendly, as today. Committing / pushing and submodule pointer updates are the maintainer's responsibility.

Appendix

Per-channel derivation (same maths, per channel)

For each channel c (from its own linear samples, in the full-scale [0, 1] domain):

  shadowClipFactor = 2.8     (default; user-tunable)
  targetBackground = 0.25    (default; user-tunable)

  s_c (shadows)  = clamp( median_c − shadowClipFactor · MAD_c, 0, 1 )
  h_c            = 1
  l_c, r_c       = 0, 1
  m0_c           = (median_c − s_c) / (1 − s_c)          (guard 1 − s_c ≠ 0)
  midtones_c     = mtf( m0_c, targetBackground )         (as in the STF core)

Colour → STFParameters.perChannel(red: c_R, green: c_G, blue: c_B)
Mono   → STFParameters.uniform(c)                        (unchanged)

Each channel clips only its own darkest tail, so an imbalanced channel is no longer crushed by a level derived from the (brighter) luminance.

CFA deinterleave by pattern

For a 2×2 BAYERPAT tile (e.g. GRBG), collect each channel's pixels by their tile position across the mosaic, then take each set's median / MAD. Green has two positions per tile; red and blue one each. Only per-channel statistics are needed, so the unequal sample counts are irrelevant — no demosaic and no co-location required.
