  1. Warn when no stars are detected

    Completed
    Goal

    Keep the "Show stars" overlay toggle visible even when detection finds nothing, and surface a warning so the user knows detection ran but found no stars — instead of the control silently disappearing.

    Tasks
    • Locate where the "Show stars" toggle visibility is gated on the star count (likely ImageCanvasView / toolbar / overlay model).
    • Keep the toggle visible when zero stars are detected; distinguish "not yet run" from "ran, found none".

    Completed2026-07-01
    Implementation notes

    Root cause: StarsOverlay.isAvailable was false and isLoading false once detection ran and found nothing, and stars aren't in alwaysOfferedOverlayIDs, so toolbarOverlays dropped the toggle. Also, starField is nil both before detection runs and after a fruitless run, so the two states were indistinguishable.

    Approach (confirmed with maintainer): a generic warning member on the overlay protocol rather than stars-specific code, matching the existing "the toolbar knows nothing overlay-specific" philosophy (as with isLoading).

    • CanvasOverlay: added var warning: String? with a protocol-extension default of nil. When non-nil, the toolbar keeps the toggle visible and, on tap, presents the message.
    • FITSImage: added @Published private(set) var hasDetectedStars, set to true in the detectStars() defer (so it also covers the detector-failure edge case where starField stays nil). This distinguishes "not yet run" from "ran, found none".
    • StarsOverlay: added a hasDetectedStars init parameter; warning returns a message only when detection has run, found no stars, and is not currently loading.
    • ImageCanvasView: passes hasDetectedStars into the overlay; toolbarOverlays now also keeps overlays with warning != nil; toggleOverlay presents an alert (title = overlay title, message = warning) when a warned, unavailable overlay is tapped — mirroring the existing plate-solve prompt. Added isOverlayWarningPresented/title/message state and a second .alert.
    • ImageToolbarButton: added an isWarning flag; preview gains a warning example.
    • Per review: replaced the whole-icon yellow tint with a small warning badge (exclamationmark.triangle.fill, multicolour, ~9pt) drawn on the icon's bottom-trailing corner, so the glyph keeps its normal appearance while still flagging the "found nothing" state. The active/accent tint logic is back to its original form.
    • ImageToolbarView: passes the warning through as the button's tooltip (overlay.warning ?? overlay.title) and sets isWarning.

    TDD: added StarsOverlay tests (no warning before detection; warns after a fruitless run; no warning when stars found; no warning while still loading) and a ReticleOverlay test for the protocol default of nil. All 19 tests in the two suites pass; the full app target builds.

    Review comments
    • Instead of tinting the whole icon yellow, add a small warning badge icon on top of the overlay's icon.
    • Position the warning badge at the bottom-right corner of the icon rather than the top-trailing corner.

  2. Overlays are laggy when resizing the window

    Completed
    Goal

    Make the canvas overlays (stars, objects, frame, scale bar) drawn by CanvasOverlayLayer redraw in step with the image during a window resize, so they stay registered to the displayed image without visible lag.

    Tasks
    • Investigate how CanvasOverlayLayer tracks the displayed image geometry and when it redraws relative to resize events.
    • Identify the source of lag (e.g. animation/implicit layer actions, layout timing, separate update path from the image).
    • Synchronize overlay redraw with the image during live resize (disable implicit CA animations if applicable; update on the same layout pass).
    • Verify overlays track smoothly while resizing at different zoom levels.
    Completed2026-07-01
    Implementation notes

    Not an implicit-CA-animation issue (the overlays are a SwiftUI Canvas, not a CALayer). Root cause: CanvasOverlayLayer draws from ImageCanvasView's displayedImageRect @State. ZoomableImageView.Coordinator.reportDisplayedImageRect() reads the rect synchronously from the AppKit scroll view but wrote it to SwiftUI via DispatchQueue.main.async — one run-loop turn late. During a live resize the AppKit image view redraws every frame, so the overlay's rect trailed it by a turn: the lag.

    Why the deferral existed (commit a176f8e): a synchronous write of observed state while the coordinator runs inside SwiftUI's update pass triggers "Publishing changes from within view updates". The cited case is switching files (image change → updateNSView → re-fit → report).

    Approach (chosen by maintainer — try the low-risk fix first, then check for warnings; fall back to AppKit-drawn overlays if the warning returns): added a deferred: Bool = true parameter to reportDisplayedImageRect(deferred:). The live AppKit-notification callers — clipBoundsChanged (resize) and magnificationChanged (pinch / scroll-wheel zoom), which fire outside the update pass — now report synchronously (deferred: false), so the overlays re-register in the same pass as the image. The update-pass callers (fit() from makeNSView/re-fit, apply(command:)) keep the deferred write, so the known file-switch warning path is unchanged.

    Verification status (honest): the app builds. I could not automate the runtime warning check here: driving a window resize needs Accessibility permission the terminal lacks, and open -a FITScope launched the installed /Applications release build rather than the debug build. This needs an interactive check: open a file, switch files, and resize the window at a few zoom levels while watching the Xcode console for "Publishing changes from within view updates" and confirming the overlays track the image. If the warning reappears, switch to the AppKit-drawn-overlay approach.

    Maintainer verified interactively: overlays track the image during resize and no "Publishing changes from within view updates" warning appeared, so the low-risk fix held and the AppKit fallback was not needed.

Phase 2Plate solving

  1. Close the plate-solve window when its image is closed

    Completed
    Goal

    Automatically dismiss any plate-solve window (PlateSolveWindowView / the PlateSolveWindow WindowGroup) opened for a file when that file is closed, instead of leaving it behind referencing a no-longer-open file.

    Tasks
    • Trace how the plate-solve window is keyed to an open file's ID and how files are closed.
    • On file close, dismiss the matching plate-solve window (e.g. via dismissWindow/window-id correlation, or by observing the file set).
    • Handle edge cases: multiple files, window already closed, solve in progress.
    • Verify closing the image reliably closes its plate-solve window.
    Completed2026-07-01
    Implementation notes

    How it's keyed: the results window is a WindowGroup( id: "PlateSolveWindow", for: OpenFile.ID.self ), and the live session lives in AppModel.plateSolveSessions[ file.id ]. Files close through a single choke point: WindowModel.close(_:) (trash(_:) funnels through it too). File IDs are unique per window (each window makes its own OpenFiles), so dismissing by file.id is unambiguous.

    • WindowModel: added an onFileClosed: ( ( OpenFile.ID ) -> Void )? callback (plain, not @Published) invoked at the end of close(_:) — the one choke point, so both Close and Move-to-Trash trigger it.
    • AppModel: added endPlateSolve( for: ) — cancels an in-flight solve (PlateSolveSession.cancel()) and removes the session; a no-op when there is no session. Also made beginPlateSolve take an injectable client (default live) so the teardown is unit-testable without network.
    • MainWindowView: owns the WindowModel and the dismissWindow environment action, so it wires model.onFileClosed (in onAppear, before any close) to appModel.endPlateSolve(for:) + dismissWindow(id: "PlateSolveWindow", value: id). The callback captures appModel/dismiss explicitly rather than the whole view.

    Edge cases: multiple files → keyed by unique id; window already closed → dismissWindow is a harmless no-op; solve in progress → the session is cancelled so a closed file wastes no more network. Design choice (flagged for review): closing a file both dismisses the window and ends its solve/session, rather than leaving the session around, since the file is gone.

    TDD: WindowModelTests.closingAFileNotifiesWithItsID (close fires the callback with the right id); AppModelTests — ending a solve with no session is a safe no-op, and ending one cancels + forgets the session (via a mock-transport client). All 378 unit tests pass; the app builds.

Phase 3Menus & sidebar

  1. Flesh out the Image menu

    Completed
    Goal

    Add the rest of the image actions to the Image menu (ImageCommands) so they are discoverable and keyboard-accessible, rather than living only in the floating canvas toolbar (ImageToolbarView).

    Tasks
    • Inventory the actions currently only in ImageToolbarView (zoom controls + overlay toggles).
    • Add zoom commands with standard shortcuts: Zoom In, Zoom Out, Actual Size (100%), Fit to Window, Recenter.
    • Add overlay toggles (e.g. "Show Stars") to the menu.
    • Share the underlying actions/state between toolbar and menu so both stay in sync; ensure correct enable/disable state.

    Completed2026-07-01
    Implementation notes

    Scope (clarified with maintainer): every action in the top floating toolbar — Recenter, Zoom Out, Zoom In, Fit to Window, Actual Size, and the overlay toggles (Plate Solve was already there) — is mirrored into the Image menu, kept in sync with the toolbar.

    Architecture. The blocker was that the zoom state, the one-shot CanvasCommand (with its token source) and enabledOverlays were private @State in ImageCanvasView, while the menu sits at scene level and can only reach the frontmost window through focused values. Introduced ImageCanvasController (an ObservableObject, new file FITScope/Views/Canvas/ImageCanvasController.swift) as the single source of truth for canvas interaction; both the toolbar and the menu drive it. ImageCanvasView owns it as @StateObject and publishes it with .focusedSceneObject(self.controller); ImageCommands reads it via @FocusedObject var canvas: ImageCanvasController?, exactly as FileCommands reaches the selected file — so items follow the key window and disable when no image is shown. (Two .focusedSceneObjects of different types now coexist: OpenFile from MainWindowView and ImageCanvasController from ImageCanvasView.)

    • Controller. @Published zoom / canZoomOut / command (private set) / enabledOverlays / overlay-alert state; zoom methods (fit/actualSize/recenter/zoomIn/zoomOut) issue distinct-token commands; overlayTapped(_:) holds the generic toggle-or-warn-or-call-to-action decision (moved verbatim out of the view), so the canvas stays free of overlay-specific knowledge — the pattern the maintainer settled on in M5.
    • Overlay mirror. The controller's overlays list is a plain (non-@Published) property, kept current by the view via .onChange(of: overlaySignature, initial: true) — a cheap string of each overlay's id/availability/warning — so it is never written mid-body (the "publishing changes from within view updates" hazard M2/M4 were careful about) and rebuilds only when a tap's outcome would change, not on unrelated renders like a rotation. The overlay set is structurally fixed, so the menu re-renders correctly off the published enabledOverlays (checkmarks) while tap decisions read the live mirror.
    • Menu items. Zoom items with ⌘+ (Zoom In), ⌘- (Zoom Out, also disabled when canZoomOut == false), ⌘0 (Actual Size), ⌘9 (Fit to Window), and Recenter (no shortcut); none collide with the existing ⌘⇧S/E/P/I / ⌘N/O. Overlay items are Toggles (native checkmark) whose binding ignores the new value and routes to canvas.overlayTapped, so a menu tap on an overlay with no data behaves exactly like its toolbar button (shows the warning alert, or proposes a plate solve). Existing "Plate Solve…" kept at the bottom.
    • Zoom keyboard shortcuts (review — keyboard-layout fix). SwiftUI's .keyboardShortcut matched ⌘+ but not ⌘- for the maintainer — and not even on a US layout — because SwiftUI matches by the produced character in a way that missed the minus key. The menu still displays the shortcuts, but the actual ⌘+ / ⌘- handling now lives in the AppKit ZoomingScrollView.performKeyEquivalent(with:) (the same view that does scroll-wheel zoom), matching the key by its character exactly as AppKit/Preview do — so it works on every layout, including the keypad +/-. Being deeper in the responder chain, it runs before the menu's equivalents, so the items never double-fire; the zoom change reports back through the existing bounds-change notifications, keeping the read-out and overlays in step.
    • View cleanup. Removed the view's zoom/canZoomOut/command/tokens/enabledOverlays/overlay-alert @State, its overlayTapped/presentOverlayAlert/send methods, and rewired the toolbar, ZoomableImageView callbacks, per-file overlay reset, and the overlay .alert onto the controller. requestPlateSolve/plateSolve (which need appModel/openWindow) stayed in the view and are wired into the overlays' onUnavailableTap as before.

    TDD: new ImageCanvasControllerTests (added to the FITScopeTests target via the xcodeproj gem, since the project uses explicit file references) — zoom methods issue their matching command kind; a repeated command bumps the token so the scroll view applies it again; an available overlay toggles on/off; an unavailable overlay with a warning raises the alert without enabling; one with a call to action runs it without alerting; an unknown id is a no-op. Watched them fail to compile (no ImageCanvasController) before writing it. All 388 unit tests pass; the app builds.

    Review round — more menu items. Per review, the menu now also carries the rest of the toolbar/inspector actions: Rotate Left / Right, Flip Horizontal / Vertical, Invert, Reset View, Levels…, Curves…, and View FITS Headers… (all file-targeted, gated on a loaded image via @FocusedObject var file: OpenFile?).

    • Shared model actions. Added action methods to FITSImage — rotateLeft/rotateRight/flipHorizontal/flipVertical, toggleInvert(), resetAdjustments() — so the menu drives the same model the inspector does. Rotate/flip just compose the orientation transform and re-render; Invert and Reset also bump a new @Published controlsRevision.
    • The inspector-sync problem, interim fix. The inspector controls cache their values in local @State, so a menu-driven Reset/Invert would otherwise leave them stale. InspectorView now keys its controls' identity off image.controlsRevision (replacing its private controlsID UUID), so a menu change recreates and reseeds them.     • Dedup + a fix. The 12-field reset that lived inline in InspectorView.reset() moved to a single ImageAdjustments.reset() that both the inspector button and the menu use. It copies from a fresh instance, so it can't omit a field — which surfaced that the old inline reset never reset debayerAlgorithm; the shared reset now does.   2. Sidebar sort button doesn't match the add button

    Completed
    Goal

    Make the sort control (the arrow.up.arrow.down menu) in the files sidebar header (FilesSidebarView) match the adjacent + add button: same icon size and same tint.

    Tasks
    • Compare the modifiers/styles applied to the add button vs. the sort menu in FilesSidebarView.
    • Align icon size (font/image scale) and tint between the two controls.
    • Verify the header controls look consistent in both light and dark appearance.
    Completed2026-07-01
    Implementation notes

    Root cause of the mismatch: the add button rendered with .buttonStyle( .borderless ), while the sort menu used .menuStyle( .borderlessButton ). Those are two different rendering paths: a borderless button tints its glyph with the accent color and sizes it as a plain image, whereas the borderless-button menu style draws its label through its own chrome — so the sort glyph read in a different tint and a slightly different size than the neighbouring +.

    Fix: switched the sort menu to .menuStyle( .button ) + .buttonStyle( .borderless ) so it adopts the same button style as the add button, giving both controls an identical icon size and tint. This mirrors the established in-repo pattern in HistogramControlView, where a Menu is made to match its neighbouring control via .menuStyle( .button ).buttonStyle( … ) rather than a bespoke style. .menuIndicator( .hidden ) and .fixedSize() were kept, so no disclosure chevron appears and the control stays sized to its glyph. One-line change; no new files, so no Xcode-project edits were needed.

    TDD note (honest): this milestone is a purely visual style tweak (icon size + tint). There is no logic to assert — the project's XCTest setup can't verify a rendered SwiftUI glyph's color or size — so no unit test was written; a hollow test would add nothing. Verification is the build plus an interactive visual check. The FITScope target builds clean via xcodebuild (Debug, macOS).

    Review round 1 — color still mismatched. Matching the button style fixed the size but not the tint: a borderless button tints its glyph with the accent color, but the Menu — even with .buttonStyle( .borderless ) — kept drawing its label in the default label/control color, so it didn't pick up that accent tint. Added an explicit .foregroundStyle( Color.accentColor ) to the sort menu. This did nothing (see review comment): .buttonStyle( .borderless ) imposes its own tint and ignores .foregroundStyle, so the override was silently dropped, and the menu label kept rendering a dimmer shade than the borderless +.

    Review round 2 — guaranteed match by unifying both controls. Rather than fight two different default tints, both controls now use the identical style so they can't diverge: .buttonStyle( .plain ) plus .foregroundStyle( .secondary ) on the add Button and on the sort Menu (the menu via .menuStyle( .button ).buttonStyle( .plain )). Unlike .borderless, the .plain style honours .foregroundStyle (this is exactly what HistogramControlView relies on), so both glyphs render in the same secondary shade at the same size. Rebuilt clean.

  1. Bring the open panel to front when reactivating the app

    Completed
    Goal

    When the modal Open panel (NSOpenPanel.runModal() in AppModel.runOpenPanel() and FilesSidebarView) is open and the app is sent to the background, reactivating the app should bring the panel back to the front rather than leaving it buried/unreachable. Consider Spaces support.

    Tasks
    • Reproduce the buried/unreachable panel behavior on app reactivation.
    • On activation, bring the open panel's window to front (and order the app front) while the modal session is active.
    • Consider Spaces behavior so activation behaves sensibly when the panel lives on another Space.
    • Verify reactivation reliably surfaces the panel.
    Completed2026-07-02
    Implementation notes

    Approach (chosen with maintainer): a single app-level handler rather than per-panel configuration. Both Open panels (AppModel.runOpenPanel() and FilesSidebarView.runOpenPanel()) and the Save panel run app-modal via runModal(), so the fix is generic and lives in AppDelegate, covering any modal window regardless of where it was created — no per-site duplication (matching the M5 preference for generic solutions over feature-specific code).

    • AppDelegate.applicationDidBecomeActive(_:): on reactivation, if NSApp.modalWindow is non-nil (a panel is up), surface it. When no panel is showing the guard makes it a no-op, so normal activations are unaffected.
    • AppDelegate.surface(_ window:) (static): inserts .moveToActiveSpace into the window's collectionBehavior (Spaces — the panel follows the user to whichever Space they return on) and calls orderFrontRegardless() (un-bury — brings it above other windows). insert is used rather than assignment so any existing behavior is preserved.

    Why the notification is delivered during runModal(): runModal() blocks the main thread but runs its own modal event loop that still processes app-activation events; NSApplication posts didBecomeActiveNotification synchronously, so the delegate method fires even while the modal session is running.

    TDD: added AppDelegateTests (new file, added to the FITScopeTests target via the xcodeproj gem, in the Application test group — the project uses explicit file references). Two tests on the pure, testable part — the surface(_:) side effect on collectionBehavior: surfacing a window adds .moveToActiveSpace; surfacing preserves an existing behavior (e.g. .fullScreenPrimary) while still adding it. Watched them fail to compile (no surface) before implementing. All 393 tests in 55 suites pass; the app builds.

    Verification status (honest): the unit-testable Spaces side effect is covered and the app builds, but I could not automate the true reactivation behavior — it needs a running app with real window ordering / a second Space, which a headless test can't exercise (orderFrontRegardless()'s effect and modal-window front-ordering aren't observable in a unit test). Needs an interactive check: open the Open panel (⌘O or the sidebar +), send the app to the background (⌘-Tab away, or click another app), then reactivate FITScope from the Dock — confirm the panel comes back to the front. Repeat with the panel opened on one Space and the app reactivated from another Space, confirming the panel follows to the active Space. If the panel still doesn't surface, the fallback is to also observe NSWindow.didBecomeKeyNotification/re-order on a timer, but the activation handler should suffice.

    Review round — de-duplicate the Open panel. There were two identical NSOpenPanel builders — AppModel.runOpenPanel() and a private one in FilesSidebarView. Consolidated to one: FilesSidebarView.runOpenPanel() now calls appModel.runOpenPanel() (already in its environment) and opens the returned URLs via model.open(urls:), so the panel is constructed in a single place (AppModel). No behavior change — same panel configuration, same result handling — and the app still builds with all 393 tests passing.

    Interactive check + investigation (honest outcome). The maintainer tested the launch case — run in Xcode, switch to another app while it opens — and the panel did not come to the front. A short diagnostic run (temporary NSLogs, since removed) established the facts:

    • The launch Open panel is presented from a DispatchQueue.main.async in applicationDidFinishLaunching while the app is in the background (isActive=false), so it is born behind the frontmost app.
    • applicationDidBecomeActive does fire and NSApp.modalWindow is the NSOpenPanel (a real in-process NSWindow), so surface(_:) runs on every activation — yet the panel stays buried. This is the sandbox: the app is sandboxed (com.apple.security.app-sandbox), so the panel's visible window is hosted out-of-process, and orderFrontRegardless() / collectionBehavior on the in-process proxy does not reorder the real remote panel. The surface(_:) approach is therefore ineffective for this panel.
    • Forcing the panel forward would require activating the app. The modern NSApplication.activate() is cooperative and deliberately will not steal focus — Apple's docs describe this exact scenario as intended ("the app remains unobtrusive if the user activates another app"). Truly forcing it needs the deprecated activate(ignoringOtherApps:) (deployment target is macOS 15.0).

    Decision (maintainer): leave it like this. Rather than fight the platform with a deprecated focus-stealing API, accept macOS's native cooperative activation for the launch panel. The temporary diagnostics were removed. The applicationDidBecomeActive + surface(_:) handler and its tests were kept as-is at the maintainer's direction. The concrete, working outcome of this milestone is the Open-panel de-duplication above. All 393 tests in 55 suites pass; the app builds.

    Review comments
    • The two Open panels should be a single one — consolidate the duplicated NSOpenPanel construction into one place.
    • Interactive test: launching in Xcode and switching to another app while it opens leaves the launch panel behind — it does not come to the front as the app opens.
    • After investigation showed the panel comes up while the app is backgrounded and the sandboxed out-of-process panel can't be reordered (forcing it needs a deprecated API): leave it like this — accept macOS's native cooperative activation, don't force focus.
    • Remove the temporary diagnostics. (Also: I removed the handler/tests unprompted during cleanup — corrected; only the diagnostics were meant to go.)
