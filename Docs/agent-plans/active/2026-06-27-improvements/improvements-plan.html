Overview

This plan turns the FITScope improvements list into small, independently reviewable and committable milestones. The 13 items span four areas: the rendering pipeline, the inspector's image-processing controls, the information panels (astronomy & metrics), and app integration (overlays, external apps, window chrome).

The overall approach follows the existing architecture rather than fighting it. New image adjustments (hue, colour balance) are added as first-class SwiftPixel processors and wired through the same ImageAdjustments → ImageProcessor.Settings → PixelPipeline.Config chain the other controls use. New astronomy (planets, sun, twilight) is added to the SwiftAstro library so it is reusable and lives beside star detection and SNR. Metrics work reuses the per-file StarField/SignalToNoise values already computed at load. Each milestone names the concrete files and types it touches, and keeps its own status, notes, and review fields so this document can be updated in place as work proceeds.

Questions & Answers

1. The astronomy math for “visible planets” and “sunrise/sunset + twilight” does not exist yet (SwiftAstro currently only does star detection + SNR). Where should planet-position and solar/twilight calculations live?
Extend the SwiftAstro submodule. Add planet ephemeris and solar-altitude/twilight computation to SwiftAstro as its natural, reusable home. Additionally, check whether the current local moon-phase computation should be moved into SwiftAstro for consistency, so all ephemeris lives in one place.
2. Star-detection results are currently shown only via the canvas overlay. How should the detection info (count, median FWHM/HFR, eccentricity) be presented?
A new “Stars” tab in the sidebar info tab view, alongside Info / Location / Moon / Weather. The overlay stays as-is.
3. Where should the session metric-trend charts (SNR / star count / FWHM·HFR across all open files, via Swift Charts) live?
A dedicated window, like the existing Info / Levels / Curves windows — it fits whole-session (window-level) data and gives the charts room.
4. The “Window toolbar?” item is phrased as an open investigation, and there is already a floating canvas toolbar plus a minimal window toolbar. How should the plan treat it?
An investigation milestone — a time-boxed spike that evaluates the idea and produces a recommendation (mockup/notes), with no committed UI.
5. Hue and colour-balance have no existing SwiftPixel processor (SwiftPixel is a submodule nested inside SwiftAstro). How should these be implemented?
Add new Processors.Hue and Processors.ColorBalance to SwiftPixel, consistent with the existing pipeline and reusable. This requires committing changes in the nested SwiftPixel submodule.

Notes

Context, conventions, assumptions, and risks gathered while mapping the codebase.

Architecture facts (verified)

  • Adjustments chain: controls bind to @Published fields on ImageAdjustments (Model/ImageAdjustments.swift) → snapshot as ImageProcessor.Settings (Image/ImageProcessor.swift) → PixelPipeline.Config → SwiftPixel. Re-renders are debounced (150 ms) via FITSImageRenderer.scheduleReRender(). Only a global reset() exists today.
  • Rendering concurrency: OpenFile.prepare(throttle:) acquires a FIFO RenderThrottle (limit ≈ cores−2), loads, renders, detects stars, releases. WindowModel.open(urls:) prepares all files equally — the selected file has no priority.
  • Before/after is cheap: both FITSImageRenderer.original and FITSImageRenderer.result CGImages already exist simultaneously.
  • SwiftPixel processors present: BrightnessContrast, CorrectGamma, Curves, Debayer, Invert, Levels, MonoToRGB, Normalize, Orient, Saturation, Scale, Stretch, WhiteBalance. No Hue, no ColorBalance — these must be added.
  • SwiftAstro provides: star detection (StarField: count, medianFWHM/HFR/eccentricity), SignalToNoise (robust MAD noise + weight), FITS decoding. No planet/sun/twilight ephemeris. Moon phase is computed locally in the app (Model/MoonPhase.swift).
  • Observer inputs come from FITS headers via FITSMetadata: coordinate (SITELAT/SITELONG), elevation (SITEELEV), observationDate (DATE-OBS, UTC).
  • Info sidebar tabs (Views/Sidebar/ImageInfoTabView.swift): Info / Location / Moon / Weather. Info rows are driven by ImageInformation + InfoField + user Preferences.infoPanelFields.
  • Overlay appearance is hardcoded in Views/Overlays/CanvasOverlayStyle.swift (alpha) and each overlay's private static let color/lineWidth.
  • Preferences: @Published + UserDefaults in Model/Preferences/Preferences.swift; tabs enumerated in Views/Preferences/PreferencesTab.swift and hosted by PreferencesView.
  • Export already exists: AppModel.saveCopy(of:) (original FITS bytes) and AppModel.exportImage(of:) (rendered CGImage → TIFF/PNG/JPEG via ImageExporter). Commands use @FocusedObject; the current file is OpenFile.url.
  • Swift Charts is not yet used anywhere.

Conventions to follow

  • Xcode project + submodules stay in sync. New source files must be added to FITScope.xcodeproj; new SwiftPixel/SwiftAstro files must be added to their own .xcodeproj and Package.swift. Build and run tests through xcodebuild.
  • Submodule work is upstream-first. SwiftPixel and SwiftAstro changes are committed in those repos, then the submodule pointer is bumped in FITScope. Coordinate ordering: library change → build/tests → app wiring.
  • One type per file; add SwiftUI previews for new views; extract reusable components rather than growing long views; no force-unwrap; prefer let; explicit public for library (SwiftPixel/SwiftAstro) API.
  • Add unit tests where there is logic to test: new SwiftPixel processors (SwiftPixel tests), astronomy math (SwiftAstro tests), and app-side model/formatting (FITScopeTests).

Assumptions (default choices — flag in review if you disagree)

  • Before/after (M5): a wipe-style comparison with a draggable vertical divider over the image (original on one side, processed on the other), rather than a whole-image opacity blend. Alternative noted in the milestone.
  • Per-control reset (M2): a small, consistent reset affordance shown per control when its value differs from the default; clicking resets that single field and re-renders. Implemented once as a reusable component and reused across controls.
  • Open With (M13): original opens from OpenFile.url; the processed image is written to a temporary lossless TIFF (via the existing ImageExporter) then handed to NSWorkspace. The menu lists candidate apps via NSWorkspace.urlsForApplications(toOpen:) plus an “Open With Other…” entry.
  • Sky-quality (M10): source the read-out from the robust background/noise already available (SignalToNoise.noise and/or HistogramStatistics median & MAD); a small verification step confirms whether the star detector exposes an explicit background estimate before choosing the exact source.
  • Sun/twilight & planets placement (M7/M8): a new “Sky” sidebar tab hosting both observation-time sun/twilight and visible planets, keeping the existing Moon/Location/Weather tabs untouched. May instead extend the Location tab — open for review.

Risks & open points

  • Ephemeris scope & accuracy. Planet and solar positions need a defined accuracy target. For a viewer, low-precision analytic series (arc-minute-level) are sufficient and dependency-free; this should be confirmed when designing the SwiftAstro API (M6).
  • Submodule commit coordination. Several milestones require a SwiftPixel or SwiftAstro commit before the app can build against the new API. Each such milestone flags the upstream step explicitly.
  • “Visible planets by letter.” Interpreted as planets above the horizon at the observation time/location, labelled by a short symbol/abbreviation. The exact labelling (single letter vs. abbreviation vs. glyph) is a small UI decision inside M8.

M1Prioritize the selected file for rendering

Completed

When a file is selected, its load/render should take priority so the image on screen is processed first, instead of waiting behind others in FIFO order.

Tasks
  • Review current ordering: WindowModel.open(urls:), OpenFile.prepare(throttle:), and the FIFO RenderThrottle (Model/RenderThrottle.swift).
  • Introduce priority into acquisition — e.g. a priority-aware waiter queue in RenderThrottle, or a fast path that lets the selected file bypass/jump the queue.
  • Signal priority on selection change: observe WindowModel.selectedFileID and bump the selected OpenFile's pending preparation/render to the front.
  • Ensure correctness: no starvation of background files, generation guards still respected, cancellation still works, no priority inversion when the selected file is already prepared.
  • Also consider re-selection while a batch is still preparing (rapid arrow-key navigation).
  • Verify with a multi-file open that selecting a not-yet-rendered file renders it ahead of the rest.
Status: CompletedCompleted: 2026-07-04
Implementation notes
  • Approach: a priority-aware, keyed RenderThrottle, chosen over a “bypass the queue” fast path so the concurrency limit (the CPU/memory guard the throttle exists for) is never exceeded.
  • RenderThrottle: acquire(key:priority:) keeps the old keyless/normal call working, so existing tests and call sites are untouched. Each waiter carries an optional promotion stamp plus a FIFO ticket. release() serves the most-recently-promoted waiter, otherwise the earliest unpromoted one (FIFO). prioritize(key:) stamps a fresh promotion on a still-waiting acquirer; it is a no-op when no waiter carries the key — already acquired, finished, or not yet suspended — so there is no priority inversion.
  • Rapid re-selection (task 5): chose most-recently-promoted wins over a plain high/normal flag. Plain FIFO-among-high would render the first-navigated file first; with promotion stamps, holding an arrow key promotes each file passed through but the file finally on screen (latest promotion) is served first. Covered by repromotingServesTheMostRecentlyPromotedWaiterFirst. Promotions are one-off per selection, so background files are not starved.
  • OpenFile.prepare(throttle:priority:): passes the file’s id as the throttle key and its initial priority; the selected file starts .high.
  • WindowModel: the throttle is now injected through an internal designated init (a public convenience init() preserves the production core-count sizing), which made the wiring deterministically testable without a mock. It observes $selectedFileID and calls prioritize(key:) on change, and open(urls:) adopts the selection before preparing so the selected file starts at high priority.
  • TDD: tests were written first and watched fail (stubbed no-op, then the FIFO-among-high gap) before implementing. Suite covers throttle ordering (prioritized-beats-earlier-normal, high-acquire-beats-normal, unmatched-prioritize keeps FIFO, most-recently-promoted wins) and the WindowModel selection→prioritize wiring. Full suite: 416 tests pass.
  • Not automated: task 6’s live multi-file visual check (selecting a not-yet-rendered file renders it ahead of the rest) — the mechanism is unit-tested, but the on-screen behaviour is left for manual verification.

Status: CompletedCompleted: 2026-07-04
Implementation notes
  • Plan premise corrected (task 1): the plan claimed both original and result CGImages already exist. They do not — FITSImageRenderer.original is a HistogramSet (histogram + statistics only); the original CGImage is rendered once for the histogram and then discarded. So a source for the “before” image had to be added. Good news confirmed while investigating: the default ImageAdjustments() is “the file as captured” (linear min/max normalize, no stretch/gamma/WB), so the “before” is a meaningful, visible image (the captured view), not a black frame.
  • Before-image source (your call): chose lazy + cache per file. The before image is rendered only when the comparison is first entered and then cached for the file’s lifetime, so memory grows only for files actually compared and repeat toggles have no delay.
  • Orientation registration: the before must match the processed result’s orientation or a rotated/flipped image would not register pixel-for-pixel (a 90° rotation even swaps width/height). So the before is rendered with all adjustments at their defaults except the current orientation, and the cache is keyed by orientation — it re-renders only when the orientation changes (rare), reusing the cache otherwise.
  • Renderer (TDD): added @Published originalImage: CGImage?, a private originalImageOrientation, and prepareOriginalImage() (renders default-settings-at-current-orientation off the main actor, caches, no-ops when the cache matches). Three tests written first and watched fail: the before image is nil until prepared, is cached and reused at the same orientation, and re-renders with swapped dimensions on a 90° rotation.
  • Controller (TDD): added @Published isComparing, @Published private(set) comparisonFraction (the divider position, clamped to 0…1), toggleComparison() (recentres the divider to 0.5 on entry) and setComparisonFraction(_:). Three tests written first and watched fail: toggling on/off, re-entering recentres the divider, and the fraction clamps to the unit range.
  • Wipe layer: new Views/Canvas/ImageComparisonLayer.swift. It draws the before CGImage into the same on-screen rectangle the result occupies (displayedImageRect, already reported by ZoomableImageView for the annotation overlays), clipped to the region left of the divider. Because both images share that rectangle and the same orientation, they stay registered under zoom/pan/rotate/flip for free — the “after” is the canvas underneath, and only the left of the divider is overpainted with the before. A full-height grab handle strip is the only interactive part (rest is hit-test transparent, so panning still works); dragging it reports a new fraction through the controller’s clamp. Corner “Before”/“After” labels. Includes a #Preview with a synthetic gradient standing in for the before over a colour background standing in for the after.
  • Divider assumption (per plan): implemented the wipe divider the plan assumed, not an opacity blend. The divider is screen-space (a fraction of the viewport width), the standard before/after slider UX; the opacity-blend alternative was not built (the plan flags it as a review swap).
  • Canvas wiring: the comparison overlay is shown only when comparing and the before image is ready and its dimensions match the result’s (guarding the brief window while a rotation re-renders the before). prepareOriginalImage() is triggered when the comparison is entered and when the result’s orientation changes while comparing. Comparison is reset off when switching files (alongside the overlay reset).
  • Toggle placement: a compare button in the floating ImageToolbarView (icon rectangle.split.2x1, tinted when active, its own section after Actual Size) and a “Compare Before/After” toggle in the Image menu (after Recenter), both driving the same controller state — mirroring how the overlays are exposed in both places. New accessibility identifiers ImageToolbarView.compare and ImageComparisonLayer.divider.

Implementation notes
  • Approach (your calls): low-precision analytic ephemeris (dependency-free), and the app’s moon-phase computation moved into SwiftAstro. All new code lives in a new SwiftAstro/Ephemeris/ group.
  • Method & accuracy: after Paul Schlyter’s “Computing planetary positions” (arc-minute-class for the Sun and inner planets, a fraction of a degree for Jupiter/Saturn) — ample for a viewer, and dependency-free. All angles are degrees at the API; trig is done in radians internally.
  • Public API: value types GeographicLocation (lat/lon°), EquatorialCoordinate (RA/Dec°), HorizontalCoordinate (az/alt° + isAboveHorizon); SolarPosition.position(at:) / .horizontal(at:location:); Planet (Mercury–Saturn) + PlanetPosition.position(of:at:) / .horizontal(of:at:location:); TwilightEvents.compute(date:location:) returning sunrise/sunset and civil/nautical/astronomical dawn & dusk as Date? (nil for polar day/night); and the moved MoonPhase. Internal Ephemeris (day number, sidereal time, obliquity, ecliptic→equatorial→horizontal) and OrbitalElements (Kepler solve → heliocentric) are the shared workhorses.
  • Validation against authoritative reference values: pulled Schlyter’s formulas and his fully worked example (1990-04-19 00:00 UT, d = −3543). Tests assert the day number, sidereal time (GMST0 13.78925 h, LST 14.78925 h), the Sun’s RA/Dec (26.6580° / +11.0084°) and alt/az (15.68° / −17.96° at 60°N/15°E), and the heliocentric lon/lat/r of Mercury/Venus/Mars — all match. Geocentric planets are validated by a reference-free invariant (Venus never >48.5° and Mercury never >28.5° from the Sun — their real maximum elongations). Twilight is validated by self-consistency: the Sun’s altitude (from the independently-validated SolarPosition) at each returned event equals that event’s threshold, the events are correctly ordered through the day, and polar day (80°N solstice: no sunrise/sunset) and deep polar night (88°N: nothing at all) behave correctly.
  • MoonPhase move (task 4): the computation and Phase (with its human-readable name) moved to SwiftAstro/Ephemeris/MoonPhase.swift, with its computation tests. The SF Symbol names are kept app-side as MoonPhaseSymbol.swift (extension MoonPhase.Phase), so the library stays UI-free. MoonPhaseView and ImageInfoTabView now import SwiftAstro; the app-side test now covers only the symbol mapping. Behaviour is unchanged. (Cross-module note: the symbol switch needed an @unknown default now that Phase is a public enum in another module — falls back to the generic "moon" symbol.)

The core+Sun foundation was implemented and then immediately validated against those reference values, rather than strict red-first — the reference values, not a stubbed failure, are what proves correctness here. The controller/renderer-style compile-fail red doesn’t apply to a self-contained math port. Each layer (Sun, planets, twilight) was validated before building the next on top.

UI tests were not run, per your standing request — and M6 adds no UI (M7/M8 will surface it).
