Detection Image

Generated — 2026-07-20
Scope — extract the detection-image construction and its underlying pixel decoding from FITScope into SwiftAstro
Nature — design document; the milestone plan is derived from this separately.

FITScope builds a detection-ready, single-channel linear image at load time and hands it to SwiftAstro for star detection and the sky-background measurement. The recipe that produces that buffer — decode the file's samples, apply the format's linear scaling, demosaic a colour-filter array to luminance — lives entirely in the app, and SwiftAstro's own tests re-implement it by hand. This document specifies moving the decoding and the detection-image construction into SwiftAstro, so the app and the library's tests share one implementation.

Motivation

Four format loaders in the app each carry a private detectionImage(…) that applies the same recipe:

LoaderDecode stepThen
FITSImageLoader.swift:354 ImageProcessor.linearImage / rgbLinearLuminance wrap in PixelBuffer, then BayerGrayscaleConverter when BAYERPAT is present
XISFImageLoader.swift:285 ImageProcessor.xisfLinearLuminance same
RAWImageLoader.swift:317 ImageProcessor.rawImageLinearLuminance same
ImageIOImageLoader.swift:354 ImageProcessor.imageIOLinearLuminance no CFA step (photographic sources carry no mosaic)

On the library side, SwiftAstroTests/Helpers/FITSTestImage.swift:259-372 is a hand-written re-implementation of the FITS decode and the BAYERPAT mapping. Its own documentation calls it “a test-only reimplementation of the FITS→buffer adapter the library no longer ships”. A second, independent copy of the same algorithm exists for image-HDU selection: FITSPreviewRenderer.imageHDU(from:) (FITScope/Image/FITSPreviewRenderer.swift:49) and FITSTestImage.imageHDU(in:) (:344) implement the same rule — first .data section, paired with the section before it — independently.

The consequence is that SwiftAstro's real-frame validation tests and its decode benchmarks assert against frames decoded by code the app never runs. A change to how FITScope interprets a header (scaling, blank masking, HDU choice, Bayer phase) does not reach the library's tests, and a change in the library's test decoder does not reflect the app. That is the divergence this design removes.

There is also a duplication inside the app that the extraction exposes: ImageProcessor.render(data:properties:) (ImageProcessor+FITS.swift:62-145) hand-rolls a decode that duplicates linearImage (:384) and decodedImageHDU (:189), differing only in throwing rather than returning nil.

Prior decision this revisits

Commit c0ac847 (SwiftAstro, 2026-07-19) removed the public FITSImageDecoder on the grounds that it had degenerated into test-support scaffolding: “the FITScope app now decodes FITS itself, so the type's sole remaining users were SwiftAstro's own real-frame validation tests and the decode benchmark.” That reasoning was sound for what the type had become. This design reinstates the name with the opposite property: the app calls it in production, and it is the only decode path either side uses. Any commit reinstating the type should say so explicitly, so the change is not read as an accidental revert.

Decisions

Boundary
Decode and detection assembly both move, along with the Sendable property-snapshot types.

Sharing only the thin luminance→demosaic step would not achieve the goal: the part FITSTestImage duplicates is the header→samples decode (BITPIX, BZERO/BSCALE, BLANK, block-padding trim).

Formats
All four — FITS, XISF, RAW and photographic (ImageIO).

No format keeps an app-side duplicate. Requires adding SwiftXISF and SwiftRAW to SwiftAstro's package dependencies; the photographic path needs no new dependency, as its properties type is Foundation-only and the CGImage draw stays app-side.

API shape
Per-format decoder namespaces, one type per file.

Keeps the linear decoders public so the app's render path reuses the same decode. A protocol (DetectionImageSource) was considered and rejected: the polymorphic abstraction over formats already exists app-side as ImageRenderSource, so a second one would have no consumer; and a computed var detectionImage would invite recomputing a full decode plus demosaic of a multi-megapixel frame on every access, where the app deliberately stores it once at load time.

HDU selection
Moves into FITSImageDecoder.

It decides which HDU is decoded at all, so leaving it behind would leave the second drift point open. It stops short of file parsing: FITSFile construction, and the .lenient option choice, stay with the caller.

Test ownership
Decode tests move to SwiftAstroTests, which grows its own minimal fixture builders.

A shared test-support target was considered but rejected as scope creep. The residual duplication is acceptable because it is only in fixtures: once the decoder is shared, a drifting fixture means a different input, not different behaviour. SwiftAstro's copy covers only the shapes its decode tests need — not a port of all 340 lines of FITSTestData.

Call sites
All updated; no forwarding shims on ImageProcessor.

Shims would leave two names for every operation and a facade suggesting the app still owns the decode — the exact confusion this change removes. The edit is mechanical and compiler-verified: delete the method, fix what breaks. Roughly 103 sites (49 in the app, 36 in its tests, 18 internal to ImageProcessor+FITS), sequenced per format.

The xisf / raw / imageIO method prefixes disappear: they exist only to disambiguate within the single ImageProcessor namespace. ImageProcessor.xisfLinearLuminance becomes XISFImageDecoder.linearLuminance.

The photographic decoder is named for what it decodes rather than for the framework the app used to produce its bytes: ImageIO parsing itself stays app-side (the CGImage draw belongs to the loader), and what moves is the decode of a canonical interleaved bitmap described by BitmapImageProperties. This keeps ImageIO out of SwiftAstro's vocabulary entirely.

Sketch

public enum FITSImageDecoder
{
    public static func imageHDU( from sections: [ FITSSection ] ) throws
        -> ( data: Data, properties: [ FITSPropertySnapshot ] )

    public static func linearImage( data: Data, properties: [ FITSPropertySnapshot ] )
        -> ( width: Int, height: Int, samples: [ Double ] )?

    public static func detectionImage( data: Data, properties: [ FITSPropertySnapshot ] )
        -> PixelBuffer?
}

What stays in the app

ImageProcessor keeps everything presentation-side: Settings, DebayerSelection, AutoStretchColorSource / AutoStretchDomain, all PixelPipeline.Config building, all render(…), all *PixelValues / rawPixelValue read-out and their private sampleValue / decodeSample helpers, previewBinFactor, PixelValue, RenderResult, and the whole auto Screen Transfer derivation.

ImageRenderSource and the four render sources keep their current shape. The protocol still exposes detectionImage as a stored property; only its producer changes. The seam is therefore: decoding and header interpretation belong to SwiftAstro; rendering and presentation belong to the app.

Dependency and project changes

  • Package.swift — add SwiftXISF and SwiftRAW to both the SwiftAstro target and SwiftAstroTests.
  • SwiftAstro.xcodeproj — this is a pre-existing inconsistency to repair, not merely an addition. The project already lists SwiftXISF.framework and SwiftRAW.framework in both targets' Frameworks phases (project.pbxproj:268-280) as BUILT_PRODUCTS_DIR references, but there are no corresponding subproject file references — only SwiftPixel and SwiftFITS have those (:242-243, :770-774). SwiftAstro therefore links them only by virtue of being built inside the FITScope workspace, and swift build never sees them. Proper subproject references and target dependencies are needed.
  • FITScope.xcodeproj — remove the moved files from the FITScope target. No new subproject references are required; the app already embeds all five (:1122-1126).

Both the Xcode projects and Package.swift must stay in sync, and each milestone must build through xcodebuild as well as swift build.

Error types

The throwing helpers currently raise RuntimeError, which lives in SwiftUtilities — a FITScope-level submodule SwiftAstro cannot reach. The moved helpers must therefore throw SwiftAstro.Error. This was verified as safe: no caller inspects the error type (all use try? or propagate), and the single test that asserts a throw checks only (any Error).self (FITScopeTests/Image/ImageProcessorTests.swift:694-695).

Test changes

  • FITSTestImage loses linearImage(header:data:), imageHDU(in:), pattern(forBayerKeyword:) and numericValue(of:) — roughly :259-388 collapses into calls to FITSImageDecoder. It keeps what it exists for: fixture location (url(resource:)), the named-frame accessors, and crop.
  • The decode assertions move from FITScopeTests/Image/ImageProcessor*Tests.swift into SwiftAstroTests/Preprocessing/Decoding/. The moving surface is currently exercised at roughly 35 call sites: isRGBPlanes (9), isMultiImageCube (8), debayerPattern (6), scaling (2), linearImage (2), and one each for cubePlanes, decodedImageHDU, fullScale, rgbLinearLuminance, xisfPlaneSamples, xisfLinearLuminance, rawImageLinearLuminance and imageIOLinearLuminance.
  • SwiftAstroTests gains a minimal FITS byte-synthesis fixture builder covering only the shapes those tests need — a gradient, RGB planes, and a multi-image cube.
  • FITScopeTests keeps FITSTestData for the render, loader, graph and view tests that still depend on it (10 files use it today).

Sequencing

One format per milestone, so no single change is oversized. Each milestone is self-contained: move the property type and its decoder, update every call site, move the tests, and leave both suites green under xcodebuild and swift build.

M1 FITS

First, because it carries the actual drift, plus image-HDU selection and the Bayer keyword mapping that the other formats also reach for. Largest single milestone.

M2 XISF

Adds SwiftXISF to SwiftAstro's package dependencies and repairs the xcodeproj subproject reference.

M3 RAW

Adds SwiftRAW likewise. The LibRAW-backed crop stays app-side; only the cropped mosaic's decode moves.

M4 Bitmap (photographic)

Includes the ImageIOImageProperties → BitmapImageProperties rename. No new dependency.

Risks

Rename churn for no functional gain

ImageIOImageProperties → BitmapImageProperties touches 8 app files for a naming reason alone. Reversible if it is judged not worth the diff; the rest of M4 does not depend on it.

SwiftAstro grows two dependencies

Any future non-FITScope consumer pulls SwiftXISF and SwiftRAW — and LibRAW behind the latter — whether it needs them or not. Splitting SwiftAstro into separate library products would avoid this but adds targets; deferred until a second consumer exists.

SwiftPM may surface pre-existing breakage

Because Package.swift has never declared SwiftXISF or SwiftRAW, wiring them in could expose problems the Xcode-only build path has been masking. Encountered at M2/M3.

Large mechanical diff

Roughly 103 call sites move. The change is compiler-verified rather than subtle, but the per-format sequencing exists specifically to keep any one review tractable.

Out of scope

  • Collapsing ImageProcessor.render(data:properties:)'s inline decode onto the shared decoder. The duplication is noted above and is worth doing, but it is an app-internal cleanup independent of the extraction.
  • Moving FITSFile parsing or the .lenient option choice into SwiftAstro.
  • Any change to the star detector, the sky-background estimator, or the auto Screen Transfer derivation. The detection image's contents must be byte-identical before and after.
