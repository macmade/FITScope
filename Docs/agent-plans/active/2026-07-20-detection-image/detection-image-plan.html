Milestones — 9, in three phases

Overview

SwiftAstro's star-detection and sky-background tests validate against detection images built by a private, test-only decode (SwiftAstroTests/Helpers/FITSTestImage.swift:232-374), while FITScope builds its detection images from four entirely separate private detectionImage(…) methods over ImageProcessor's decode surface. The two agree only by coincidence. The consequence — not the duplication itself — is that a green SwiftAstro suite is no evidence the app's star detection works. This plan removes that by giving both sides exactly one way to obtain a detection image.

The approach follows the source document's sequencing. One shared decoder API is designed first, for all four formats at once, and lands as compiling stubs in SwiftAstro before any format is implemented (M1). A golden digest of every detection image the app produces today is captured before anything moves, so byte-identity is checkable rather than aspirational (M2). The test fixtures are then reorganised along the new boundary (M3). Each format is migrated in one milestone — implement the decoder in SwiftAstro, switch the app onto it, delete the app's copies, verify the digests — in the order FITS, XISF, RAW, photographic (M4–M7). A symmetry check (M8) verifies no format was left with a partial surface, and a cleanup milestone (M9) collapses the last in-app decode, removes the golden scaffolding and confirms the seam.

The guiding principle throughout is the source document's: anything that can change the detection image's bytes moves; everything else stays in the app. Two corollaries bound it — nothing that exists because FITScope has a user interface goes into SwiftAstro, and the outcome is one public API in which every format offers the same operations, not four independent migrations.

Questions & answers

Moving all 14 captures adds ~232 MB to SwiftAstro's git history (its Test Files/ is 31 MB today). Only C6-R7-M42-Light.cr3 is referenced by any test; the five *-Final.jpg processed references (~43 MB) are referenced by nothing. How should the captures move?

All 14, plain git — as the design document specifies. SwiftAstro's Test Files/ goes to ~263 MB. No Git LFS: the submodule is consumed by path from FITScope and would gain a tooling dependency for no functional benefit.

What form should the “golden digest” scaffolding take?

Temporary test plus a committed JSON — a suite in FITScopeTests that walks every fixture and capture through the current app path, hashes each detection image, and asserts against a committed digest file. It runs in CI on every milestone, so drift surfaces the moment it appears, and is deleted in M9.

How finely should each format be split into milestones?

One milestone per format — add, switch and delete together, matching the source document's sequencing list one-for-one. The short-lived duplication a format needs while its decoder lands never appears in a committed state. Each format milestone is consequently a large diff, and needs a SwiftAstro commit before the superproject commit.

The plan review found an asymmetry the design document does not mention: FITSImageLoader.multiImageFrameSources (FITSImageLoader.swift:401-422) builds each cube plane's detection image from linearImage alone and never demosaics, while the single-frame path (:380-386) does. A CFA cube therefore feeds a raw mosaic to star detection today, and a uniform shared detectionImage would change its bytes.

Fix it, and record it as intended drift — the shared path demosaics uniformly, including cube planes. Any affected golden digest is re-baselined with a written rationale rather than silently accommodated. Tracked as a task and a note in M4.

SwiftAstro.xcodeproj already links and embeds SwiftXISF.framework and SwiftRAW.framework, but Package.swift still lists only SwiftPixel and SwiftFITS, so swift build and xcodebuild disagree. Who wires that up?

The dependency wiring is manual and stays out of scope; it is a precondition of M1. The plan does own adding each new decoder source file to SwiftAstro.xcodeproj, and verifies both build systems in every milestone that adds files.

The design document names the photographic decoder BitmapImageDecoder / BitmapImageProperties; app-side the type is ImageIOImageProperties, used by four app types and their tests. How far does the rename travel?

The app's decode-facing types are renamed too — ImageIORenderSource → BitmapRenderSource and ImageIODecodedRenderSource → BitmapDecodedRenderSource, so the vocabulary is consistent on both sides of the boundary. ImageIOImageLoader keeps its name: it really is the loader that opens files with ImageIO.

What should the “API design” milestone actually deliver?

Compiling stubs in SwiftAstro — all four decoder namespaces with full signatures and doc comments, bodies throwing or returning nothing, plus a symmetry test asserting every format exposes the same operations. The shape is reviewable as real Swift, and the format milestones only fill bodies.

fullScale is the format's span, applied after BZERO/BSCALE — not a bug. fullScale( for: ) (ImageProcessor+FITS.swift:882-893) returns 2N − 1 for every integer case: 255, 65535, 4294967295. It divides the scaled sample, not the raw one — scaled = raw · scale + offset at :820, then scaled / fullScale at :821.

That is the FITS unsigned-integer convention: FITS has no unsigned 16- or 32-bit BITPIX, so unsigned data is stored signed with a compensating BZERO (32768 for BITPIX 16, 2147483648 for BITPIX 32), putting the scaled range back at 0…65535 and 0…4294967295 respectively. The 32-bit value is exactly as correct as the 16-bit one, and it deliberately matches xisfFullScale (ImageProcessor+XISF.swift:472-474), as fullScaleScaling's own doc comment states (:918).

Carry all three values across verbatim. The only imprecision — that genuinely signed data (BZERO = 0) yields a fraction spanning roughly −0.5…+0.5 — applies uniformly to .int16 and .int32 alike, and is a property of the span convention rather than a defect in one case.

Working agreement for this initiative

  • No commits are made by the agent. Each milestone ends with the work staged for review; the commits are the human's. Where a milestone touches both repositories, the SwiftAstro commit must precede the superproject commit that bumps the submodule pointer.
  • Every new SwiftAstro source file is added to SwiftAstro.xcodeproj in the same milestone that creates it — SwiftPM globs the path, Xcode does not. Commits da2af01 and 7470840 show this is a routine follow-up in this repository; here it is part of the milestone, not a follow-up.

  • No test is disabled, skipped or deleted to make a milestone pass. If the shared path shifts an assertion in RealFrameValidationTests or the benchmark, that is the drift this work exists to find: it is reported and decided on its merits.
  • Verification per milestone: full test plan via xcodebuild test -project FITScope.xcodeproj -scheme "FITScope - Debug" (the scheme references FITScope.xctestplan, which runs all eight targets), plus swift build in Submodules/SwiftAstro to keep SwiftPM honest, plus the golden digest suite from M2.

Conventions the new code follows

  • One type per file; decoders and their property types live under SwiftAstro/Preprocessing/Decoding/.
  • Explicit public on everything a consumer needs — SwiftAstro is a framework target, and the design document is emphatic that the decode is public, not a concealed core.
  • Doc comments on every type and member, private ones included, matching the existing SwiftAstro style.
  • let over var; no force-unwrap; early returns; no raw loops where map/reduce reads better; aligned = in consecutive assignments.
  • Moved code throws SwiftAstro.Error( message: ) (SwiftAstro/Core/Error.swift:35,44), never RuntimeError — the latter lives in SwiftUtilities, which SwiftAstro cannot reach.

M1. Shared decoder API — vocabulary and compiling stubs Completed

Goal

Settle one API shape against all four formats before any of them is implemented, expressed as real Swift that compiles and is reviewable. The source document is explicit that this is cheap to change on paper and expensive after three formats have shipped against it. Two things land: the vocabulary the shape is written in (the four Sendable property types, which move out of the app so the signatures can name them without cross-module ambiguity), and the four decoder namespaces themselves, with full signatures and doc comments but no bodies.

Precondition: SwiftXISF and SwiftRAW must be present in Submodules/SwiftAstro/Package.swift (both as dependencies and on the SwiftAstro / SwiftAstroTests targets) before this milestone starts. XISFImageProperties names XISFSampleFormat, XISFByteOrder, XISFPixelStorage, XISFColorSpace and XISFDisplayFunction, so it cannot move without the dependency. The Xcode side is already wired.

Why the property types move now rather than per format: if SwiftAstro and FITScope both declared FITSPropertySnapshot, every unqualified use in the app would become ambiguous the moment it imports SwiftAstro. Relocating all four up front is a mechanical, compiler-verified change with no behavioural content, and it lets M1's stub signatures be the real ones.

Implementation notes

Implemented via TDD. DecoderSymmetryTests was written first and observed failing to compile (the decoder types and property types did not yet exist in SwiftAstro), then the sources were added until it built and passed.

Appendix B decisions (each settled against all four formats, with rationale):

  • One shared protocol, not four independent enums. The four decoders conform to a single ImageDecoding protocol with associated Container / Frame / Properties types, rather than the independent enums Appendix A literally sketches. Rationale: the source document's named failure mode is stopping early on a format; with a protocol, an omitted operation is a compile error on that format's conformance, not a test somebody forgets to extend. The trade-off (associated types preclude an existential array of heterogeneous decoders) does not bind here — every call site knows its format statically. The enums still exist as the conforming namespaces, so Appendix A's per-format table is unchanged.
  • Frame is a lazy, per-format handle and is not required to be Sendable. Appendix B suggested a Sendable struct carrying XISFImage / the RAW file, but those container types are non-Sendable classes (verified: FITSSection, XISFImage, RAWFile are reference types; CGImageSource is a CF type), so a Sendable frame is impossible without eagerly cropping/drawing/decompressing every frame up front — which would make contents( of: ) vestigial for three formats. Instead frames( in: ) enumerates cheaply and contents( of: ) does the real work, exactly as Appendix A's "where the RAW crop and the photographic draw live" intends. Only FITSImageFrame is Sendable (a FITS file is wholly in memory, so the frame can hold its Data outright). The protocol keeps Properties: Sendable and returns Data / PixelBuffer, so everything a decode produces crosses the isolation boundary; the frame handle stays within the loader's one background domain, which matches how all four loaders already work.
  • decodeSample returns Double?, not Double. The app code it replaces bounds-checks before decoding (ImageProcessor+FITS.sampleValue:810 guards byteOffset + bytesPerSample <= data.count before calling the unchecked private decodeSample:827). Publishing the unchecked variant would expose a trapping API to consumers, so the public operation keeps the bounds check and answers nil past the end.
  • The CFA string → Pattern mapping is one shared ColorFilterArray.pattern( named: ) in SwiftAstro, throwing on an unknown keyword. FITS, XISF and RAW all route through it; photographic never calls it. Adopting the throwing behaviour (over the removed test helper's silent nil) means a mosaic whose pattern is unrecognised is never mistaken for a monochrome frame.
  • isRGBPlanes / isMultiImageCube do not survive as public API. Cube-ness is answered by frames( in: ) (a multi-image cube yields N frames); colour-ness by channelCount( from: ) (which every format answers, RGB → 3). Neither FITS-specific predicate is on the shared surface.
  • Pixel read-out crosses the boundary as sampleByteOffsets( x:y: ) + decodeSample, never PixelValue. The offset arithmetic is format vocabulary and moves; the app composes PixelValue from the sample plus fullScale. Nothing in SwiftAstro learns what a tooltip is.

Additions to the sketched shape (the Appendix A "★" members): the protocol also declares bitsPerPixel( from: ) alongside dimensions and channelCount. All four formats already derive a BitsPerPixel label today (FITS from BITPIX, XISF via xisfBitsPerPixel, RAW as .int16, photographic from bytesPerComponent), and the render config needs it, so it is a uniform operation rather than a per-format detail.

Vocabulary relocation. FITSPropertySnapshot, XISFImageProperties and RAWImageProperties moved into SwiftAstro/Preprocessing/Decoding/ unchanged (only doc wording adjusted — the render comments now read "a decode" rather than "the renderer", since the types no longer live in the app). ImageIOImageProperties moved as BitmapImageProperties, keeping fullScale and isColor. The app's four copies were deleted and removed from FITScope.xcodeproj; every use site gained import SwiftAstro and, for the photographic type, the rename. The *RenderSource renames are deferred to M7 as planned.

Frame handles. One file each: FITSImageFrame (Data + properties, Sendable), XISFImageFrame (XISFImage), RAWImageFrame (RAWFile), BitmapImageFrame (CGImageSource + index + EXIF orientation, read at enumeration time so the draw can bring the frame upright).

Uniform answers verified as members, not omissions. RAWImageDecoder.frames documents "exactly one"; RAWImageDecoder.planeSamples "exactly one plane"; BitmapImageDecoder.cfaPattern is present and (in its final form) answers nil. Stub bodies use a sentinel per kind: the five throwing operations throw SwiftAstro.Error via a shared internal unimplemented( _: ) helper that names the format and operation; the optional operations return nil; scaling returns (0, 0) and channelCount returns 0. DecoderSymmetryTests pins every one of these, plus the compile-time conformance of all four decoders.

Two adjustments outside the task list, both necessary and recorded:

  • Package.swift gained .interoperabilityMode( .Cxx ) on both the SwiftAstro and SwiftAstroTests targets. SwiftRAW's libraw clang module is C++ (requires cplusplus), so once SwiftAstro depends on SwiftRAW, a plain swift build fails with module 'libraw' requires feature 'cplusplus' unless the importing target enables C++ interop. The Xcode side already sets this via SWIFT_OBJC_INTEROP_MODE = objcxx in SwiftRAW's own project and consumes the prebuilt framework, so no Xcode change is needed — the reviewer confirmed both build systems build. This is the SwiftPM half of the manual "wire SwiftXISF / SwiftRAW into Package.swift" precondition; the dependency lines themselves were already present.
  • Bare Error shadowing. After import SwiftAstro, an unqualified Error in the app resolves to SwiftAstro.Error (a struct), so seven test files' ( any Error ).self and one struct StaleError: Error were qualified to Swift.Error — matching the convention the app already uses in FITSImageLoader.swift:54. No production behaviour changed.

Goal

Capture what the app produces today, before a byte of decoding moves. The source document is right that there is no way to prove byte-identity after the fact. This milestone must therefore run before M3 touches the fixtures and before any decoder body exists.

Tasks

  • Add FITScopeTests/Golden/DetectionImageGoldenTests.swift, named and documented as temporary scaffolding removed in M9.
  • Enumerate every input on both sides of the coming boundary: the 21 synthetic fixtures, the 14 full-frame captures, and the three frames already in Submodules/SwiftAstro/Test Files/.

M4. FITS — FITSImageDecoder Not started

Goal

Fill in the FITS decoder, switch the app onto it, and delete every app-side and test-side copy of the FITS decode. FITS goes first because it is the format carrying the actual drift — the test-only re-implementation the whole initiative exists to remove — and because its Bayer keyword mapping is the one the other formats reach for. This milestone ends with FITSTestImage's private decode gone and the decode benchmark measuring the real path.

Tasks

SwiftAstro — implement the decoder
  • frames( in: FITSFile ): the single image-HDU selection rule (first section of kind .data at an index greater than zero, paired with the immediately preceding section's properties), plus cube-plane expansion. Sources: the four existing copies listed in the Notes, and ImageProcessor.isMultiImageCube (ImageProcessor+FITS.swift:297) / cubePlanes (:328), which synthesise per-plane headers by rewriting NAXIS to 2 and dropping NAXIS3.
  • contents( of: Frame ): HDU data with the 2880-byte block padding trimmed to the byte count the geometry implies.
  • linearImage( bytes:properties: ) from ImageProcessor.linearImage (:384): BITPIX → BitsPerPixel, dimensions, BLANK → NaN via PixelUtilities.readRawPixels, then BZERO/BSCALE.
  • planeSamples from the private rgbPlaneSamples (:454) and linearLuminance( fromPlanes:properties: ) from rgbLinearLuminance (:565).

Appendix

A — The shared shape, and its concrete instantiations

The shape below is the source document's, annotated with the additions this plan proposes (marked ★). It is a starting point for M1, not a settled API — M1's job is to settle it, and M8 replaces this section with what shipped. 

// Written once. Each format supplies its own Container, Frame and Properties.

public enum <Format>ImageDecoder
{
    // 1. Which frames does this container hold?
    public static func frames( in container: Container ) throws -> [ Frame ]

    // 2. A frame's canonical bytes and properties.
    //    Where the RAW crop and the photographic draw live.
    public static func contents( of frame: Frame ) throws -> ( bytes: Data, properties: Properties )

    // 3. The linear decode — the app renders from this; the detection image is built on it.
    public static func linearImage( bytes: Data, properties: Properties )
        -> ( width: Int, height: Int, samples: [ Double ] )?

    // 3b. Multi-plane frames. RAW answers with a single plane.
    public static func planeSamples( bytes: Data, properties: Properties ) throws -> [ [ Double ] ]

    public static func linearLuminance( fromPlanes planes: [ [ Double ] ], properties: Properties )
        -> ( width: Int, height: Int, samples: [ Double ] )?

    // 4. Header interpretation the app's pipeline configuration needs.
    public static func scaling( from properties: Properties )      -> ( scale: Double, offset: Double )
    public static func fullScale( from properties: Properties )    -> Double?
    public static func cfaPattern( from properties: Properties )   throws -> Processors.Debayer.Pattern?
    public static func dimensions( from properties: Properties )   -> ( width: Int, height: Int )?   // ★
    public static func channelCount( from properties: Properties ) -> Int                            // ★

    // 5. One sample at a byte offset — the app's pixel read-out calls these.
    public static func decodeSample( bytes: Data, at index: Data.Index, properties: Properties ) -> Double

    public static func sampleByteOffsets( x: Int, y: Int, properties: Properties )                   // ★
        -> [ Data.Index ]?

    // 6. The detector's input: the primitive the app calls with what it already has...
    public static func detectionImage( bytes: Data, properties: Properties ) -> PixelBuffer?

    // ...and the convenience the tests call to go end to end.
    public static func detectionImage( of frame: Frame ) throws -> PixelBuffer
}

B — Open design questions for M1

Each of these needs a decision recorded in M1's implementation notes.

QuestionContextSuggested answer
How do isRGBPlanes and isMultiImageCube generalise? FITS distinguishes NAXIS=3 RGB planes (ImageProcessor+FITS.swift:270) from an N-plane cube (:297). XISF and photographic have a plain channelCount; RAW is always 1. Cube-ness belongs to frames — a cube yields N frames. Colour-ness belongs to channelCount( from: ), which every format answers. Neither FITS predicate survives as public API.
How does the app read one pixel without PixelValue crossing the boundary? All four *PixelValues methods (:507, :732, XISF :317, RAW :160, ImageIO :184) compute a byte offset then decode. The offset arithmetic is format vocabulary; PixelValue is presentation. Publish sampleByteOffsets( x:y:properties: ) alongside decodeSample; the app composes PixelValue from the sample plus fullScale. Nothing in SwiftAstro learns what a tooltip is.
Where does the CFA string → Pattern mapping live? Three variants exist today: throwing (ImageProcessor.debayerPattern( named: ):598), non-throwing (FITSTestImage.pattern( forBayerKeyword: ):349), and the removed FITSImageDecoder's throwing one. One shared mapping in SwiftAstro, throwing on an unknown keyword. FITS, XISF and RAW all route through it; photographic never calls it.
What exactly is a Frame? It must survive being handed back to contents( of: ) and detectionImage( of: ) without the caller reconstructing container state. An opaque per-format Sendable struct carrying what that format needs (HDU + optional plane index; XISFImage; the RAW file; source + index). One file each.
Does contents( of: ) hold a reference to the container? CGImageSource and RAWFile are reference-like; FITS and XISF hand back Data. Decide explicitly, and make the Sendable story hold — the loaders call this from nonisolated static context on a background queue.
