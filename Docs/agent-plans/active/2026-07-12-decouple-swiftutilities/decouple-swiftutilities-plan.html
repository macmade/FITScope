Decouple SwiftUtilities to a First-Level Submodule

Generated — 2026-07-12
Source — design discussion in this session (no source document on disk)

SwiftUtilities is currently a doubly-nested submodule, living only under Submodules/SwiftAstro/Submodules/SwiftPixel/Submodules/SwiftUtilities. It is consumed by SwiftPixel (four low-level types only) and by the FITScope app (those types plus the AppKit/SwiftUI surface: About, Credits, GitHub updater, window helpers, Pill). SwiftAstro does not use it in source at all — its .xcodeproj only links and embeds SwiftUtilities.framework transitively so SwiftPixel works when SwiftAstro is built standalone. The nesting, and SwiftAstro's .xcodeproj reaching across into SwiftPixel's copy (Submodules/SwiftPixel/Submodules/SwiftUtilities/…), is the coupling to remove.

The goal is for SwiftUtilities to become a first-level submodule of FITScope, with no change in built behavior. The approach is not to relocate the submodule (SwiftPixel legitimately needs it to build standalone), but to remove SwiftPixel's dependency on SwiftUtilities entirely: adopt the language-level nonisolated(unsafe) in place of the two @unchecked Sendable boxes, absorb the tiny benchmark timer, and replace RuntimeError with structured error types. Once SwiftPixel is SwiftUtilities-free, SwiftAstro's transitive embed disappears, and SwiftUtilities drops into FITScope as a clean, app-only, first-level submodule. Work lands bottom-up across three repos (SwiftPixel → SwiftAstro → FITScope); SwiftUtilities itself is not modified.

Questions & answers

Why not simply relocate the SwiftUtilities submodule up to FITScope's top level?

Because SwiftPixel and SwiftAstro are standalone repos with their own CI that builds their .xcodeproj by relative path. There is one physical SwiftUtilities working copy today, referenced from two parents by different relative paths — those paths differ per build context and can't all be satisfied at once without risking two copies producing two SwiftUtilities.framework targets. The robust fix is to remove SwiftPixel's dependency, not to move a shared nested copy.

What does SwiftPixel actually use from SwiftUtilities?

Only four low-level types: RuntimeError (103 sites), UnsafeMutableSendable (9), UnsafeSendable (3), and Benchmark (1). None of the AppKit/SwiftUI surface. All four are replaceable within SwiftPixel.

How should the UnsafeSendable / UnsafeMutableSendable boxes be handled?

Eliminate them, not copy them. They are pre-nonisolated(unsafe) hand-rolls that box a raw pointer so it can be captured into a @Sendable concurrentPerform closure. Replacing each with nonisolated(unsafe) let on the local binding removes the wrapper types entirely (and the .value indirection). Verified to compile under Swift 6.3.2 with complete concurrency for both patterns SwiftPixel uses; same safety profile.

How should Benchmark be handled?

SwiftPixel already owns the injection point — PixelPipeline.Config.benchmarkOutput, a (@Sendable (String) -> Void)? sink. Only the ~6-line sync timing helper is borrowed. Absorb it into SwiftPixel (small internal helper or inline at the one call site), keep the sink as-is, and preserve the identical "Benchmarking - {label}: {seconds} seconds" output.

Should errors preserve their current messages, or is changing them acceptable?

Changing them is acceptable and desired — make the API clear. Replace RuntimeError with genuinely structured cases per failure kind. Tests that assert on messages get adapted.

One error enum, or several?

Several. A single monolithic enum is not required. Use domain-focused enums for runtime/data failures (PixelBufferError, PixelImageError, PixelInterleaveError, PixelPipelineError) plus per-processor nested ValidationError enums for config-time constraints (Levels, Curves, CorrectGamma, STFParameters). This is the granular option, chosen over a coarser two-type version because it makes each processor's failure contract explicit.

nonPositiveGamma occurs in both Levels and CorrectGamma — share or duplicate?

Keep it per-processor (duplicated case in each processor's nested ValidationError) for clearer ownership, rather than factoring a shared case.

Are submodule changes to SwiftPixel and SwiftAstro approved?

Yes. The plan deliberately modifies the SwiftPixel and SwiftAstro repositories (source and .xcodeproj) and updates FITScope's .gitmodules. SwiftUtilities itself is not modified.

Notes

  • Bottom-up landing, one repo per phase. Submodule pointers flow upward, so land in SwiftPixel first, then bump and adjust SwiftAstro, then FITScope. Each phase is independently green and is a separate repository commit. Per the working agreement, the user commits — this plan never commits or pushes.
  • Changing thrown types is control-flow-safe. There are zero as RuntimeError / as? RuntimeError / is RuntimeError pattern matches anywhere in FITScope, SwiftAstro, or SwiftPixel — every caller uses a generic catch. Only assertions on messages break, and those are all in-repo per phase.
  • Test impact. SwiftPixelTests has ~45 error assertions across 16 files (updated in Milestone 3). FITScopeTests has 0 RuntimeError references, so FITScope-side test churn is expected to be near-zero.
  • New error types must match RuntimeError's conformances where callers rely on them: RuntimeError: LocalizedError, CustomStringConvertible, Equatable. The new types conform to LocalizedError (so localizedDescription keeps working) and Equatable (tests compare).
  • FITScope owns the framework product after Phase 2 — the single riskiest step. FITScope currently has no project reference to SwiftUtilities; it inherits SwiftUtilities.framework from the nested project via BUILT_PRODUCTS_DIR. Once SwiftAstro's reference is removed, FITScope must add its own direct project reference + target dependency, or the link breaks.
  • Preserve the pinned commit. When adding SwiftUtilities as a first-level submodule in FITScope, pin it to the same commit the nested copy uses today (d138534) so behavior is unchanged.
  • FITScope keeps SwiftUtilities. FITScope's own ~47 RuntimeError uses and the AppKit/SwiftUI surface are unaffected — FITScope continues to depend on SwiftUtilities; only its submodule location and project reference change.
  • Keep Xcode and SwiftPM in sync. SwiftPixel has both a .xcodeproj and a Package.swift; both must drop SwiftUtilities. SwiftAstro's Package.swift never referenced SwiftUtilities directly, and FITScope is Xcode-only, so no SwiftPM surprises are expected (confirm Package.resolved).
  • Verification per phase. Build via xcodebuild (Debug + Release) plus swift build where a package exists, run the relevant test suite, and for FITScope launch the app and exercise the About / Credits / GitHub-updater UI.

Appendix A — error type mapping

The 103 RuntimeError throw sites collapse into the failure kinds below. All error types conform to LocalizedError and Equatable. Case names and associated-value shapes are the proposed design; exact spellings may be refined during implementation.

Proposed caseReplaces (message)Approx. sites
.notNormalized"Buffer needs to be normalized"~13
.mustNotBeNormalized"Input buffer must not be normalized"2
.bufferAccessFailed(role)"Failed to access {data / input / output} buffer"~9
.dataSizeMismatch(expected:actual:)"Data size does not match expected size: a != b"5
.pixelCountMismatch(expected:actual:)"Pixel count does not match geometry"1
.invalidChannelCount(Int)"Channel count must be at least 1"1
.negativeDimensions(width:height:)"Dimensions must not be negative"1
