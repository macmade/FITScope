Improvements — Implementation Plan

Generated 2026-07-12
Source: Docs/agent-plans/active/2026-07-11-improvements/improvements.html

This plan turns the 12-item FITScope improvements backlog into independently reviewable and committable milestones — one milestone per backlog item, as requested. Each milestone carries its own status, completion date, implementation notes, automated-review findings, and human review comments so it can be updated in place as work proceeds.

The milestones are reordered relative to the backlog's numbering to sequence them by dependency and quick-win value: isolated UI wins first, then a warnings/stability cleanup pass, then rendering and processing behavior, and finally the FITS-write feature cluster (which shares the FITS/SwiftFITS subsystem and is best built together). Each milestone notes its original backlog number. The mapping between plan order and backlog order is summarized in the appendix.

Questions & answers

Items 1–3 depend on SwiftFITS gaining FITS-write capability — what is the current state of that dependency?
Available now. SwiftFITS already exposes write support (serializedData(options:), write(to:options:) in FITSFile.swift), so items 1–3 are planned as ready-to-implement. The app currently only reads FITS; these milestones introduce the first write usage.
How should the 12 items be grouped into milestones?
One item per milestone — 12 milestones total, each independently reviewable and committable. Related milestones are grouped under named phases for readability only.
Should the plan cover all 12 items, or a subset/priority order?
All 12 items, reordered by dependency and quick-win value, with the reasoning recorded (see Notes and the Appendix mapping).
Item 5 runs brightness/contrast before the STF stretch, and that ordering is fixed inside the SwiftPixel submodule. How should the plan treat the "move after STF" idea?
Include the submodule reorder as in-scope: milestone 9 (backlog item 5) may reorder the PixelPipeline stages in the SwiftPixel submodule so brightness/contrast run after the STF stretch, alongside the app-side behavior fix.

Build & test

An .xcodeproj exists (FITScope.xcodeproj), so build and test through Xcode (xcodebuild) rather than swift build/swift test. Keep the Xcode project and any package manifests in sync. Test plan: FITScope.xctestplan.

Dependency layout

  • Direct submodules (.gitmodules): xcconfig, SwiftAstro, SwiftUtilities.
  • SwiftFITS, SwiftPixel, SwiftXISF, SwiftRAW, LibRAW come in transitively through SwiftAstro's nested submodules / Package.swift. They live under Submodules/SwiftAstro/Submodules/….
  • Per the working agreement, submodule changes require explicit approval. The submodule reorder for milestone 9 has been pre-approved (see Q&A). Any other submodule change surfaced during implementation must be raised before making it.

Reordering rationale

  • Phase A (quick UI wins) — small, isolated, low-risk view changes that deliver value immediately and touch little shared state.
  • Phase B (warnings & stability) — console-warning and resource-usage cleanups; grouped so the debug console is quieted in one focused pass.
  • Phase C (rendering & processing) — behavior changes to the render/zoom path and the pixel pipeline (including the pre-approved SwiftPixel reorder).
  • Phase D (FITS-write features) — all three depend on SwiftFITS write. Milestone 10 (backlog item 3) is sequenced first because a robust FITS-keyword/card generation path (replacing the hand-built cards) is the foundation that the FITS export (item 1) and the FITS plate-solve upload (item 2) both build on.

backlog item 7

  • Launch the app and confirm the warning no longer appears in the console.
Completed Completed: 2026-07-13
Implementation notes

Investigation — the warning is a benign OS artifact, not a bug (no code change).

  • Entitlements verified consistent: all three targets (FITScope.entitlements, FITScopePreviewExtension.entitlements, FITScopeThumbnailExtension.entitlements) are sandboxed and declare com.apple.security.application-groups → group.com.xs-labs.FITScope. No missing/mismatched entitlement.
  • Trigger: AutoStretchPreference.sharedDefaults = UserDefaults( suiteName: "group.com.xs-labs.FITScope" ), first read during Preferences.init. Reproduced reliably (the warning appears in the app-host launch of any xcodebuild test run): "Couldn't read values in CFPrefsPlistSource … (Domain: group.com.xs-labs.FITScope, User: kCFPreferencesAnyUser, ByHost: Yes …): Using kCFPreferencesAnyUser with a container is only allowed for System Containers, detaching from cfprefsd".
  • Root cause & conclusion: this is a well-known, benign CFPreferences logging artifact emitted the first time a sandboxed macOS process reads an App Group UserDefaults suite. Apple DTS confirms it is safe to ignore and that the shared preferences are still written/read correctly (CFPrefs "detaches" and reads the group's plist directly). There is no app-side fix while sharing preferences through an App Group UserDefaults suite — eliminating it would require abandoning that mechanism (raw CFPreferences / a group-container file / keychain) across the app and both extensions, with uncertain success. References: Apple Developer Forums thread 659448 (DTS "safe to ignore") and thread 728434.
  • Decision (user): accept & document as a known benign OS artifact — no behaviour change. The auto-stretch "previews" toggles continue to round-trip between the app and the sandboxed extensions. Per follow-up user feedback, no source-code comment was added; this plan entry is the documentation of record.

Implementation notes

All four warnings are external/system artifacts, not app bugs — three of them trace to the sidebar's capture-location MKMapView (MapKit / VectorKit). A definitive backtrace was captured under lldb (breakpoint on CGPostError, opening the bundled sample image), settling what static analysis alone could not.

  • 📄 External — clip: empty path. (MapKit / VectorKit). The captured backtrace is unambiguous: CoreGraphics`clip → VectorKit`grl::ShapeLayerRenderer::renderBalloonToContext(…) → MapKit`-[MKMarkerStyle initWithBalloonIcon:configuration:] → MapKit`-[MKMapView _didChangeRegionMidstream:]. It is emitted when the sidebar's location map (FITScope/Views/Sidebar/LocationMapRepresentable.swift, an MKMapView with an MKPointAnnotation) renders its marker for an image that carries location metadata. This is inside VectorKit's balloon-icon rendering — not app code, and not app-fixable. The app has no explicit clip anywhere except the comparison layer (below), confirming the observed warning is entirely MapKit-internal. Backtraces were captured for both of the two clip: empty path. messages logged per image load; both originate at VectorKit`renderBalloonToContext, with no FITScope, SwiftUI Canvas, or CanvasOverlayLayer frame in either stack — so no app Canvas is a source. (The [com.xs-labs.FITScope] subsystem tag on the message is just the running process's identifier, not an indication of app code.)
  • ➕ Separate defensive fix (not the observed warning) — ImageComparisonLayer. While hunting the source, the one place the app itself could clip an empty path was found: the before/after comparison's beforeReveal(dividerX:) did context.clip( to: Path( CGRect( x: 0, y: 0, width: dividerX, height: size.height ) ) ), which is empty when the divider is dragged fully left (dividerX == 0) or during a transient zero-height layout. Guarded it with a new tested nonisolated static func revealsBeforeImage( dividerX:height: ) (early-returns when there's nothing to reveal — visually identical). This prevents a real but rarely-hit, comparison-mode-only empty clip from our code; it is not the warning the user sees (which is MapKit). New ImageComparisonLayerTests (3 cases), wired via project.pbxproj; passes automated review. Kept (user decision) as a small robustness improvement — this is the milestone's only shipped code change.
  • Attempted map-side mitigation — reverted (empirically did not help). At the user's request, tried deferring the MKMapView mount until its card had a non-zero size (a GeometryReader guard in LocationMapView), to avoid the zero-size map/Metal setup. Re-ran the lldb capture afterward: clip: empty path. (same VectorKit renderBalloonToContext backtrace), default.csv, and setDrawableSize width=0 all still fired. The backtrace shows the clip originates in MapKit building its default marker style (+[MKMarkerStyle defaultUnselectedMarkerStyleForScale:] → balloon-icon rendering) and the Metal layer during MKMapView/marker init — internal work independent of when or at what size the map is mounted.
