STF Stretch — Implementation Plan

Generated — 2026-07-10
Source — Docs/agent-plans/active/2026-07-04-stf-stretch/stf-stretch.html

This plan adds a PixInsight-style Screen Transfer Function (STF) auto-stretch to FITScope and wires it into the places where a sensible default rendering matters most: the stretch inspector, opening images, star detection, and the system QuickLook / Finder previews.

The stretch is a Midtones Transfer Function (MTF), implemented in the SwiftPixel submodule as a new Stretch.Algorithm case that carries explicit, per-channel parameters (shadows / midtones / highlights, plus low/high range expansion). Those parameters can be filled two ways, both converging on the same editable representation in the stretch inspector:

  • Auto-STF — a derivation helper computes the parameters from the image's own statistics (shadow clip = median − 2.8·MAD, target background = 0.25).
  • XISF display function — when a file carries one, its parameters are mapped straight into the same MTF and applied on open (an XISF display function is a stored STF).

Priority on open (XISF): if the file carries a display function, use it; otherwise apply auto-STF when the format's preference is enabled. Either way the result lands as editable, pre-filled parameters in the stretch inspector — the user can then tweak them, exactly like PixInsight's STF.

Questions & answers

Is modifying the SwiftPixel submodule acceptable for this work?

Yes — implement the STF/MTF core in SwiftPixel, as the source doc directs. SwiftPixel already provides PixelUtilities.median and medianAbsoluteDeviation; it is missing only the MTF curve, the parameter type, and the new algorithm case.

How should the one-click auto-STF integrate with the existing adjustment model?

STF is a stretch phase, like the other stretch controls — just applied automatically based on the preferences. It lives in the stretch inspector alongside log / arcsinh / sigmoid, and exposes its own controls (shadows / midtones / highlights and the auto shadow-clip factor + target background).

The QuickLook / Finder extensions are sandboxed and can't read the app's UserDefaults. How should previews apply the default STF?

Honor the per-format preference via a shared App Group: the app writes the auto-stretch preference to a shared suite the extensions can read, so previews match the app's choice.

Which formats should the per-format auto-stretch-on-open preference expose?

Only the linear formats — FITS, XISF and RAW. Already-display-ready formats (PNG / JPEG / TIFF / HEIC, opened via ImageIO with an "as authored" baseline) are excluded.

When an XISF file carries a display function, what should happen?

It should be used (applied on open). Auto-STF is only the fallback when no display function is present and the preference is on.

How should an applied XISF display function appear in the UI?

As an editable STF in the inspector: the stretch control opens in Screen Transfer mode with its sliders pre-filled from the file, and the user can adjust them.

What fidelity should the display-function / MTF support target?

Full: per-channel parameters (R/G/B/lightness) plus low/high dynamic-range expansion, not just a single midtones/shadows/highlights triple.

Notes

  • One MTF, two parameter sources. The new Stretch.Algorithm.screenTransfer(STFParameters) applies explicit per-channel MTF parameters. Auto-STF and the XISF display function are just two ways to produce those parameters; both then flow through the identical apply path and the identical editable inspector control. This keeps a single source of truth for "what the STF is."
  • Where it plugs in. The pipeline models the non-linear stretch as Processors.Stretch.Algorithm?, carried through ImageAdjustments.stretch → ImageProcessor.Settings.stretch → PixelPipeline.Config.stretch. The new case flows through all of these unchanged; no new pipeline field is required.
  • Materializing auto-STF parameters (key implementation point). Because the parameters must be editable and pre-filled, auto-STF can't compute silently at render time — it must produce concrete STFParameters at load. SwiftPixel will expose a one-shot helper that runs the minimal normalize + statistics pass and returns the parameters, so the loaders and preview extensions can materialize them without duplicating pipeline logic. Confirm this helper's exact shape during Milestone 1.
  • Per-image baseline. Each image opens on a baseline (ImageProcessor.Settings) passed to ImageRenderer(source:defaults:). Auto-apply-on-open (or applying an XISF display function) means seeding that baseline's stretch, so the stretched view is the "as opened" state that reset() / hasAdjustments compare against. The linear-format loaders are the hook points: FITSImageLoader.swift:213, XISFImageLoader.swift:182, RAWImageLoader.swift:152. ImageIOImageLoader already seeds asAuthoredDefaults and is correctly excluded.
  • XISF display function is currently parsed but dropped. SwiftXISF parses it (XISFImage.displayFunction: XISFDisplayFunction? — per-component midtones m, shadows s, highlights h, shadows/highlights expansion l/r), but the app's XISFImageProperties drops it and the render path never applies it. Milestone 4 surfaces it and maps it onto the MTF.
  • Sandboxed extensions. FITScopePreviewExtension and FITScopeThumbnailExtension are separate processes rendering via PreviewRenderer. They read the auto-stretch preference only through a shared App Group suite (Milestone 3) and materialize auto-STF parameters via the same SwiftPixel helper. Confirm which types each extension declares support for (FITS, XISF).
  • Reuse the per-channel UI pattern. The Levels and Curves controls (Views/Levels, Views/Curves) already offer a uniform ↔ per-channel editing pattern; the STF inspector control should follow it rather than invent a new one.
  • Conventions (repo working agreement). Prefer let; no force-unwrap; no raw loops; one type per file; add SwiftUI previews for new/changed views; document public and private members. Build and test through xcodebuild; keep FITScope.xcodeproj and the SwiftPixel project in sync when files are added. Committing / pushing and submodule pointer updates are the maintainer's responsibility.
  • Open decision surfaced for review (does not block starting): whether the auto-stretch-on-open preference defaults on or off per format — the plan proposes off (opt-in) and flags it in Milestone 3.

Improve star detection

Completed
Design decisions (maintainer)
  • Re-scoped from "Auto-STF before star detection." The original milestone proposed running detection on an STF-stretched copy of the detection buffer. That premise was investigated and dropped: FITScope's MatchedFilterStarDetector is a linear detector with an adaptive robust threshold (background + N·MAD), so a monotonic nonlinear stretch adds no detection information and, by distorting each star's profile, would corrupt the geometric metrics (medianFWHM / medianHFR / medianEccentricity) that feed image weighting and the session graphs — which is exactly why StarDetecting documents that its input must be linear. NINA (the reference) confirms it: its built-in detector does not nonlinearly stretch before detection and measures HFR on the original linear array (it finds candidates on a resized, linearly bit-reduced bitmap via an adaptive edge/threshold, then measures metrics on the linear data). So this milestone becomes "make star detection actually work," driven by concrete failing frames rather than by a stretch.
  • Driven by real failing frames. Detection currently finds zero stars on some real-world subs — e.g. a ZWO Seestar S30 10 s M42 light-pollution sub (16-bit, BAYERPAT = GRBG, 1080×1920). The maintainer will provide the failing test frame(s) to diagnose against and turn into repeatable fixtures.

Appendix

MTF and STF math (PixInsight-style)

mtf(m, x) = ((m − 1)·x) / ((2m − 1)·x − m)

  where   m = midtones balance (0 < m < 1),  x ∈ [0, 1]
  edges:  m = 0   → 1
          m = 0.5 → x          (identity)
          m = 1   → 0

Applying an MTF stage (per channel), matching the XISF display-function model:

// s = shadows clip, h = highlights clip, m = midtones,
// l = low range expansion, r = high range expansion
clipped   = clamp( (x − s) / (h − s), 0, 1 )     // guard h ≠ s
curved    = mtf( m, clipped )
expanded  = clamp( (curved − l) / (r − l), 0, 1 ) // guard r ≠ l

Deriving auto-STF parameters from a channel's statistics (source doc):

shadowClipFactor = 2.8     (default; user-tunable)
targetBackground = 0.25    (default; user-tunable)

s (shadows) = clamp( median − shadowClipFactor · MAD, 0, 1 )
h           = 1
l, r        = 0, 1        (no range expansion for auto-STF)

// normalized median after clipping the shadows:
m0 = (median − s) / (1 − s)          (guard 1 − s ≠ 0)

// midtones solved so mtf(midtones, m0) = targetBackground:
midtones = mtf( m0, targetBackground )   // MTF is self-inverse in the balance

Validate the midtones-from-background derivation against a reference implementation in Milestone 1; the unit tests that assert the background lands near targetBackground are the guardrail.
