Overview

The star-detection algorithm rewrite lives in the SwiftAstro submodule (see the companion plan there). On the FITScope side the change is small: adopt the new MatchedFilterStarDetector as the default, keep the rest of the pipeline (overlay, coordinate mapping, off-main-actor detection) unchanged, and advance the submodule pointer. This plan can only land after the SwiftAstro work is committed.

Questions & answers

Q: Scope of FITScope changes?

A: Default-detector swap, test update, and submodule pointer bump; the design otherwise leaves the FITScope pipeline untouched.

Notes

  • Call site: FITScope/Model/StarDetection.swift — detectStars(in:using:) defaults the detector.
  • Detection already runs off the main actor (FITSImage.detectStars() via Task.detached); the added cost doesn't affect UI responsiveness.
  • The overlay (StarsOverlay) and coordinate mapping are verified correct and stay unchanged.
  • Keep FITScope.xcodeproj and any package manifest in sync; build/test via xcodebuild.

Status: Completed
Completed: 2026-06-28
Implementation notes
  • Changed the default detector in FITScope/Model/StarDetection.swift: detectStars(in:using:) now defaults detector to MatchedFilterStarDetector() instead of MomentStarDetector() (its initializer is fully defaulted, so the swap is a one-line change). Updated the doc comment to point at MatchedFilterStarDetector.
  • The test did not pin the old detector type, but its fixture was incompatible with the new default: the old starImage built a flat, noiseless bright square, and the matched filter returns an empty field for an image with no measurable noise. Replaced it with a file-private SyntheticStarField helper (Gaussian star + deterministic seeded noise, mirroring SwiftAstro's test helper, which is not importable from SwiftAstroTests). detectsStarsInImage() now plants a σ=2 Gaussian star on a noisy background.
  • TDD note: a coordinator-level test cannot produce a meaningful red for this change. I first tried a nebulosity-rejection test (star planted on a strong gradient, expecting exactly one detection) as a discriminator, but (a) the old MomentStarDetector default also passed it, so it was not a discriminator, and (b) after the swap it failed with count == 0 — the matched filter dropped even the real star because a strong gradient inflates the global noise estimate. Detecting a star buried in strong nebulosity is not a documented/tested guarantee of the algorithm, so asserting it was wrong. I removed that test (and the unused gradient helper) rather than tune a brittle fixture against SwiftAstro internals.
  • Verified via xcodebuild test -scheme FITScope -destination 'platform=macOS': the full FITScopeTests target passes — 184 tests in 31 suites — with the new default.

Status: Completed
Completed: 2026-06-28
Implementation notes
  • Submodule pointer advanced by the user to 952d9e3 (heads/main), which contains MatchedFilterStarDetector.
  • Build: FITScope, FITScopeThumbnailExtension and FITScopePreviewExtension all build cleanly against the new submodule (xcodebuild build -destination 'platform=macOS'). The full FITScopeTests target passes (184 tests).
  • Objective real-frame verification via SwiftAstro's RealFrameValidationTests (run through the SwiftAstro scheme), which exercise the matched filter on the same M42 and M35 frames bundled in the submodule: doesNotLatchOntoTheM42Nebula (M42 count ≤ 150, vs. the hundreds the old global-threshold detector produced), detectsWellFormedStarsInTheM35Cluster, and detectsStarsOnTheRealFrameNearReportedHFR all pass. This objectively covers "markers land on real stars / nebula ring gone / noise not circled" at the algorithm level. The overlay and coordinate mapping are unchanged (see Notes) and covered by StarsOverlayTests.
  • Root cause of the overlay misalignment (found via instrumentation on the real H3.69 Bayer frame and M35): the detected coordinates match the rendered byte buffer under identity — the flip was purely in the view layer. HoverImageNSView (in ZoomableImageView.swift) is isFlipped = true (top-left origin, matching the overlay and cursor readout) but drew the CGImage with a raw CGContext.draw(_:in:), which assumes a bottom-left origin and therefore rendered the image upside-down. The overlay and cursor-readout coordinate systems were correct; the displayed image was the outlier.
  • Fix: draw via NSImage(cgImage:size:).draw(in:), which honours the view's flippedness and renders the image upright (row 0 at top). This corrects both the star overlay and the (previously also-flipped) cursor pixel readout with one change. Added a regression test FITScopeTests/Views/Canvas/ZoomableImageViewTests.swift that renders the view through an offscreen window and asserts row 0 lands at the top; it fails on the old draw and passes on the fix. Full FITScopeTests target: 185 tests pass. Note: this vertically flips how every image previously appeared on screen (the previous appearance was the bug).
  • Pending: the in-app visual confirmation (open M42 & M35 in the running app; confirm markers now land on real stars; exercise the toolbar toggle and loading state) — a human visual check to be performed by the user.
Review comments
  • User (visual check on M42): the overlay markers do not land on the actual stars. Empirically, rotating the overlay and flipping it horizontally makes the markers align with real stars — indicating a coordinate-orientation mismatch between the detector's coordinate space and the displayed image. This contradicts the plan's earlier assumption that the overlay / coordinate mapping were "verified correct"; investigate the StarDetection → overlay coordinate transform under the new detector.
  • Confirmed objectively (default/identity orientation): I extracted the rendered display (m42.png) and the overlay (detect.png), both 2034×1132, and measured marker-to-star nearest-neighbour distance under each transform — identity matched 0% of stars, a vertical flip matched best (≈46% within 15px, the rest being faint stars the quick detector missed). The user's "rotate 180° + flip horizontal" composes to a vertical flip. So there is a genuine vertical-flip (FITS bottom-up row-order) mismatch between the detection coordinate space and the displayed image.
  • Diagnosis: this is pre-existing, not introduced by the detector swap — both detectors emit Star(x: column, y: row) in identical row-major order, and the rewrite did not touch FITSImageDecoder or Star. Static reading of both decode paths did not reveal where the flip is introduced (neither path nor createCGImage visibly flips), so the exact root-cause location still needs runtime instrumentation of the real pipeline. The fix lives in pre-existing FITScope render/overlay code, which is outside this plan's stated scope.
