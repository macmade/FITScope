Detection Image

Generated — 2026-07-21
Supersedes — the 2026-07-20 revision of this document
Scope — give FITScope and SwiftAstro's tests exactly one way to obtain a detection image
Nature — design document; the milestone plan is derived from this separately.

SwiftAstro's tests do not test the app. They validate star detection and sky-background measurement against frames produced by a hand-written decode that exists only inside the test suite, while the app produces its detection images with entirely different code. The two agree today by coincidence, and nothing keeps them aligned. This document specifies sharing a single detection-image path between the two. What has to move turns out to be the whole of each format's header interpretation and sample decoding — producing a detection image needs all of it. What stays is everything the app does with the result: rendering, processing, configuration and presentation. The constraint throughout is that SwiftAstro learns about file formats and nothing about an app.

Problem

SwiftAstroTests/Helpers/FITSTestImage.swift carries a private re-implementation of the FITS decode — linearImage(header:data:) (:286), imageHDU(in:) (:331), pattern(forBayerKeyword:) (:349), numericValue(of:) (:366). Its own documentation describes it as “a test-only reimplementation of the FITS→buffer adapter the library no longer ships”. Every real-frame validation test and the decode benchmark consume buffers built by that code.

The app builds its detection images somewhere else entirely: four private detectionImage(…) methods, one per loader — FITSImageLoader.swift:354, XISFImageLoader.swift:285, RAWImageLoader.swift:317, ImageIOImageLoader.swift:354 — over ImageProcessor's decode surface.

Nothing holds the two together. A change to how FITScope interprets BZERO/BSCALE, masks BLANK, chooses an image HDU, or maps BAYERPAT to a Bayer phase does not reach the library's tests; a change in the test decoder does not reflect the app.

The consequence is the one that matters, and it is not the duplication itself: a green SwiftAstro test suite is not evidence that the app's star detection works. The detector, the sky-background estimator and the benchmarks are tuned and regression-guarded against inputs the app never produces. That unreliability is what this design removes.

Two smaller duplications sit alongside it and are worth closing while the area is open: image-HDU selection exists twice more — FITSPreviewRenderer.imageHDU(from:) (FITScope/Image/FITSPreviewRenderer.swift:49) and FITSTestImage.imageHDU(in:) — and ImageProcessor.render(data:properties:) (ImageProcessor+FITS.swift:62-145) hand-rolls a decode duplicating linearImage and decodedImageHDU within the app.

Goal

One way to obtain a detection image, run by the app in production and by SwiftAstro's tests against the committed frames.

The goal is narrow, but its consequences are not. Producing a detection image turns out to require essentially the whole of a format's header interpretation, so “share the detection path” and “move decoding into SwiftAstro” amount to the same change — the section What has to be shared works through why. What the goal does exclude is everything on either side of the decode: the app keeps opening files, and it keeps every use it makes of the samples — rendering, processing, configuration, presentation.

Guiding principle

Anything that can change the detection image's bytes moves. Everything else stays in the app.

That criterion is checkable, and it bounds the surface in both directions. It is what forces the RAW crop across — the crop origin sets the Bayer phase, so cropping differently produces a different detection image — and it is what keeps metadata, settings, the render pipeline and the whole loader shell out of SwiftAstro, since none of them can perturb a single sample. Note the asymmetry it implies: the render pipeline stays, but the decode it consumes moves, because that decode is the same one the detection image is built from.

A second rule constrains the vocabulary: if a type exists because FITScope has a user interface, it does not go into SwiftAstro. No ImageProcessor.Settings, no PixelPipeline.Config, no RenderResult, no PixelValue, no ImageRenderSource, no ImageLoading, no Combine, no progress or cancellation, no metadata model. SwiftAstro should end up knowing about file formats, not about an app.

A third rule governs the result, and it is the one most likely to be violated by accident:

The outcome is a public API, not four migrations. Every format offers the same operations.

This is not a per-format refactor that happens to run four times. If FITS gains a capability in SwiftAstro, the equivalent exists for XISF, RAW and photographic — no format is left with a partial surface, and no format is special-cased out because its path looks less astronomical. A consumer should be able to reach a detection image the same way regardless of what it opened.

Where a format has no meaningful answer, it answers uniformly rather than omitting the operation: RAW always enumerates exactly one frame, and a photographic frame never carries a colour-filter array. That is symmetry of capability, not padding every type with members that mean nothing — the test is whether a caller has to know which format it holds in order to get a detection image out of it.

What has to be shared

The detection image is the same recipe in all four formats:

  1. Get the frame's samples out of the file, applying the format's linear scaling.
  2. If the frame carries a colour-filter array, demosaic to luminance via BayerGrayscaleConverter; otherwise take the single linear channel as-is.

Step 2 already lives in SwiftAstro. Step 1 is the whole problem. And step 1 cannot be shared as a pure (bytes, properties) → buffer function alone, because the tests start from a file: if SwiftAstro's tests produce those bytes and properties by their own means, the divergence simply moves down a level — from the decode to its inputs — and the tests are no more trustworthy than they are today.

So a minimal amount of file handling has to come along: exactly the part that determines the canonical bytes and the properties, and nothing beyond it. Applying that test yields a set of capabilities — and by the symmetry rule, the set is the same for every format.

Four points deserve comment, because they are where the “it determines the bytes” test bites hardest and where instinct would get it wrong.

The decode is not a small hidden core. It is tempting to imagine SwiftAstro exposing only “give me a detection image” and keeping the rest private. It cannot: ImageProcessor.linearImage (ImageProcessor+FITS.swift:384) already reads BITPIX, resolves imageDimensions, trims FITS block padding, passes blankValue into readRawPixels and applies scaling's BZERO/BSCALE — and the loader's detection path (FITSImageLoader.swift:354) adds isRGBPlanes, rgbLinearLuminance and bayerPattern on top. Producing a detection image therefore requires essentially the whole header interpretation. Keeping it private would mean SwiftAstro holding a concealed copy while ImageProcessor keeps a public parallel one — full duplication, now across a submodule boundary where no shared test can catch a divergence. So the decode is public, and the app's rendering and read-out are built on it. One implementation exposed beats two with one hidden.

The RAW crop. RAWImageProperties's own documentation notes the CFA pattern is “derived at the crop origin so its Bayer phase is correct after the margins are removed”. A test cropping even slightly differently from the app would demosaic on the wrong phase and validate the detector against an image the app never sees. So RAWImageLoader.croppedMosaic(file:sizes:) (:261) and the properties derivation move — while RAWFile construction, unpacking and RAWImageInfo stay.

The photographic draw. It fixes the byte layout the decode then reads, so it moves on the same test as every other row — which means SwiftAstro imports ImageIO. That is not a special case to be argued around: a format whose decode stops short of its own bytes is exactly the partial surface the symmetry rule forbids, and the result would be that SwiftAstro cannot test a photographic frame end to end. ImageIO is a system framework, so it costs nothing but vocabulary.

Frame enumeration is worth calling out as a genuinely cross-format concern rather than a FITS peculiarity: the app already enumerates frames for all four — FITSImageLoader.swift:403,409 (cube planes), XISFImageLoader.swift:144,150 (file.images), ImageIOImageLoader.swift:156,162,178 (CGImageSourceGetCount) — and the committed fixtures cover three of them (MultiImage3D.fits, MultiImage.xisf, MultiImageHEIC.heic). Which frame you pick decides which bytes you decode, so it moves; and because the app's render sources are built per frame, they consume the shared enumeration rather than keeping a second one.

Proposed shape

Per-format decoder namespaces under SwiftAstro/Preprocessing/Decoding/, one type per file, alongside the Sendable property snapshots they need. Every decoder answers the same questions in the same order, differing only in the container it opens from and the properties it produces: 

// The shape, written once. Each format provides its own Container and Properties.

public enum <Format>ImageDecoder
{
    // 1. Which frames does this container hold?
    public static func frames( in container: Container ) throws -> [ Frame ]

    // 2. What are a frame's canonical bytes and properties?
    //    This is where the RAW crop and the photographic draw live.
    public static func contents( of frame: Frame ) throws -> ( bytes: Data, properties: Properties )

    // 3. The linear decode — the app renders from this, and the detection image is built on it.
    public static func linearImage( bytes: Data, properties: Properties )
        -> ( width: Int, height: Int, samples: [ Double ] )?

    // 3b. Multi-plane frames (FITS, XISF, photographic — RAW is always single-channel).
    public static func planeSamples( bytes: Data, properties: Properties ) throws -> [ [ Double ] ]

    public static func linearLuminance( fromPlanes planes: [ [ Double ] ], properties: Properties )
        -> ( width: Int, height: Int, samples: [ Double ] )?

    // 4. Header interpretation the app's pipeline configuration needs.
    public static func scaling( from properties: Properties )   -> ( scale: Double, offset: Double )
    public static func fullScale( from properties: Properties ) -> Double?
    public static func cfaPattern( from properties: Properties ) throws -> Processors.Debayer.Pattern?

    // 5. One sample at a byte offset — the app's pixel read-out calls this.
    public static func decodeSample( bytes: Data, at index: Data.Index, properties: Properties ) -> Double

    // 6. The detector's input: the primitive the app calls with what it already has...
    public static func detectionImage( bytes: Data, properties: Properties ) -> PixelBuffer?

    // ...and the convenience the tests call to go end to end.
    public static func detectionImage( of frame: Frame ) throws -> PixelBuffer
}

Concretely, Container is FITSFile / XISFFile / RAWFile / CGImageSource, and Properties is [ FITSPropertySnapshot ] / XISFImageProperties / RAWImageProperties / BitmapImageProperties. RAW's frames returns a single element; the rest enumerate. The caller parses the container — that stays app-side, and costs a test one line.

The multi-plane path is a further instance of the symmetry rather than a FITS special case: three of the four formats already have one, and the app's own documentation says so — ImageProcessor+XISF.swift:152 calls xisfPlaneSamples the “XISF analogue of rgbPlaneSamples”, and ImageProcessor+ImageIO.swift:110 calls imageIOPlaneSamples the “ImageIO analogue of xisfPlaneSamples / rgbPlaneSamples”. So planeSamples and linearLuminance(fromPlanes:) belong in the shared shape for FITS, XISF and photographic alike. RAW is the exception, and uniformly so: a sensor mosaic is always a single channel.

Steps 3 to 5 exist because the app needs them, not because the detection image does — but they are the same code the detection image runs, and publishing them is what prevents a second copy. They are format vocabulary throughout: nothing here knows that a value will end up in a pipeline, a histogram or a tooltip.

Naming
The photographic decoder is named for what it decodes, not for the framework that produced its bytes.

What moves is the decode of a canonical interleaved bitmap, so BitmapImageDecoder / BitmapImageProperties rather than ImageIO*. SwiftAstro does import ImageIO to perform the draw — the framework is an implementation detail of one decoder, not a concept the API exposes.

Error type
Moved code throws SwiftAstro.Error.

RuntimeError lives in SwiftUtilities, a FITScope-level submodule SwiftAstro cannot reach. SwiftAstro.Error (SwiftAstro/Core/Error.swift:35) has the same init( message: ) shape. No caller inspects the error type; the single test asserting a throw checks only (any Error).self.

Reinstating a removed name
A commit bringing back FITSImageDecoder must say why it is not a revert.

Commit c0ac847 (SwiftAstro, 2026-07-19) removed the public FITSImageDecoder with a BREAKING CHANGE trailer, on the grounds that it had degenerated into test-support scaffolding whose “sole remaining users were SwiftAstro's own real-frame validation tests and the decode benchmark”. That reasoning was sound for what the type had become. The name comes back with the opposite property: the app calls it in production, and it is the only path either side uses.

What stays in the app

Everything to do with rendering, processing, configuration and presentation. The line is drawn at interpretation versus use: SwiftAstro says what the bytes mean; the app decides what to do with them.

ImageProcessor keeps Settings, DebayerSelection, AutoStretchColorSource / AutoStretchDomain, all PixelPipeline.Config building, every render(…), previewBinFactor, PixelValue, RenderResult, and the whole auto Screen Transfer derivation. The four loaders keep their ImageLoading conformance, their async and progress handling, and their metadata extraction. ImageRenderSource and the four render sources keep their current shape: detectionImage remains a stored property, and only its producer changes.

What changes for these is where they get their numbers, not what they do. render builds its pipeline configuration from the decoder's scaling and fullScale instead of its own header reads, and renders the decoder's linear samples. sampleValue keeps its shape and its PixelValue return type, but obtains the raw sample from the decoder rather than a private decodeSample. So the app's display and its detection image are provably derived from one interpretation of the file — the number under the cursor cannot disagree with the image on screen.

Test fixtures

The frames the shared path must be validated against currently live on the wrong side of the boundary. Test Files/ in the app holds two quite different things:

  • Test Files/Fixtures/ — 21 small synthetic files (~4.5 MB): MonoImage.fits, RGBImage.fits, ColorImage.fits, MultiImage3D.fits, InvalidImage.fits, MultiImage.xisf, RGBImage.xisf, PhotoRGB.png, PhotoHEIC.heic, OrientedPhoto.tiff, Spectrum1D.fits and similar. These serve app-side render, loader, view and metadata tests, and are resolved by path via TestFixtures.url(_:).
  • The Test Files/ root — 14 full-frame real captures (~230 MB): seven FITS/FIT lights and stacks, one XISF, one Canon CR3, and five processed *-Final.jpg references. Of these, exactly one is referenced from any Swift source: C6-R7-M42-Light.cr3, via TestFixtures.cameraRAW (TestFixtures.swift:176).

The reorganisation follows the boundary:

  • The synthetic fixtures stay with the app, promoted from Test Files/Fixtures/ up into Test Files/ itself. With the captures gone the subdirectory has nothing to distinguish it from, and TestFixtures.directory (:50) collapses onto testFilesDirectory (:39).
  • All fourteen full-frame captures move to SwiftAstro's Test Files/, joining the FITS frames already there. They are what the library needs in order to validate the shared path against real data, and every format needs its own — the CR3 is the reason SwiftAstro must reach a detection image from a RAW file at all, and the same argument applies to the XISF and the photographic frames.

Fixtures on both sides resolve by #filePath-relative path rather than as bundled resources, deliberately, “so tests open real files exactly as the app does”. That keeps the move cheap: the app's six remaining cameraRAW assertions in FITScopeTests/Model/RAW/RAWImageLoaderTests.swift (:42, :55, :78, :99, :117, :159) exercise loader behaviour rather than decoding, so they can stay where they are and point TestFixtures.cameraRAW at the submodule path.

Once the captures are in place, FITSTestImage loses its private decode entirely (:286-374) and keeps only what it exists for: fixture location (url(resource:extension:)), the named-frame accessors, and crop. The decode benchmark and RealFrameValidationTests then measure and assert against the app's real path.

Consequences and risks

Real drift may surface when the two paths merge

The app's decode and FITSTestImage's are asserted to agree only once they become the same code. If RealFrameValidationTests or the benchmark shifts at that point, that is the divergence this work exists to find. It must be reported and decided on its merits, never accommodated by adjusting an assertion. Detection-image contents are otherwise required to be byte-identical before and after — a golden digest over the committed frames, captured before anything moves, makes that checkable rather than aspirational.

Asymmetry creeping back in

The failure mode for this design is not a bug — it is stopping early. Each format's work will present a moment where the remaining piece looks unnecessary: photographic has no CFA, RAW has only one frame, XISF's parse is already a one-liner. Taken individually each omission is defensible, and together they rebuild the partial, per-format surface the whole exercise exists to avoid. The check is the one stated up front: can a caller get a detection image the same way without knowing which format it holds?

App vocabulary crossing the boundary

The public surface is deliberately wider than “give me a detection image”, so “keep it small” is not the guard here — the guard is what kind of thing is being published. Format vocabulary (scaling, BLANK, sample formats) is welcome; anything that knows a value is destined for a pipeline, a histogram or a tooltip is not. The test to apply to each new public: would this member still make sense to a consumer that has no user interface at all?

Mechanical churn

Deleting the app's copies rather than leaving forwarding shims means a large compiler-verified diff — on the order of a hundred call sites. Shims would leave two names for every operation and a facade implying the app still owns the decode, which is the confusion being removed. Sequencing one format at a time keeps any single review tractable.

Sequencing

Sequencing is about keeping any single review tractable — it is not a licence to ship formats independently. The API is designed once, for all four formats, before the first one is built; the per-format steps are then implementations of an agreed shape rather than four chances to invent one. The initiative is finished when every format offers the full set, not when the last format compiles.

  1. API design — settle the shared shape against all four formats at once: frame enumeration, properties, canonical bytes, linear decode, header interpretation, single-sample read, CFA, detection image. Cheap to change on paper, expensive after three formats have shipped against it.
  2. Baseline — capture golden digests for the committed frames through the current app path, before anything moves. There is no way to prove byte-identity after the fact.
  3. Fixtures — promote the synthetic fixtures into Test Files/, move the captures to SwiftAstro, repoint TestFixtures.cameraRAW at the submodule path.
  4. FITS — first, as the format carrying the actual drift, and the one whose Bayer keyword mapping the others reach for. Ends with FITSTestImage's private decode deleted and the benchmark retargeted.
  5. XISF, then RAW, then photographic — each an add-switch-delete against the shape already agreed. Because no forwarding shims are left behind, a format's decoder must land in SwiftAstro before the app's copy is deleted, so a short-lived duplication inside a format's step is expected and must not outlive it. Each step rewires that format's render and read-out onto the decoder too — a format is not done while ImageProcessor still interprets its headers.
  6. Symmetry check — before cleanup, verify no format ended up with a partial surface, and that a caller can reach a detection image identically for all four.
  7. Cleanup — collapse ImageProcessor.render(data:properties:)'s inline decode (ImageProcessor+FITS.swift:62-145), which duplicates linearImage and decodedImageHDU and differs only in throwing rather than returning nil; remove the golden scaffolding; confirm the seam.

SwiftAstro will need SwiftXISF and SwiftRAW as dependencies for this work. Wiring them into Package.swift and the Xcode project is handled manually and is out of scope for the plan.

Out of scope

  • Any change to the star detector, the sky-background estimator, or the auto Screen Transfer derivation. The detection image's contents must be byte-identical before and after.
  • Moving metadata extraction, the render sources, or any part of the loader shell.
  • A shared test-support target between the two suites. Once the path is shared, a drifting fixture means a different input, not different behaviour.
