Decode Once, Render Many

Design note — 2026-07-13
Reduce redundant per-render pixel decoding on the interactive render path, and unify the thumbnail decode-once special-case, without raising steady-state memory.

Motivation

The image renderer decodes a frame's pixels from raw Data on every render, and keeps no decoded pixels — a deliberate choice to hold memory low. The cost of that choice is redundant decoding. This work targets the redundant decoding on the render path (CPU / latency), not the held detectionImage buffer. The guiding constraint is unchanged: steady-state memory must not increase.

Concretely, ImageRenderer.render() runs the pixel pipeline twice per pass — once for the displayed result and once for the unstretched original / before-image — and each call re-decodes the same bytes independently (ImageRenderer.swift:363-364). The two decodes are of identical samples (orientation is a pipeline step applied after decode), so one of them is pure waste. It happens on the first render of every image and on every orientation change (rotate / flip).

The thumbnail / QuickLook path already avoids this: it decodes once and shares the samples between the auto-stretch statistics and the single render (FITSPreviewRenderer.swift:78-94, XISFPreviewRenderer.swift:69-76). The main render path simply does not reuse that machinery.

Scope

  • In scope: the render-pass dedup (decode once, render result + original from the same samples) and the thumbnail fold-in (the preview renderers share the same decode-once seam), for all four formats: FITS, XISF, RAW, ImageIO.
  • Out of scope: releasing detectionImage after star detection / background analysis, and any persistent decoded-pixel cache that survives across renders (a session-scoped cache would trade the low-memory design for per-adjustment CPU — a separate, opt-in decision, not taken here).
  • Behaviour: unchanged. Decoding is deterministic, so the shared samples are byte-identical to today's independent decodes; the rendered output is identical. This is a pure dedup / refactor.

Current per-format decode seams

Feasibility hinges on each format having a decode-once → render-from-decoded pair. Two formats already expose it (the preview path uses them); two need a small public entry added.

FormatByte render pathDecode-once core exposed?
FITS render(data:properties:settings:) → readRawPixels → render(rawSamples:…) Yes — decodedImageHDU(data:properties:) + render(rawSamples:…). Returns nil for RGB colour-plane frames / data cubes, which keep the byte path.
XISF render(data:xisf:settings:) → xisfPlaneSamples → render(planes:xisf:…) Yes — xisfPlaneSamples(data:properties:) + render(planes:xisf:…). No fallback; every layout decodes to planes.
RAW render(data:raw:settings:) → rawImageSamples (private) → render(planes:…) Needs a public entry — decode + plane-render machinery exist; expose a decode-free render(plane:raw:…) (and the sample decode), mirroring FITS/XISF.
ImageIO render(data:imageIO:settings:) → imageIOPlaneSamples (private) → render(planes:…) Needs a public entry — same as RAW; expose a decode-free render(planes:imageIO:…) (and the plane decode).

Design

1 — A "decoded once" abstraction

A Sendable protocol representing a source whose pixels are already decoded and can be rendered repeatedly and have their auto-stretch input derived, all without touching bytes again: 

protocol DecodedRenderSource: Sendable
{
    func makeResult( settings: ImageProcessor.Settings ) throws -> ImageProcessor.RenderResult
    func autoStretchColorSource( maxDimension: Int? ) -> ImageProcessor.AutoStretchColorSource?
}

Each format has a small value-type conformer wrapping its decoded representation — FITS: samples + bitsPerPixel + properties; XISF / ImageIO: planes + properties; RAW: plane + properties. makeResult delegates to the existing decode-free render(rawSamples:/planes:…); autoStretchColorSource delegates to the existing autoStretchColorSource(fromSamples:/fromPlanes:…).

2 — ImageRenderSource gains a decode-ahead entry

func decoded() throws -> ( any DecodedRenderSource )?   // default: nil

FITS returns nil for the RGB-plane / cube case (keeping the byte fallback exactly as decodedImageHDU does today); XISF / RAW / ImageIO always return a decoded frame. A default implementation returns nil, so a source that opts out simply keeps decoding per render.

3 — Render path dedup (the win)

ImageRenderer.render() decodes once, renders twice:

let decoded  = ( try? source.decoded() ) ?? source   // decoded frame, or the source itself
let result   = try makeResult( decoded, settings )
let original = needsOriginal ? try makeResult( decoded, originalSettings ) : nil

ImageRenderer.makeResult is retargeted from any ImageRenderSource to the shared makeResult(settings:) method both the decoded frame and the source provide (a small shared protocol, or a common supertype). The decoded samples live only for the duration of the render() call, so steady-state memory is unchanged — the two result / original decodes collapse into one.

4 — Thumbnail fold-in

FITSPreviewRenderer / XISFPreviewRenderer currently inline decodedImageHDU / xisfPlaneSamples plus a previewSettings(decoded:) / previewSettings(planes:) twin plus render(rawSamples:/planes:…). With the shared DecodedRenderSource, each preview renderer builds the decoded frame once and calls frame.autoStretchColorSource(maxDimension:) for the stats and frame.makeResult(settings:) for the render — letting each drop its bespoke decode-once previewSettings twin. The XISF display-function branch and the previews-preference gating stay in the preview renderer.

Risks & notes

  • Non-goal drift: resist turning DecodedRenderSource into a persistent cache. Its instances are created inside render() / a single preview call and dropped immediately. Holding one across renders reintroduces the memory the design avoids.
  • FITS RGB / cube frames stay on the byte path (double decode) — matching today's preview behaviour. Extending decode-once to those is possible but out of scope.
  • Auto Screen Transfer (the interactive "Auto" button) is a separate consumer of detectionImage / the source's data-derived colour source; it is intentionally untouched here.
  • Build & test through Xcode (xcodebuild, scheme FITScope) — an .xcodeproj exists; keep it and any package manifests in sync. New files must be wired into the target via project.pbxproj.
  • Submodules (SwiftPixel / SwiftAstro) are not expected to change: the decode-free render cores already exist there; the new seams are app-side. Any submodule change surfaced during implementation must be raised first.
