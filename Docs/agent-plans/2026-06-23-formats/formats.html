FITScope — Formats & Dimensionality Roadmap

Generated: 2026-06-23

Scope: Everything here is about expanding what FITScope can open — both new file formats (non-FITS rasters, XISF) and new data dimensionalities within FITS (1-D, 3-D, ≥3-D). It deliberately excludes the astro/feature work in Phase 5+.

Source document consolidating the five evaluation outcomes from the implementation plan (M4.6–M4.10), to be turned into one or more milestone plans later.

All findings below are grounded in the current code as of this date:

  • The open path is FITS-only: Info.plist declares gov.nasa.gsfc.fits; AppModel.runOpenPanel() sets allowedContentTypes = [.fits]; DropAcceptance gates drops.
  • FITSImageLoader.load() → FITSFile(data:options:.lenient) → builds FITSImageInfo(url:file:) (metadata from header cards) + a FITSImageRenderer.RenderInput (data: Data + properties: [FITSPropertySnapshot]).
  • ImageProcessor.render(data:properties:settings:) validates and requires BITPIX (8/16/32/−32/−64), NAXIS == 2, NAXIS1/2, optional BAYERPAT. It is the single gate that rejects everything non-2-D.
  • The SwiftPixel PixelPipeline.run(...) accepts single-channel input and synthesizes colour (expand 1→3, or demosaic CFA→RGB). PixelBuffer itself already supports N channels, but no run entry point ingests a pre-built multi-channel buffer.
  • FITSImageInfo (and the info panel, headers window, and all Phase 5 astro features) read FITS header keywords. SwiftFITS's FITSSection exposes data, bitpix, naxis, and naxis(n) for any axis.

The three shared foundations

These are the reusable pieces every track below leans on. Building them once, deliberately, is the difference between a clean expansion and five bolted-on special cases.

F1ImageSource loader abstraction

A seam above the FITS specifics so a window can hold either a FITS-backed or a non-FITS-backed image, both feeding the existing renderer/inspector. The natural boundary is the renderer's input: generalize from "raw FITS bytes + properties" to "a renderable buffer + a metadata snapshot."

Used by: non-FITS rasters (M4.6), XISF (M4.10).

F2Multi-channel PixelBuffer entry point (SwiftPixel)

An additive PixelPipeline.run that accepts a pre-built multi-channel buffer and skips the 1→3 expansion, then runs the colour-appropriate processor subset (stretch, gamma, white balance, brightness/contrast, saturation, levels, curves, invert, orient — not debayer / raw-scale). PixelBuffer already models N channels, so this is additive, not a redesign.

Used by: non-FITS RGB (M4.6), FITS colour cubes (M4.8), XISF RGB (M4.10).

Note: SwiftPixel changes are marked approved in the plan legend, but re-confirm before editing the submodule.

F3N-dimensional plane model (index vector)

Model the displayed plane of an N-D FITS array as a higher-axis index vector (one selector per axis above 2), not a single scalar. Because NAXIS1/NAXIS2 are always the two fastest axes, any single display plane is one contiguous W·H·bpp byte range at offset p·W·H·bpp, where p = i₃ + N₃·(i₄ + N₄·(…)). Slicing is pure in-app arithmetic over the existing RenderInput.data, reusing decodeSample + scaling.

Used by: 1-D (degenerate), 3-D (M4.8), ≥3-D (M4.9).

Track A — File formats

M4.6 — Non-FITS rasters (PNG/JPEG/TIFF, then HEIC; RAW later)

Verdict: Go, scoped, as its own plan.
  • The decode is trivial (CGImageSource); the cost is that the model is FITS-shaped end to end (FITS-keyword render contract, single-channel pipeline, FITS-only metadata).
  • Needs F1 (loader seam) and F2 (multi-channel buffer) for colour. Metadata becomes EXIF/TIFF → an info-panel mapping, with the FITS headers window gracefully empty.
  • First slice: 8-bit PNG/JPEG/TIFF (LDR, RGB or grayscale). HEIC second (10-bit / wide-gamut / colour-space handling). RAW is a separate, much larger evaluation (demosaic + develop via CIRAWFilter) — do not bundle.
  • Effort: medium, ~5–6 milestones — F1 + UTType/open-panel/drop changes; F2; raster render path + histograms; EXIF→info mapping; branch FITS-only inspector controls (debayer); tests.

M4.10 — XISF (PixInsight's format)

Verdict: Go eventually, as its own dedicated plan, after F1 lands.
  • Open, free spec. Monolithic file = UTF-8 XML header + binary data blocks. Sample formats (UInt8/16/32, Float32/64) are exactly the app's BITPIX set, with planar multi-channel storage like FITS planes — so decodeSample/scaling and the 2-D pipeline largely apply. XML parses with XMLParser.
  • One new dependency: decompression. Blocks may be zlib / lz4 / lz4hc / zstd (± byte-shuffling). Apple's Compression framework covers zlib + lz4 (shuffle is trivial); zstd is not and needs an external dep. First slice = uncompressed + zlib (+ lz4); defer zstd.
  • Metadata fits: XISF carries FITS keywords + XISF properties → maps to the existing info panel / headers window.
  • Licensing — write clean-room. No Swift library exists; the notable open one (sergio-dr/xisf) is Python + GPLv3, incompatible with this app's MIT licence. Implement a fresh Swift reader from the open spec.
  • Architecture: a dedicated SwiftXISF submodule (XML → block extraction → decompress/un-shuffle → decode) plugging into F1, with RGB sharing F2.
  • Effort: large (from-scratch format submodule). Sequence after F1; first slice = monolithic, uncompressed+zlib(+lz4), mono+RGB, embedded FITS keywords; defer distributed files, zstd, thumbnails, ICC profiles.

Spec / references:

  • PixInsight — XISF: https://pixinsight.com/xisf/
  • XISF 1.0 Specification: https://pixinsight.com/doc/docs/XISF-1.0-spec/XISF-1.0-spec.html
  • sergio-dr/xisf (Python, GPLv3): https://github.com/sergio-dr/xisf

Track B — FITS data dimensionality

All three of these are one feature family built on F3, and should likely be one "N-dimensional data / data-cube" plan.

M4.7 — NAXIS=1 (1-D data, e.g. spectra)

Verdict: Go; small–medium, self-contained.
  • The only block is ImageProcessor.render's guard nAxis == 2; the 1-D bytes already reach the renderer, and decoding a series reuses decodeSample + scaling. Swift Charts is available (macOS 14 target).
  • It's a presentation, not a render: the whole detail pane assumes a CGImage, and the floating toolbar, cursor read-out, histogram and every inspector section are image-only.
  • Approach: model a content kind (image Result or a Series = [Double] + x-axis metadata); relax the gate so NAXIS=1 decodes to a series; route the detail pane to a new SpectrumChartView (Swift Charts LineMark); inspector shows info-only. Optional WCS axis mapping (CTYPE1/CRVAL1/CRPIX1/CDELT1/CUNIT1 for X, BUNIT for Y). Unit-test decode-to-series + routing.
  • Out of scope: BINTABLE spectra; single-row NAXIS=2.
  • Effort: small–medium, ~3–4 milestones.

M4.8 — NAXIS=3 (3-D: colour cubes vs. stacks)

Verdict: Go, scoped. SwiftFITS flag resolved → no change needed.
  • Two semantically different cases with no definitive FITS marker: colour cube (NAXIS3=3 → one RGB image) vs. stack/data cube (N planes: spectral, time, focus…).
  • Stack path — cheap, very high reuse: relax the gate, add a plane index (F3), render the selected plane through the unchanged 2-D pipeline. No submodule change.
  • Colour-cube path — heavier: combine 3 planes into one RGB image → needs F2; until then a colour cube is still browsable as 3 mono planes.
  • Disambiguation: default NAXIS3=3 → colour, with a per-file toggle (treat-as-colour ↔ browse-planes), optionally informed by CTYPE3.
  • UI: plane slider/stepper, optional CTYPE3/CRVAL3/CDELT3 labelling, optional playback for time series.
  • Effort: medium, ~3–5 milestones.

M4.9 — NAXIS≥3 (hypercubes, e.g. NAXIS=4 RA/Dec/freq/Stokes)

Verdict: Go, by folding into M4.8 — essentially zero extra architecture.
  • A hypercube is M4.8 generalized: every axis above 2 just selects which contiguous plane is shown. If M4.8's plane selection is built as a per-axis index vector (F3) from the start, NAXIS=3/4/5… all work uniformly.
  • No SwiftFITS change (same as M4.8); only one plane decoded at a time, so large cubes are fine on memory/perf.
  • Incremental work over M4.8: N−2 sliders/steppers, each labelled by CTYPEk (+ CRVALk/CDELTk); special-case a STOKES axis to I/Q/U/V.

Recommended sequencing

  1. F1 — ImageSource loader seam (unlocks both non-FITS rasters and XISF).
  2. F2 — multi-channel PixelBuffer entry point (unlocks all colour: rasters, FITS colour cubes, XISF RGB).
  3. Track B / F3 — one "N-dimensional data" plan (M4.7 + M4.8 + M4.9): build the index-vector plane model; ship 1-D charts, plane-stack browsing, and hypercube navigation together. Colour-cube combine lands once F2 exists.
  4. M4.6 first slice — 8-bit PNG/JPEG/TIFF (on F1 + F2), then HEIC.
  5. M4.10 — SwiftXISF dedicated plan (on F1 + F2), uncompressed+zlib first.
  6. RAW — its own separate evaluation, much later.

Track A (formats) and Track B (dimensionality) are independent once F1/F2/F3 exist and can proceed in parallel. F1 and F2 are the highest-leverage first steps because four of the five items depend on them.
